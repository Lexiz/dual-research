Design system · v2.0.1 · two modes · light + dark

A locked visual contract for nine kinds of architecture diagram — in two parallel design systems, each shipping light + dark.

The diagram skill ships two design systems side-by-side. Pixel (the default) is cream + indigo on a polished doc page — the system this site has documented since v1. Material is a Material 3 sibling — sable + sage palette, Roboto Flex + Roboto Serif type, Material Symbols Outlined icons, all design tokens owned by the skill in references/material/_tokens.css. Every diagram emits a pair of self-contained SVGs under the requested mode: <slug>.<mode>.{light,dark}.svg. Diagrams ship in clusters of 3–6 for any given proposal; cross-diagram coherence across both themes and within one mode is the quality bar. Each mode locks its own primitives — cards, icons, connectors, spacing — into a closed, named, copy-pasteable library, and the shared manifest mechanism pins mode, theme, and entity → gradient → icon across a whole set.

What's new in v2.0.1. Material mode rebuilt natively against M3 tokens (no more mechanical transform from Pixel) — the skill folder is now fully self-contained, design tokens owned by material/_tokens.css. Canonical example set (36 SVGs across 9 templates × 2 modes × 2 themes) regenerated with a generic OrderFlow worked example. Mode-aware routing (pixel default; material opts into M3), per-set mode: + theme: pin in the manifest — see manifest §07.5. Pixel mode is at pixel/; Material mode is at material/. 00.1What changed

The current skill ships abstract rules and lets the model fill the gaps. The annotated screenshot in screenshots/ shows what happens when the gaps are visual primitives — icons crash through titles, labels rotate vertically, arrows route through cards, deferred state is drawn two different ways in the same diagram. Each fix below is a named primitive the generator references by ID instead of inventing.

Before — abstract rules

“~40px breathing room.” One number, applied to every situation: cards adjacent, cards with arrows between, columns, stages, canvas edges. Every template invents its own card geometry from scratch.

  • No card primitive — icon position drifts per template
  • No spacing system — arrows crowd cards
  • No connector geometry — labels rotate, lines cross unrelated cards
  • No fallback icon — unknown services get improvised
  • No set manifest — same service looks different in two figures

After — named primitives

Tokens, components, markers, lanes. A generator that knows only the names card.primary, arrow.solid-primary, and --gap-card can produce a diagram visually identical to the canonical example.

  • 8 card variants + 6 shape primitives with reserved slots
  • 14 spacing tokens, used by name across all templates
  • 8 arrow types · gutter system · label zones · crossing jogs
  • 78 icons in 9 categories + monogram fallback + 6 shape primitives
  • YAML manifest that pins entity → gradient → icon set-wide

00.3The four hard rules

Everything in the spec ladders up to four principles. When a downstream generator faces ambiguity, fall back to these.

01 · One identity, nine templates, two themes

The cream-and-indigo identity is fixed for light; a near-black + lifted-indigo identity is fixed for dark. Background gradient, indigo accent, Inter, viewBox width 1660 — none of these vary across the nine templates or between themes (structurally). Every other choice cascades from this.

02 · Geometry by token, not by guess

Every spatial decision references a named token (--gap-card, --lane-gutter, --label-clearance). “Looks fine here” is not a layout strategy. If a number isn't in the registry, the generator doesn't get to invent one.

03 · Same service, same look, both themes

A “Postgres” card in the system-context diagram and the sequence diagram of the same proposal must use the same gradient id, same icon, same label string — in light and in dark. The set manifest pins these once; the theme pass swaps stop values, not assignments.

04 · Improvise nothing

Cards, icons, arrows, chips, labels — all named in this spec. If the system needs a primitive that isn't here, it doesn't get invented inline; the system uses the documented fallback (e.g. icon.generic-service with a monogram).

01.0Theme model

Every diagram ships in two flavors — light (cream canvas, the v1 spec) and dark (near-black canvas). The two share everything structural: viewBox, layout, type roles, spacing tokens, animation classes, connector geometry, manifest pins. They differ only in color values. Below is the contract. Every token in the rest of this page has a dark sibling named --<token>-dark.

Light · default · v1

Cream & indigo on a polished doc page.

Vertical gradient #f5f1ea → #ece8e0. Dark categorical cards float on cream with a soft drop shadow. Light cards are white or warm-tint on cream, separated by 1px --rule strokes. Ink scale runs #1a1a18 → #9e9b95. Indigo identity at #4f5fb8.

Files emit as <slug>.light.svg.

Dark · new · same diagram

Near-black canvas with lifted categorical surfaces.

Vertical gradient #1a1a1f → #14141a. Categorical surfaces lift one value step toward mid-tone so they stay elevated; light cards become neutral mid-tones (#252531) separated by 1px rgba(255,255,255,0.10) strokes (no drop shadow). Ink scale inverts. Indigo lifts to #7785d4 for AAA-adjacent contrast.

Files emit as <slug>.dark.svg.

Surface gradient ids are theme-agnostic

Inside an emitted SVG, gradient ids stay stable: <linearGradient id="surfaceSql"> in both .light.svg and .dark.svg. What differs is the stop-color values inside. This lets every connector reference (fill="url(#surfaceSql)") and every card primitive author once and render correctly in either theme — the theme pass swaps stop values, not ids.

Filter ids are theme-agnostic too

The two shadow filters (cardShadow, cardShadowDark) keep the same ids across themes. The dark theme rewrites their bodies — cardShadow becomes a near-zero halo at rgba(255,255,255,0.08) (elevation via stroke-like glow), cardShadowDark becomes a deeper #000000 drop at 0.55 opacity. See §01.5.

Dual-output workflow

The skill emits two SVG files per diagram. Step 5 generates one layout; the theme pass applies each token set to produce the two files. Step 6 renders both PNGs and runs the self-review checks against each independently — see SKILL.md §5–7. A multi-diagram set pinned by theme: both in its manifest ships 2 × N SVGs.

Decisions locked. Two-file output (no prefers-color-scheme); theme-suffix naming; mixed elevation strategy (light cards lose shadow, dark cards deepen it); neutral mid-tone dark surfaces; manifest-level theme is authoritative.

Theme portability

All five keyframes and seven classes are theme-agnostic — the timing, easing, and shape of every animation is identical across light and dark renders. The one keyframe with literal colors is tick (#3d7f5b → #5aad80); both greens read on the dark canvas (luminance ≥ 0.30, ratio ≥ 6:1 against #1a1a1f), so no dark-variant keyframe is needed. If a future status color is added that fails the dark legibility check, define a sibling keyframe <name>-dark rather than overwriting the existing one.

01.7Cross-template consistency rules

A proposal ships 3–6 diagrams. Today the same Postgres can show up as --surface-sql in one and --surface-neutral in another, because each template re-decides. The rules below are enforced by the set manifest; this is the list it pins.

  • Service → gradient is pinned per-set. First diagram in the set declares the mapping; every subsequent diagram in the same proposal consults it.
  • Service → icon is pinned per-set. Same logical service uses the same icon shape (e.g. cylinder for Postgres) wherever it appears.
  • Label string is pinned per-set. “Postgres” is “Postgres” everywhere — not “Cloud SQL” in one diagram and “the DB” in the next.
  • Title typography is identical. Same size, weight, letter-spacing, position (centered, y=56).
  • Letter-spacing values come from --type-section and --type-conn-label. Never tighten or loosen for one diagram.
  • Margin and gap tokens are identical. A “wide” diagram doesn't get to compress --gap-card — it uses --canvas-width-wide instead.
  • Theme is pinned per-set in the manifest. Within one proposal, all diagrams render at minimum all-light or all-dark; the default theme: both ships both flavors of every figure. Per-diagram theme override is a hard error — see Set manifest §07.4.
The set manifest enforces these. A one-page YAML stub authored on the first diagram becomes part of the conversation; subsequent diagrams read it before generating. See Set manifest for the schema.

04.4Lanes & gutters · parallel arrows

When two or more arrows run between the same region pair, they need reserved space to live in. Without it, they bunch onto one line and become illegible.

04.4a
Gutter rule. When ≥2 arrows run between the same region pair, allocate a --lane-gutter (16px) reservation between adjacent lanes. Each lane is centered on its allocated row; labels sit above each lane's own line, never shared.
04.4b
Card height stretches to accommodate lanes. If you have 3 parallel arrows landing on a card, the card's height must support 3 lanes × --lane-gutter. The card grows; the lanes don't crowd.
04.4c
Trunk collapse. When >3 parallel arrows exist between the same region pair, collapse them into a single labeled trunk arrow with a chip.count badge (“4 EVENTS”). The individual semantics belong in the receiver's body text or in a footnote, not as four arrows.

04.5Label placement · zones & the no-rotation rule

The “DESIGN DOCS” / “MERGED PRS” rotation failure from the screenshot lives here. The fix is mechanical: a label occupies one of three zones, and rotation is forbidden. If horizontal space isn't sufficient, the arrow changes shape, not the label.

the three legal label zones--label-clearance 12 · no rotation, ever
bad — label rotated for cross-column linescreenshot pattern
good — line jogs to make room, label horizontalafter
04.5a
No rotated labels — ever. Vertical text is hard to read at every scale. If the natural horizontal label position is blocked, the arrow changes shape (zone C pill on a jog) or the label becomes a chip.label on its owning element.
04.5b
Every connector label is bound to its line. Floating ALL-CAPS labels (like the “MCP TOOLS” / “EMBEDS” problem) are forbidden. If the label describes a region, it's a chip.label on a card. If it describes a flow, it sits in zone A above that line.
04.5c
Label-on-label collision is impossible by spec. Two labels in the same zone within --label-clearance × 2 (24px) of each other = move one arrow into a different lane. Two labels overlapping is never an aesthetic decision.

04.8Connector contract · the checklist

A diagram passes the connector contract if every one of these is true. If any is false, the diagram is wrong — not a matter of taste.

  • Every arrow has a named type from the eight-arrow taxonomy
  • Every arrow uses a marker from the registry — no inline marker definitions
  • Curve mode matches the geometry rule (straight axial / Q short / C long)
  • No bend has radius below --bend-radius (24) or angle above 60°
  • Parallel arrows are spaced --lane-gutter (16) apart; >3 parallel collapses to a trunk
  • Every label sits in zone A, B, or C — no rotation, no float, no overlap
  • Every label is bound to a specific line (or it's a chip on a card, not a connector label)
  • Crossings ≤ 3; jog applied per the priority rule (secondary over primary, short over long)
  • No arrow passes within --arrow-clearance (16) of any unrelated card
  • Arrows end --arrow-stub (8) short of card edges
  • All density caps respected — when in doubt, split the diagram

Cross-diagram consistency mechanism

A one-page YAML stub authored on the first diagram. Every later diagram in the set reads it.

Today's SKILL.md says “read the first diagram and use it as the style anchor.” That's hopeful but unenforceable — the model has to re-derive what's anchored every time. A small manifest, authored once at the start of a proposal and persisted in the conversation, lets every later diagram look up the answer instead of inferring it.

07.1What it pins

The manifest is a closed list of the things that must be identical across a set. It does not pin layout or content — those are per-template decisions. It pins identity.

07.3Lifecycle

Three checkpoints. Skipping any of them means a downstream diagram drifts.

on first diagram

Author the manifest

As you build the first diagram, write the YAML. Every service you decide to draw gets a row in services:. Save it inline in the conversation or as a sibling file.

on each later diagram

Look up before drawing

Before instantiating any card, look up its service in services:. Use the pinned label, surface, and icon. If the service isn't in the manifest, add it now and propagate.

on any change

Re-render the set

If the manifest changes (a service is renamed, a gradient swap), every diagram in the set is regenerated. The whole point is that the set is coherent — partial updates aren't allowed.

07.4Theme pinning

Theme is set-level, not diagram-level. A proposal is a coherent reader experience: either it ships in one theme, or it ships both flavors of every figure (the default). A per-diagram theme override is a hard error — generate the one-off outside the set if you want it.

theme: valueOutput behavior
bothDefault. Emit <slug>.pixel.light.svg and <slug>.pixel.dark.svg for every diagram. A 5-diagram proposal ships 10 files. Identity pins apply to both — the gradient name pins; the gradient value varies by theme.
lightEmit only <slug>.pixel.light.svg. Backward-compatible.
darkEmit only <slug>.pixel.dark.svg. For known-dark hosts.

07.5Mode pinning

Mode is set-level, exactly like theme. A proposal renders in one design system end-to-end — Pixel for one proposal, Material for another, never mixed. The two systems use different palettes, type families, and shadow recipes; intermixing them within a single proposal produces a visually incoherent reader experience.

mode: valueOutput behavior
pixelDefault. Cream + indigo on a polished doc page. Inter type. 78-icon custom library. Files emit as <slug>.pixel.{light,dark}.svg. Use for general-purpose architecture diagrams and subject-agnostic systems.
materialMaterial 3 design system — sable + sage palette. Roboto Flex + Roboto Serif. Material Symbols Outlined icons. Files emit as <slug>.material.{light,dark}.svg. Use when the diagram should share visual DNA with an M3 product surface.

What stays unchanged across modes

The structural pins — services, labels, icons, groups, animation budget — are mode-agnostic by intent. A given service maps to the same surface-token name (e.g. --surface-sql) in both modes; the token's value is what differs. The diagram structure, the layout rules, the input contract — all identical. Mode swaps the rendering, not the meaning.

07.6Where the manifest lives

Two options, depending on workflow.

  • Inline in conversation. For ad-hoc proposals — the YAML lives in the conversation history. The skill reads it before each new diagram. Cheap, ephemeral, fits one-off proposals.
  • Committed as diagram-set-manifest.yaml next to the SVGs. For proposals that go through revision cycles — the manifest is durable, diff-able, and authoritative. The skill loads it from disk on each invocation.
What this replaces. The current “read the first diagram as a style anchor” instruction in SKILL.md. That instruction relies on the model correctly inferring which decisions were intentional vs incidental — the manifest separates them: anything in the manifest is intentional, anything not in it is per-diagram.

Deliverable 04 · Connector geometry

The arrows. Where most visible failures live, made impossible by spec.

Eight named arrow types, a marker registry, a gutter system for parallel arrows, label zones with a hard no-rotation rule, crossing-jog geometry, and density caps that force a diagram to split rather than crowd. If the generator can't honour all of these, the diagram is wrong — split it.

04.0Theme behavior across connectors

Connector geometry is theme-agnostic — every rule on this page (curve modes, lane gutters, label zones, clearance, density caps, crossing priority) applies unchanged to light and dark renders. What differs between the two output files is the color of strokes, marker fills, label text, and the callout-pill chip. The mapping is mechanical and lives in foundations §01.2.

Each output file declares its theme-appropriate markers once. The ids are stable (arrowAccent, arrowGrey, etc.) so every marker-end="url(#arrowAccent)" reference in the SVG body works unchanged across both files. Only the <path fill=> inside the marker differs.

04.1Arrow taxonomy · eight types, one per semantic

Each arrow type carries a specific meaning. The generator picks by semantic, not by aesthetic. solid-primary for high-traffic flow, dashed-handoff for discrete handoff, mirror-secondary for read-only / “also goes here”. Adding a ninth type means the spec is wrong — extend the taxonomy formally, never inline.

the eight arrow typeslive stroke specimens at canon scale
Adding a ninth arrow type is a spec amendment, not a per-diagram decision. If you reach for one (e.g. “a feedback loop with retry semantics”), document it here first, then use. The point of a closed set is that two diagrams in the same proposal read the same way.

04.2Marker registry · exact dimensions

All markers are declared at the top of <defs>. refX places the marker tip relative to the path end; refY centers it. These dimensions are tuned to look correct against a 1.6–2px stroke. Don't scale markers per arrow — pick the named marker that fits.

04.3Curve rules · straight, quadratic, cubic

Three curve modes. Pick by the geometry of the shortest path, not by aesthetics.

three curve modes, three situations--bend-radius 24 · max 60° per bend
RuleValueWhy
--bend-radius24Minimum curvature radius. Below this, a curve reads as a kink. If your control point produces <24, increase the gap between endpoints or switch to straight.
--max-bend-angle60°No single curve may bend more than 60°. If the geometry demands more, you need a different layout — not a sharper curve.
curve choiceL · Q · CStraight for axial. Quadratic for offsets up to ~200px. Cubic for longer S-curves spanning rows or columns. Don't mix.
cornersforbiddenNo M…L…L… right-angle elbows. Use Q with a control point at the corner instead.

04.4Lanes & gutters · parallel arrows

When two or more arrows run between the same region pair, they need reserved space to live in. Without it, they bunch onto one line and become illegible.

bad — arrows bunch on one center-linebefore
good — gutter of 16 between parallel lanesafter
04.4a
Gutter rule. When ≥2 arrows run between the same region pair, allocate a --lane-gutter (16px) reservation between adjacent lanes. Each lane is centered on its allocated row; labels sit above each lane's own line, never shared.
04.4b
Card height stretches to accommodate lanes. If you have 3 parallel arrows landing on a card, the card's height must support 3 lanes × --lane-gutter. The card grows; the lanes don't crowd.
04.4c
Trunk collapse. When >3 parallel arrows exist between the same region pair, collapse them into a single labeled trunk arrow with a chip.count badge (“4 EVENTS”). The individual semantics belong in the receiver's body text or in a footnote, not as four arrows.
trunk collapse · 5 arrows → 1 + chip.countdensity rule applied

04.5Label placement · zones & the no-rotation rule

The “DESIGN DOCS” / “MERGED PRS” rotation failure from the screenshot lives here. The fix is mechanical: a label occupies one of three zones, and rotation is forbidden. If horizontal space isn't sufficient, the arrow changes shape, not the label.

the three legal label zones--label-clearance 12 · no rotation, ever
bad — label rotated for cross-column linescreenshot pattern
good — line jogs to make room, label horizontalafter
04.5a
No rotated labels — ever. Vertical text is hard to read at every scale. If the natural horizontal label position is blocked, the arrow changes shape (zone C pill on a jog) or the label becomes a chip.label on its owning element.
04.5b
Every connector label is bound to its line. Floating ALL-CAPS labels (like the “MCP TOOLS” / “EMBEDS” problem) are forbidden. If the label describes a region, it's a chip.label on a card. If it describes a flow, it sits in zone A above that line.
04.5c
Label-on-label collision is impossible by spec. Two labels in the same zone within --label-clearance × 2 (24px) of each other = move one arrow into a different lane. Two labels overlapping is never an aesthetic decision.

04.6Crossings · which arrow jogs over which

Crossings are unavoidable in some layouts. When they happen, the rule is deterministic: the secondary arrow jogs over the primary; if both are primary, the shorter jogs over the longer.

04.7Clearance & density caps

The MCP-Adapter-through-the-cards failure from the screenshot lives here. The fix: an arrow can't pass within --arrow-clearance (16px) of any card it doesn't terminate at. If geometry demands closer, the arrow routes around.

TokenValueRule
--arrow-clearance16Minimum perpendicular distance between any arrow and any card it doesn't terminate at.
--arrow-stub8Arrow path ends 8px short of the card edge so the arrowhead has air.
--lane-row56Minimum vertical separation between successive horizontal arrows in a sequence diagram.

Density caps · the “split it” numbers

When any of these is exceeded, the diagram must be split or simplified. These are not aesthetic targets — they are the line below which a diagram becomes unreadable.

CapLimitWhat to do if exceeded
Arrows entering or leaving one card6Group functionally related arrows into a single trunk, or move the card's role onto two cards.
Parallel arrows in one region pair3Collapse to a single trunk + chip.count (see 04.4c).
Crossings per diagram3Re-layout. If the geometry truly requires more, split the diagram.
Cards per diagram18Above this the diagram reads as a list. Use a higher-level system-context view + drill-down.
Distinct arrow types per diagram4If a fifth seems needed, two of them are doing similar work. Merge.
Distinct surface gradients per diagram5Above this, the legend dominates the diagram. Re-map a category to --surface-neutral.
Why caps and not “use judgment”. A locked spec lets the generator say “this won't fit” instead of crowding silently. The annotated screenshot is the result of judgment under pressure; caps make pressure visible early.

04.8Connector contract · the checklist

A diagram passes the connector contract if every one of these is true. If any is false, the diagram is wrong — not a matter of taste.

  • Every arrow has a named type from the eight-arrow taxonomy
  • Every arrow uses a marker from the registry — no inline marker definitions
  • Curve mode matches the geometry rule (straight axial / Q short / C long)
  • No bend has radius below --bend-radius (24) or angle above 60°
  • Parallel arrows are spaced --lane-gutter (16) apart; >3 parallel collapses to a trunk
  • Every label sits in zone A, B, or C — no rotation, no float, no overlap
  • Every label is bound to a specific line (or it's a chip on a card, not a connector label)
  • Crossings ≤ 3; jog applied per the priority rule (secondary over primary, short over long)
  • No arrow passes within --arrow-clearance (16) of any unrelated card
  • Arrows end --arrow-stub (8) short of card edges
  • All density caps respected — when in doubt, split the diagram

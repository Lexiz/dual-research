Deliverable 05 · Per-template visual contracts

Each of the nine templates gets one page of binding visual rules.

A visual contract is a five-field card per template: which components from the library it uses, which icons it pulls from the set, the spacing and layout rules specific to that diagram type, which arrow types appear, and the anti-patterns to avoid. The semantic-side guidance — "what information to capture" — stays in the shared template Markdown at references/templates/<name>.md; these contracts replace the visual-side guidance only.

9templates 5contract fields each 2themes per template 18canonical SVGs

05.0Theme behavior across templates

Every template's visual contract is theme-agnostic. The components used, icons pulled, spacing and layout rules, arrow types, and anti-patterns are all identical between light and dark renders. The only thing that differs per template is the color values referenced via foundation tokens — and those swap mechanically per foundations §01.0.

TemplateDark behavior
layered-architectureIdentical layout. Surface tokens swap. Layer dividers use --rule-strong-dark. Lane gutters unchanged. See examples/layered-architecture.{light,dark}.svg.
pipeline-flowIdentical layout. Stage tokens use --indigo-dark for the circle fill. Output cards (reference variant) become --surface-reference-dark. The repair-turn callout pill uses #252531 fill + #7785d4 stroke. See examples/pipeline-flow.{light,dark}.svg.
sequenceIdentical layout. Lane lifelines use --rule-strong-dark. Lifeline labels swap to --ink-1-dark. Activation boxes stay solid surface gradient.
system-contextIdentical layout. External integration tiles use the same monogram surfaces. Trust boundary stroke uses --indigo-dark.
data-schemaIdentical layout. Entity card chrome lifts; PK/FK chip fills use --surface-tint-dark; relationship lines use --ink-3-dark.
infrastructureIdentical layout. Region/VPC boundaries use --ink-4-dark dashed; cloud-provider icons follow the icon matrix (§03.0).
event-flowIdentical layout. Topic/queue cards use lifted --surface-slate-dark; consumer fan-out arrows use the dark primary stroke.
connector-mapIdentical hub-and-spokes geometry. Spoke monograms follow §03.4 mapping in both themes.
freeformIdentical layout. Multi-column strategies unchanged. All component primitives follow their own theme behaviors from components §02.0.
Rule: a template that needs theme-specific layout decisions does not exist in this system. If you find yourself wanting to move a card or reflow a region in the dark variant, the problem is in foundations, not in the template — fix the tokens and regenerate both.

05.1Layered architecture

templates/layered-architecture.md
Horizontal layers with handoff arrows downward
filled · v1
Components
card.secondary for outer-edge layers (surfaces, third-parties)
card.primary in 4 surface variants for the active layer
Layer header = --type-section centered, no boundary box needed
Icons
By layer role: surfaces → icon.browser/.mobile/.terminal; API → icon.gateway; services → icon.agent/.service/.worker; data → icon.sql/.bucket/.cache
Layout
viewBox 1660 × auto (typically 800–880)
Layer rows: 4 layers max, --gap-section (72) between layer baselines
Cards in a row use --gap-card (56)
Arrows
solid-primary downward between adjacent layers
mirror-secondary for read-replica / lookup
Lane gutter applies when ≥2 arrows land on the same lower-layer card
Anti-patterns Upward arrows (data layer should not arrow back to API). Five or more layers (split into two diagrams). A “mixed” layer combining services and data (use separate layers).

05.2Pipeline flow

templates/pipeline-flow.md
Left-to-right numbered stages with typed outputs
filled · v1
Components
stage.numbered-token for each stage (ø28)
card.primary hero per stage (240×120 fixed)
card.reference optional sub-row showing typed output
stage.divider only when an asynchronous boundary exists between two stages
Icons
By stage role — usually one icon per hero card. icon.scheduled for cron stages; icon.function for transform stages
Layout
viewBox 1660 × auto (typically 620–700)
5 stages fit comfortably at --gap-stage (120)
7+ stages → split. Never wrap to a second row.
Arrows
solid-primary between adjacent stages, label ALL-CAPS in zone A naming the transformed payload
dashed-handoff for the (max 1) bounded feedback loop, label as a zone-C pill
Anti-patterns Cross-stage arrows that aren't strictly adjacent. Multiple feedback loops. A stage with no card (the numbered token alone is not a stage). Wrapping stages to a second row.

05.3Sequence

templates/sequence.md
Time-ordered messages between actor lifelines
filled · v1
Components
lane.header as light card or surface variant per actor type
lane.vertical dashed lifeline dropping from each header
lane.activation-box on actors that are busy across rows
callout.note sparingly, tethered or anchored to a lane
Icons
Inside lane headers only — keep them small (no icon slot box, just a 20px icon). Actor type drives the icon (user, browser, gateway, sql, etc.)
Layout
viewBox 1660 × auto (height = 200 + N × --lane-row + 80)
Up to 6 lanes at --lane-width (240)
7+ actors → split or collapse a peripheral one
Arrows
sync-call for requests (solid slate)
return for responses (dashed-open slate)
async-event only when the message is fire-and-forget
All labels horizontal, no rotation
Anti-patterns Rotated labels (always horizontal — split a long message into a label + italic subtitle instead). Activation boxes on every actor (only on actors that meaningfully span ≥2 rows). Crossings between message arrows (re-order lanes instead).

05.4System context

templates/system-context.md
C4-level-1 — the system, its users, and what it touches
Components
One hero card.primary centered (the system). Surrounding card.compact for actors and externals. group.boundary for the system trust boundary.
Icons
icon.user/.admin/.analyst for actors. icon.external/.api-external/.connector for third-parties. icon.gateway for the system itself.
Layout
Radial — hero at canvas center, satellites on a ring. --gap-card-arrow at minimum between hero and any satellite.
Arrows
solid-primary for primary usage. mirror-secondary for ancillary data flows. Labels describe verb (sends, syncs, reads).
Anti-patterns More than one hero (split into multiple context diagrams). Internal components (those belong in layered/infrastructure). Bare arrows with no verb label.

05.5Data schema

templates/data-schema.md
ER-style entities with typed fields and relationships
Components
card.secondary with a stack of typed-field rows. card.reference for enums / lookups. Field rows use the monospace type.
Icons
A 16×16 PK / FK badge inside the field row when relevant. No service icons in this template.
Layout
Free-flow with implicit columns (parents left, children right). --gap-card minimum.
Arrows
solid-primary with crow's-foot endpoint variants (1:1, 1:N, N:M). Labels are the FK column name.
Anti-patterns Inheritance arrows (use one card per concrete table). All-table mega-diagrams (split by aggregate root).

05.6Infrastructure

templates/infrastructure.md
Cloud topology — VPC, regions, compute, storage, queues
Components
group.boundary heavy use — region, VPC, subnet (up to 2 nested levels). card.primary in surface variants for the infra components themselves.
Icons
The full network + data + compute set. Strong consistency rule: same cloud service = same icon across diagrams.
Layout
Nested boundaries with --boundary-pad 32 inset. Cards within a region cluster by layer (compute top, storage bottom).
Arrows
Solid for primary traffic. Often paired with a protocol label (HTTPS, gRPC, TCP/5432). Avoid showing every connection — only the topologically important ones.
Anti-patterns Drawing every network link (the diagram becomes a hairball). Three-level deep nesting (split). Cloud-provider logos (use the generic icon set + label).

05.7Event flow

templates/event-flow.md
Producers → topics → consumers
Components
card.primary for producers and consumers. card.primary with --surface-slate + icon.stream for topics (centered).
Icons
icon.service/.worker/.function for producers/consumers. icon.stream for every topic.
Layout
Producers on left column, topics in middle column, consumers right. Trunk-collapse rule applies aggressively when 4+ events flow between same pair.
Arrows
async-event (dotted indigo) for every producer→topic and topic→consumer line. Labels are event names in ALL CAPS.
Anti-patterns Drawing every event individually when there are >3 from one producer to one topic. Synchronous arrows (use sequence diagram instead). Implicit topic ordering — always label.

05.8Connector map

templates/connector-map.md
Central hub, spokes to integrations
Components
One card.primary hub, many card.compact (160×56) spokes. Optional group.boundary grouping spokes by category.
Icons
Heavy use of icon.generic-service monogram fallback — most integrations don't have a slot in the canonical icon set.
Layout
Hub centered. Spokes arranged in 2 or 3 columns either side, never in a literal circle (radial layouts crowd the labels).
Arrows
Short solid-primary for live integrations, mirror-secondary for read-only / future. Labels are the protocol or product (OAuth, webhook, REST).
Anti-patterns Radial spoke layout (labels collide). Spokes without a category. Hub with two “hub” cards (collapse to one or split into two maps).

05.9Freeform · the catch-all

templates/freeform.md (NEW)
For anything that doesn't fit the other eight
Components
Any component from the library is allowed. Pull from the appropriate templates as starting points. The constraint is the spec, not the specific shape.
Icons
From the canonical set. Use icon.generic-service for anything unmapped.
Decomposition
Identify nouns → cards
Identify verbs / interactions → arrows from the taxonomy
Identify groupings → boundaries
Identify ordering → numbered stages or lanes
Arrows
Any from the taxonomy. Use the connector contract checklist (04.8) before claiming the diagram is done.
Anti-patterns Inventing a new card shape or arrow type because the situation feels new — the situation usually isn't. Choosing freeform when one of the eight templates fits with a small adaptation.

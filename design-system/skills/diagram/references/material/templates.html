Deliverable 05 · Per-template visual contracts

Each of the nine templates gets one page of binding visual rules.

A visual contract is a four-field card per template: which M3 primitives + diagram extensions it uses, which Material Symbols it pulls from the set, the spacing and layout rules specific to that diagram type, and which arrow types appear. The semantic-side guidance ("what information to capture") stays in the mode-shared template Markdown at references/templates/<name>.md; these contracts replace the visual-side guidance only.

9templates 4contract fields 2themes each 18canonical SVGs
Mode-shared input contracts. The data a template asks for is identical between Pixel and Material — both modes consume the same references/templates/<name>.md files. Mode-specific differences live only in this page (visual contract) and in foundations.html / components.html (token + primitive vocabulary).

05.0Theme behavior across templates

Every template's visual contract is theme-agnostic. The primitives composed, icons pulled, spacing and layout rules, arrow types, and anti-patterns are identical between light and dark renders. The only thing that differs per template is the M3 token values referenced by the V2 classes — and those swap mechanically per foundations §01.0.

TemplateDark behavior
layered-architectureIdentical layout. M3 surface tokens flip via body.light rule. Layer dividers use --md-outline-variant.
pipeline-flowIdentical layout. Stage tokens use the theme-portable info-blue (--md-tertiary) circle fill in both themes.
sequenceIdentical layout. Lane lifelines use --md-outline-variant. Activation boxes stay --md-tertiary at 0.4 opacity (theme-portable).
system-contextIdentical layout. External integration tiles use the same md-card--service-* variants. Trust boundary stroke uses --md-tertiary.
data-schemaIdentical layout. Entity card chrome lifts via M3 surface-container tier; PK/FK chips use --md-tertiary-container; relationship lines use --md-on-surface-faint.
infrastructureIdentical layout. Region/VPC boundaries use --md-outline-variant dashed; provider icons follow Material Symbols mapping (§03.4).
event-flowIdentical layout. Topic/queue cards use md-card--service-slate; consumer fan-out arrows use --md-tertiary.
connector-mapIdentical hub-and-spokes geometry. Spoke monograms follow §03.4 mapping in both themes.
freeformIdentical layout. All component primitives follow their own theme behaviors from components §02.0.
Rule: a template that needs theme-specific layout decisions does not exist in this system. If you find yourself wanting to move a card or reflow a region in the dark variant, the problem is in foundations, not in the template — fix the tokens and regenerate both.

05.1Layered architecture

templates/layered-architecture.md
Horizontal layers with handoff arrows downward
Components
md-card--outlined for outer-edge layers (surfaces, third-parties)
md-card--service-* in the appropriate hue for each active layer
Layer header in .t-label-m (uppercase, +0.5px tracking) centered — no boundary box needed
Icons
By layer role: surfaces → web / smartphone / terminal; API → api or hub; services → smart_toy / dns / function; data → database / cloud / bolt
Layout
viewBox 1660 × auto (typically 800–880)
Layer rows: 4 layers max, --ds-gap-section (72) between layer baselines
Cards in a row use --ds-gap-card-arrow (96)
Arrows
solid-primary downward between adjacent layers
mirror-secondary for read-replica / lookup
Lane gutter applies when ≥2 arrows land on the same lower-layer card
Anti-patterns Upward arrows (data layer should not arrow back to API). Five or more layers (split into two diagrams). A "mixed" layer combining services and data (use separate layers).

05.2Pipeline flow

templates/pipeline-flow.md
Left-to-right numbered stages with typed outputs
Components
stage.numbered-token for each stage (36 dia, --md-tertiary fill)
md-card--service-* hero per stage (240 × 120 fixed, hue by stage role)
md-card--service-neutral optional sub-row showing typed output
stage.divider only when an async boundary exists between two stages
Icons
By stage role — usually one Material Symbol per hero card. schedule for cron stages; function for transform stages; biotech for research stages.
Layout
viewBox 1660 × auto (typically 620–700)
5 stages fit comfortably at --ds-gap-stage (120)
7+ stages → split. Never wrap to a second row.
Arrows
solid-primary between stages, single straight line
Optional md-chip--sm on each arrow with the typed output ("validated bytes", "classified records")
.anim-motion-dot on the main path for "running" feel — counts as 1 animation class
Anti-patterns Vertical pipeline. Skipping a stage number. Stages of unequal width (visual rhythm breaks). Adding a "loop back" arrow — internal loops belong inside the stage card, not as cross-stage back-arrows (see SKILL.md "Current state, not history").

05.3Sequence

templates/sequence.md
Vertical lifelines with horizontal messages
Components
lane.header per actor (240 wide × 56 tall, md-card--filled)
lane.vertical dashed lifeline per actor (--md-outline-variant)
lane.activation-box when actor is processing (--md-tertiary at 0.4)
note primitive for sequence-level annotations (use sparingly)
Icons
Inside lane.header — one Material Symbol per actor at top-left. Pick from §03 categories matching the actor type (web, smart_toy, api, database).
Layout
viewBox 1660 × auto (height = header + N × 56 + footer)
4–6 lanes ideal; 8 max before density caps trigger
Messages flow time-down — y position = message order
Arrows
sync-call for request/response pairs (shows wait)
async-event for fire-and-forget
return dashed-thinner for explicit return values
Labels in zone A above the line; subtitle in zone B for payload notes
Anti-patterns Lanes wider than 240 (rhythm breaks). Diagonal arrows (always horizontal). Self-loops on a single lane (use an activation-box extension instead). More than one note per page-fold (notes are interrupts).

05.4System context

templates/system-context.md
Hub-and-stakeholders · what's the system and what touches it
anchor SVG
Components
md-card--outlined for users / actors (left column)
md-card--service-primary for the system hub (center, 600 wide)
md-card--filled + service-* tint for external integrations (right column, 240×140)
group.boundary.trust wrapping the hub
Optional AgentStrip inside the hub when an agent identity is the system
Icons
User actors: person / admin_panel_settings / badge
Hub gets a single hero Material Symbol (hub / smart_toy / api depending on system kind)
External integrations: monogram tiles (2-letter initials) over extension host glyph on service-card tint backgrounds
Layout
viewBox 1660 × 720 standard
3 columns: users (left, 280), platform (center, 600), externals (right, 280)
Trust boundary wraps platform with 32 px inset
Arrows
solid-primary (--md-tertiary) for user-initiated flows (left → hub)
dashed-handoff (--md-on-surface-muted) for system-scheduled flows (hub → externals)
Trust-boundary crossings get a small lock glyph at the boundary
Anti-patterns Putting the hub on one side (always center). More than 5 user cards or 6 externals (split or use connector-map). Inter-external arrows (those belong in infrastructure or connector-map, not here).

05.5Data schema

templates/data-schema.md
Entity-relationship · tables, fields, types, foreign keys
Components
md-card--filled for each entity table
md-chip--sm for PK / FK / UNIQUE / INDEX markers
md-card--service-neutral for enum / lookup tables (visually subordinate)
Icons
database in card header for primary entities (optional — most schemas don't need icons; the row structure tells the story).
Layout
viewBox 1660 × auto
Entities arranged so foreign-key chains read left-to-right
Cards 240 wide; rows inside each card are field name + type + key chip
Arrows
Relationship lines, not arrows — thin --md-on-surface-faint rules between FK field and target PK
"1:N" / "N:M" cardinality in zone-C pill at the midpoint
No arrowheads on relationship lines (they aren't directional flows)
Anti-patterns Putting field types in a different color than field names (use weight, not hue). Drawing FK crows-feet (use simple lines + pills). More than 8 entities (split into bounded contexts).

05.6Infrastructure

templates/infrastructure.md
Cloud topology · regions, VPCs, compute, storage
Components
group.boundary.neutral for regions / VPCs (dashed, --md-outline-variant)
md-card--service-* with the right hue for each compute/storage kind
hexagon primitive for cluster members / mesh nodes
Icons
Heavy icon usage — every card has a category Material Symbol. Compute (dns / deployed_code / function), data (database / cloud / bolt), network (traffic / public / api). Cloud-provider monograms (AWS, GCP, Azure) when the diagram crosses providers.
Layout
viewBox 1660 × auto (often 800+)
Regions stacked vertically or arranged side-by-side
VPCs nested inside regions with second-level group.boundary.neutral
Arrows
solid-primary for synchronous traffic
async-event for cross-region replication
mirror-secondary for read-replicas / backup paths
Anti-patterns Drawing every IAM role (those go in a separate auth diagram). Showing more than 2 levels of nested boundaries (region → VPC is enough; subnet detail goes in a focused sub-diagram). Mixing logical and physical topology (pick one).

05.7Event flow

templates/event-flow.md
Producer → topic → consumers · async-first topology
Components
md-card--service-slate for topics / queues
md-card--filled for producers and consumers
circle primitive (small, --md-on-surface-faint stroke) for partition / shard markers
Icons
Producers: dns / schedule. Topics: sync_alt / water. Consumers: function or service-specific Material Symbol.
Layout
viewBox 1660 × auto
Topics in center column; producers on left, consumers on right
Fan-in (multiple producers → 1 topic) compressed via trunk + count rule (§04.4)
Arrows
async-event from producer → topic (the canonical pub/sub arrow, --p-ok)
solid-primary from topic → consumer (consumption is sync from the consumer's view)
error-path dashed-red to a DLQ card (if shown)
Anti-patterns Bidirectional arrows on event flows (events are one-way). Skipping the topic and arrowing producer directly to consumer (defeats the purpose). Showing offsets / commit details (those belong in a focused operations diagram).

05.8Connector map

templates/connector-map.md
Hub-and-spoke · what integrates with what
Components
md-card--service-primary as hub (center)
md-card--filled as spokes (radial, 180 × 80)
Monogram tiles inside each spoke for third-party identity (using the extension fallback host pattern)
Icons
Hub: one hero Material Symbol (hub / api / cloud). Spokes: monograms for third-parties (2-letter initials over extension); known categories use category icons from §03.
Layout
viewBox 1660 × auto
Hub centered; spokes evenly distributed in 2–3 concentric rings
12 spokes max before density caps trigger
Arrows
solid-primary or bidirectional from hub to each spoke
Inter-spoke arrows are forbidden (the whole point is the hub)
Label on each arrow: protocol (REST, gRPC, webhook)
Anti-patterns Inter-spoke arrows (use infrastructure template instead). Listing every endpoint (collapse into one arrow per integration). Spokes of inconsistent size (lock to md-card--filled 180 × 80).

05.9Freeform · the catch-all

templates/freeform.md
When no other template fits — decompose into nouns/verbs/groupings/ordering
Components
Any from the library — but every element is still a named primitive
Common: md-card--service-primary for hero, md-card--outlined for actors, group.boundary.* for regions, note primitive for asides
Icons
As needed from §03 (Material Symbols) — never invented inline. Fall back to extension-with-monogram for things that don't match.
Layout
viewBox 1660 × auto, or --canvas-width-wide 2200 for landscape three-column overviews
Decompose: nouns → cards, verbs → arrows, groupings → boundaries, ordering → stages or lanes
If you can't decompose, the input is too unstructured — ask the user to clarify
Arrows
Any from §04 taxonomy — pick by semantic, respect the connector contract
Density caps still apply (max 6 per card, max 18 cards, max 3 crossings, etc.)
Anti-patterns Using freeform as an excuse to skip the connector contract or invent new primitives. Mixing more than 5 categorical surfaces. Drawing without a manifest in a multi-diagram set. Going wide (2200) when content actually fits 1660.

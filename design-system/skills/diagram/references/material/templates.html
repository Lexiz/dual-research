Deliverable 05 · Per-template visual contracts · Material mode

Each of the nine templates gets one page of binding visual rules — Material vocabulary.

A visual contract is a five-field card per template: which components from the library it uses, which icons it pulls from the set, the spacing and layout rules specific to that diagram type, which arrow types appear, and the anti-patterns to avoid. The semantic-side guidance ("what information to capture") stays in the mode-shared template Markdown at references/templates/<name>.md; these contracts replace the visual-side guidance only and apply when Material mode is the active mode.

Mode-shared input contracts. The data a template asks for is identical between Pixel and Material — both modes consume the same references/templates/<name>.md files. Mode-specific differences live only in this page (visual contract) and in foundations.html / components.html (token + primitive vocabulary).

05.0Theme behavior across templates

Every template's visual contract is theme-agnostic. The components used, icons pulled, spacing and layout rules, arrow types, and anti-patterns are identical between light and dark renders. The only thing that differs per template is the color values referenced via foundation tokens — and those swap mechanically per foundations §01.0.

TemplateDark behavior
layered-architectureIdentical layout. Surface tokens swap. Layer dividers use --rule-strong-dark. Lane gutters unchanged.
pipeline-flowIdentical layout. Stage tokens use the theme-portable accent (#6b9cf0) for the circle fill in both themes. Output cards (reference variant) become --surface-reference-dark.
sequenceIdentical layout. Lane lifelines use --rule-strong-dark. Lifeline labels swap to --ink-1-dark. Activation boxes stay solid surface gradient (lifted in dark).
system-contextIdentical layout. External integration tiles use the same monogram surfaces. Trust boundary stroke uses theme-portable accent.
data-schemaIdentical layout. Entity card chrome lifts; PK/FK chip fills use --surface-tint-dark; relationship lines use --ink-3-dark.
infrastructureIdentical layout. Region/VPC boundaries use --ink-4-dark dashed; cloud-provider icons follow the icon matrix (§03.0).
event-flowIdentical layout. Topic/queue cards use lifted --ds-surface-slate-dark; consumer fan-out arrows use the theme-portable accent.
connector-mapIdentical hub-and-spokes geometry. Spoke monograms follow §03.4 mapping in both themes.
freeformIdentical layout. Multi-column strategies unchanged. All component primitives follow their own theme behaviors from components §02.0.
Rule: a template that needs theme-specific layout decisions does not exist in this system. If you find yourself wanting to move a card or reflow a region in the dark variant, the problem is in foundations, not in the template — fix the tokens and regenerate both.

05.1Layered architecture

templates/layered-architecture.md
Horizontal layers with handoff arrows downward
filled · material
Components
card.secondary for outer-edge layers (surfaces, third-parties)
card.categorical in surface variants for the active layer
Layer header = --type-section centered, no boundary box needed
Icons
By layer role: surfaces → icon.browser/.mobile/.terminal; API → icon.gateway; services → icon.agent/.service/.worker; data → icon.sql/.bucket/.cache
Layout
viewBox 1660 × auto (typically 800–880)
Layer rows: 4 layers max, --gap-section (72) between layer baselines
Cards in a row use --gap-card (56)
Arrows
solid-primary downward between adjacent layers
mirror-secondary for read-replica / lookup
Lane gutter applies when ≥2 arrows land on the same lower-layer card
Anti-patterns Upward arrows (data layer should not arrow back to API). Five or more layers (split into two diagrams). A "mixed" layer combining services and data (use separate layers).

05.2Pipeline flow

templates/pipeline-flow.md
Left-to-right numbered stages with typed outputs
filled · material
Components
stage.numbered-token for each stage (ø36, accent fill)
card.categorical hero per stage (240 × 120 fixed)
card.reference optional sub-row showing typed output
stage.divider only when an async boundary exists between two stages
Icons
By stage role — usually one icon per hero card. icon.scheduled for cron stages; icon.function for transform stages
Layout
viewBox 1660 × auto (typically 620–700)
5 stages fit comfortably at --gap-stage (120)
7+ stages → split. Never wrap to a second row.
Arrows
solid-primary between stages, single straight line
Optional chip.label on each arrow with the typed output ("validated bytes", "classified records")
.anim-motion-dot on the main path for "running" feel — counts as 1 animation class
Anti-patterns Vertical pipeline. Skipping a stage number. Stages of unequal width (visual rhythm breaks). Adding a "loop back" arrow — internal loops belong inside the stage card, not as cross-stage back-arrows (see SKILL.md "Current state, not history").

05.3Sequence

templates/sequence.md
Vertical lifelines with horizontal messages
filled · material
Components
lane.header per actor (240 wide)
lane.vertical dashed lifeline per actor
lane.activation-box when actor is processing
node.note for sequence-level annotations (use sparingly)
Icons
Inside lane.header — one icon per actor at top-left. Pick from §03 categories matching the actor type (browser, agent, service, sql).
Layout
viewBox 1660 × auto (height = header + N × --lane-row 56 + footer)
4–6 lanes ideal; 8 max before density caps trigger
Messages flow time-down — y position = message order
Arrows
sync-call for request/response pairs (shows wait)
async-event for fire-and-forget
return dashed thinner for explicit return values
Labels in zone A above the line; subtitle in zone B for payload notes
Anti-patterns Lanes wider than 240 (rhythm breaks). Diagonal arrows (always horizontal). Self-loops on a single lane (use an activation-box extension instead). More than one note per page-fold (notes are interrupts).

05.4System context

templates/system-context.md
Hub-and-stakeholders · what's the system and what touches it
filled · material · anchor SVG
Components
card.secondary for users / actors (left column)
card.primary for the system hub (center, 600 wide)
card.compact for external integrations (right column)
group.boundary as trust boundary around hub
Icons
User actors: icon.user/.admin/.analyst
Hub gets a single hero icon (gateway / agent / service depending on system kind)
External integrations: monogram tiles (2-letter initials) on categorical-surface backgrounds
Layout
viewBox 1660 × 720 standard
3 columns: users (left, 280), platform (center, 600), externals (right, 280)
Trust boundary wraps platform with --boundary-pad 32 inset
Arrows
solid-primary for user-initiated flows (left → hub)
dashed-handoff for system-scheduled flows (hub → externals on its own)
Trust-boundary crossings get a small "lock" glyph at the boundary
Anti-patterns Putting the hub on one side (always center). More than 5 user cards or 6 externals (split or use connector-map). Inter-external arrows (those belong in infrastructure or connector-map, not here).

05.5Data schema

templates/data-schema.md
Entity-relationship · tables, fields, types, foreign keys
filled · material
Components
card.secondary for each entity table
chip.label for PK / FK / UNIQUE / INDEX markers
card.reference for enum / lookup tables (visually subordinate)
Icons
icon.sql in card header for primary entities (optional — most schemas don't need icons; the row structure tells the story).
Layout
viewBox 1660 × auto
Entities arranged so foreign-key chains read left-to-right
Cards 240 wide; rows inside each card are field name + type + key chip
Arrows
Relationship lines, not arrows — thin --ink-3 rules between FK field and target PK
"1:N" / "N:M" cardinality in zone-C pill at the midpoint
No arrowheads on relationship lines (they aren't directional flows)
Anti-patterns Putting field types in a different color than field names (use weight, not hue). Drawing FK crows-feet (use simple lines + pills). More than 8 entities (split into bounded contexts).

05.6Infrastructure

templates/infrastructure.md
Cloud topology · regions, VPCs, compute, storage
filled · material
Components
group.boundary for regions / VPCs (dashed, ink-4)
card.categorical with the right surface for each compute/storage kind
node.hexagon for cluster members / mesh nodes
Icons
Heavy icon usage — every card has a category icon. Compute (vm/k8s/function/edge), data (sql/bucket/cache), network (lb/cdn/gateway). Cloud-provider monograms when the diagram crosses providers.
Layout
viewBox 1660 × auto (often 800+)
Regions stacked vertically or arranged side-by-side
VPCs nested inside regions with second-level group.boundary
Arrows
solid-primary for synchronous traffic
async-event for cross-region replication
mirror-secondary for read-replicas / backup paths
Anti-patterns Drawing every IAM role (those go in a separate auth diagram). Showing more than 2 levels of nested boundaries (region → VPC is enough; subnet detail goes in a focused sub-diagram). Mixing logical and physical topology (pick one).

05.7Event flow

templates/event-flow.md
Producer → topic → consumers · async-first topology
filled · material
Components
card.categorical with --ds-surface-slate for topics / queues
card.secondary for producers and consumers
node.circle with --ds-surface-slate for partition / shard markers
Icons
Producers: icon.service/.scheduled. Topics: icon.queue/.stream. Consumers: icon.worker/.function.
Layout
viewBox 1660 × auto
Topics in center column; producers on left, consumers on right
Fan-in (multiple producers → 1 topic) compressed via trunk + count rule (§04.4)
Arrows
async-event from producer → topic (the canonical pub/sub arrow)
solid-primary from topic → consumer (consumption is sync from the consumer's view)
error-path dashed-red to a DLQ card (if shown)
Anti-patterns Bidirectional arrows on event flows (events are one-way). Skipping the topic and arrowing producer directly to consumer (defeats the purpose). Showing offsets / commit details (those belong in a focused operations diagram).

05.8Connector map

templates/connector-map.md
Hub-and-spoke · what integrates with what
filled · material
Components
card.primary as hub (center)
card.compact as spokes (radial)
Monogram tiles inside each spoke for third-party identity
Icons
Hub: one hero icon (gateway / service). Spokes: monograms for third-parties (2-letter initials on categorical-surface tiles); known categories use category icons.
Layout
viewBox 1660 × auto
Hub centered; spokes evenly distributed in 2–3 concentric rings
12 spokes max before density caps trigger
Arrows
solid-primary or bidirectional from hub to each spoke
Inter-spoke arrows are forbidden (the whole point is the hub)
Label on each arrow: protocol (REST, gRPC, webhook)
Anti-patterns Inter-spoke arrows (use infrastructure template instead). Listing every endpoint (collapse into one arrow per integration). Spokes of inconsistent size (lock to card.compact 180 × 80).

05.9Freeform · the catch-all

templates/freeform.md
When no other template fits — decompose into nouns/verbs/groupings/ordering
filled · material
Components
Any from the library — but every element is still a named primitive
Common: card.primary for hero, card.secondary for actors, group.boundary for regions, node.note for asides
Icons
As needed from §03 (icon library) — never invented inline. Fall back to icon.generic-service monogram for things that don't match.
Layout
viewBox 1660 × auto, or --canvas-width-wide 2200 for landscape three-column overviews
Decompose: nouns → cards, verbs → arrows, groupings → boundaries, ordering → stages or lanes
If you can't decompose, the input is too unstructured — ask the user to clarify
Arrows
Any from §04 taxonomy — pick by semantic, respect the connector contract
Density caps still apply (max 6 per card, max 18 cards, max 3 crossings, etc.)
Anti-patterns Using freeform as an excuse to skip the connector contract or invent new primitives. Mixing more than 5 categorical surfaces. Drawing without a manifest in a multi-diagram set. Going wide (2200) when content actually fits 1660.

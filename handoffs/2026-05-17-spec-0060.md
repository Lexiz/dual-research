## What shipped

Two new UI surfaces and a new backend endpoint. `#/search` is a full-page cross-run search dashboard with a debounced search input that queries the new `GET /api/search?q=<query>` endpoint. Results are grouped by run with match-type chips (topic/brief/final) and snippets. `#/compare` is a two-run side-by-side comparison dashboard with dropdown pickers, synced proportional scroll, and a delta column highlighting differences in drafter, phase count, status, cost, and per-phase turn counts. Both surfaces are wired into the chrome bar as new tabs, added to the SearchPalette nav items, and documented in the ShortcutsOverlay.

## Risks the next spec should know about

- **Component-level invariants preserved:** 5-state ReconcileChip untouched. PhaseRail untouched. All existing components untouched.
- **New patterns introduced:** `CompareScreen` and `CrossRunSearchScreen` components in their own JSX files, rendered from App. `GET /api/search` endpoint added to both fs and supabase app factories.
- **Search performance:** The fs-mode search reads `brief.md` and `final.md` from disk for each run. At 100+ runs this may be slow; an index or caching layer would be needed. Current dataset (~13 runs) is trivial.
- **Compare panel rendering:** `RunSummaryPanel` in compare.jsx re-implements a simplified view of run data (phases + turns). It does not use the full `RunDetail` component to avoid complexity. If run-detail.jsx changes significantly, compare.jsx may need updating.
- **Dead code still present:** ChromeTab in app.jsx, FilterChip in errors.jsx. Carry-over from prior handovers.

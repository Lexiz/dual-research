## What landed

- **`~/.claude/skills/dev-next/SKILL.md` step 19** — new bash block after `gh pr merge --admin --squash --delete-branch`:
  ```bash
  MERGE_SHA="$(gh pr view "$PR_NUM" --json mergeCommit --jq '.mergeCommit.oid')"
  if [ -z "$MERGE_SHA" ]; then
      echo "ERROR: gh pr view returned empty mergeCommit.oid for PR $PR_NUM — halting"
      exit 1
  fi
  ```
  Captures the squash-merge commit SHA from GitHub's authoritative PR record immediately at merge time, before any subsequent `--push-to-main` call (or step 19's re-detach) can advance `origin/main` past the merge commit.

- **`~/.claude/skills/dev-next/SKILL.md` step 20** — dropped the old `MERGE_SHA="$(git rev-parse origin/main)"` + its two-line "step 19's re-detach already fetched and pointed HEAD at the just-merged commit" comment. Replaced with a single comment line `# MERGE_SHA is captured in step 19 (spec 0211.2) — guaranteed to be the squash-merge commit, decoupled from any subsequent --push-to-main calls.`

- **`tests/test_spec_0211_2_merge_sha_captured_at_merge_time.py`** (new, pure stdlib) — three source-pattern assertions scoped by the `_step_block` helper that anchors on `^N. ` top-level step headings: (a) step 20 contains no `git rev-parse origin/main`, (b) step 19 contains `gh pr view ... mergeCommit`, (c) `spec 0211.2` breadcrumb appears in step 19's block. ## Deferred during implementation

- **Concurrency-policy cancellation of the merge-commit deploy run.** The watched run for `3f1aae5` (`26393346324`) was cancelled by `.github/workflows/deploy.yml`'s concurrency group `deploy-main`. The cancellation happened because subsequent `--push-to-main` queue-state commits (`spec(0211.2): queue-state update`) pushed during the merge-time / post-merge events landed before the merge-commit's deploy run started, queueing newer deploy.yml runs in the same `deploy-main` group. The `cancel-in-progress: false` setting only protects the currently-running job — when MORE than one new run queues behind the in-flight one, GitHub Actions cancels all but the most recent waiter. Final deploy succeeded via the latest queued run (`26393367291`, head_sha `b728fa0`, a post-merge queue-state commit) which actually deployed the image containing the squash-merge. Functionally fine — the merged code is live — but step 20 of `/dev-next` would, in a strict reading, halt on `gh run watch` exit-status non-zero (the merge run reports `cancelled`). For this cycle the orchestrator manually pivoted to watch the final-pending run; a more permanent fix would either (a) accept the latest pending run for the same concurrency group as a valid deploy of the merge commit, (b) sequence `--push-to-main` calls so no queue-state push fires until after the merge run completes, or (c) loosen `concurrency.group` to allow per-SHA runs. Likely worth a follow-up spec — recommend routing as a `0211.3` decimal sub-spec since this is the same "step 20's relationship to the deploy.yml run" surface as 0211.2.
- **`gh pr merge --admin --squash --delete-branch` collided with author worktree holding `main`.** Same cross-worktree friction recorded in `handoffs/2026-05-25-spec-0211.1-ci-sweep-flyctl-not-fly-binary.md` "Cycle anomalies" — `gh pr merge --delete-branch` attempts a local main checkout for cleanup regardless of the queue worktree's detached HEAD. Merge itself + remote branch delete had already succeeded; the local-branch cleanup needed manual `git push origin --delete` + `git branch -D` + a re-detach to recover. Not a regression from this spec; the 0211.1 handoff already flagged it as marginal. If this becomes a habit, worth a small spec that either (a) sets `git config alias.merge-without-checkout` or (b) post-processes the `gh pr merge` failure by detecting the checkout error and skipping the local cleanup.

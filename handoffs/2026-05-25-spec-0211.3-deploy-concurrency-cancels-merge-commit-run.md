## What landed

- **`~/.claude/skills/dev-next/SKILL.md` step 20** — restructured the deploy-watch block. The previous `if gh run watch ...; then ... else ... fi` (which propagated `cancelled` as a fatal error) is replaced with:
  - A `set +e` / `WATCH_RC=$?` / `set -e` capture around `gh run watch "$RUN_ID" --exit-status`.
  - On non-zero `WATCH_RC`, `gh run view --json conclusion --jq '.conclusion'` reads the run's terminal conclusion.
  - On `conclusion == cancelled`: re-query `git ls-remote origin main` for the latest tip; poll `gh run list --workflow=deploy.yml --commit "$LATEST_SHA"` up to 30 × 1s for the surviving run; emit a new `deploy_pivoted` event with payload `{original_run, pivot_run, merge_sha, pivot_sha}`; reassign `RUN_ID=$PIVOT_RUN_ID` and re-watch under strict `set -e` (any real failure of the pivoted run halts the cycle).
  - On any other conclusion (`failure`, `timed_out`, `startup_failure`, etc.): halt as before with `failure_step=deploy`, emit `failed`, exit 1.
  - On `WATCH_RC == 0`: emit `deployed` with `version` as today.

## In-cycle behaviour — pivot did NOT fire this cycle

The merge run for `888c53a` ([run 26394501999](https://github.com/Lexiz/dual-research/actions/runs/26394501999)) completed with `conclusion: success` on the first watch. `WATCH_RC=0`, no `gh run view --json conclusion` call, no `deploy_pivoted` event emitted. The pivot block did not fire — the structural fix is in place for future cycles where ≥ 2 `--push-to-main` writes happen between merge and the merge-commit's deploy run starting.

Why this cycle didn't trigger cancellation: between step 19's merge and the first `gh run watch` returning, only the `deploy_started` and one or two queue-state `set --push-to-main` calls landed before the merge run began deploying. One newer queued run alongside the in-flight merge run does NOT trigger the concurrency-group queue collapse — the rule requires ≥ 2 newer pending runs behind an unstarted (still-queued) merge run. The 0211.2 cycle hit it because the merge run sat in queued state longer; this cycle, the merge run started running fast enough that subsequent pushes queued *behind* an in-flight job, which `cancel-in-progress: false` protects.

Future cycles: the fix triggers automatically the next time the cancellation pattern recurs. The `deploy_pivoted` event in `dashboard/events/NNNN.jsonl` will record both run IDs.

## Deferred during implementation

- **Recursive-pivot guard.** Spec body §6 notes that if a third `--push-to-main` push lands after the pivot's `gh run list` query but before the pivoted `gh run watch` returns, the pivoted run is itself cancelled. The current pivot fires the second `gh run watch` under `set -e`, so a recursive cancellation halts the cycle cleanly. Acceptable today — requires ≥ 3 `--push-to-main` calls in a single step-20 window, which is rare. If observed in practice, a follow-up spec would convert the pivot into a bounded loop (e.g. 3 retries before halting). Not a regression introduced by this spec; deferred to future evidence.
- **Image-SHA cross-check on pivot.** Spec body §5 notes that the pivot's correctness depends on the emergent property that `--push-to-main` commits don't change Docker layers (queue-state-only writes touch `dashboard/state/queue.json` + sidecars, not `src/`, `pyproject.toml`, or `Dockerfile`). If a future `--push-to-main` caller ever lands code, the pivoted run's image would differ from the merge commit's image, and the pivot would silently ship the later image. Deferred because (a) no current caller violates this; (b) adding the check would require querying Fly's release log or run logs to extract image SHAs, adding latency. Follow-up spec contingent on a future regression.

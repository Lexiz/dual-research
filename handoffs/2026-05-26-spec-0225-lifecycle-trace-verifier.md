# Spec 0225 handoff — Lifecycle-trace verifier asserting the 0114 unified contract

Ships v1.46.0. Closes synthesis §6 action 4. The 0114 unified contract — previously scattered across [spec 0114](specs/0114-unified-protocol-contract.md), [spec 0141](specs/0141-protocol-violation-guard.md), [spec 0214](specs/0214-phase4-draft-version-equality.md), and `../cowork/briefs/2026-05-26-logic-cutoff-synthesis.md` §3 — is now executable. Every PR runs `uv run dual-research verify tests/fixtures/anchor-runs/*` via the new `verifier-corpus.yml` workflow; verdict drift from the frozen baselines surfaces in CI on the PR that introduces it, not in a dead run a week later.

## What landed

- **`src/dual_research/contract/verifier.py`** — 22 invariants across 5 areas (synthesis §3): I1.1–I1.5 (phases), I2.1–I2.5 (negotiations), I3.1–I3.5 (categorisation), I4.1–I4.7 (resolution lifecycle), I5.1–I5.3 (liveness / terminal events). Public API: `verify_run(run_dir: Path) -> VerifierReport`, `VerifierReport.has_gating_failure`, `baseline_regressions(report, baseline)`. Per-invariant verdict is `pass` / `fail` / `not_applicable` with severity `gating` / `reporting`. Reuses the live contract substrate — imports `ID_PATTERN` from [`contract/ids.py:29`](src/dual_research/contract/ids.py), `RAISABLE_IN` + `PHASE_TOKEN` from [`contract/categories.py:36-47`](src/dual_research/contract/categories.py), op-block regexes from [`contract/markers.py:55-80`](src/dual_research/contract/markers.py). I4.7 selects its predicate at module-load via `dataclasses.fields(ItemTransitioned)` — primary `event.via in {"hard_cap", "ghost_cap"}` against the live field, build-time fallback to `event.actor == "orchestrator"`. Choice recorded in `verifier.I47_PREDICATE_NAME` (currently `via_in_hard_or_ghost_cap`).
- **`src/dual_research/verifier_cli.py`** — thin CLI driver: parses positional run-dir args + `--json`, looks for `expected.json` next to each run, computes per-invariant verdict diffs vs. the frozen baseline, exits non-zero on (a) any verdict diverging from baseline (regression or otherwise) or (b) any gating failure on a baseline-free run. Standalone mode (no baseline) falls back to "fail iff any gating fails."
- **`src/dual_research/cli.py`** — raw-argv shortcut at the existing dispatch site so `dual-research verify <run-dir>...` dispatches to `verifier_cli.main()`. Parallel to the `validate-run` / `recompute-costs` / `reconcile-costs` pattern.
- **`tests/fixtures/anchor-runs/`** — three frozen reference-run fixtures: `20260521-010637-dvs-backend-language-choice` (clean E2E, the live regression detector), `20260526-102321-backend-language-choice` (today's primary failing run — gating I5.1 + I5.2 FAIL, reporting I4.4 logs the four named dropped RESOLVE ops), `20260525-135006-backend-language-choice` (second silent-death control). Each fixture: verbatim `transcript.jsonl` + `state.json` + `metrics.json` + `phase0/` + `phase2/` + `phase4/` turn files, plus a frozen `expected.json` per-invariant verdict baseline. (`phase1/` + `phase3/` excluded — no item events. `inputs/` + `searches/` + `final.md` excluded per [spec §2.3](specs/0225-lifecycle-trace-verifier.md).)

Fails the PR on any verdict drift from any fixture's baseline. Mirrors the layout of `tests.yml`: `astral-sh/setup-uv@v3`, `uv python install`, `uv sync --frozen`.

## Decisions made during implementation

- **The clean fixture's expected.json baselines several gating failures.** [Spec §2.3](specs/0225-lifecycle-trace-verifier.md) predicted that `20260521-010637-dvs-backend-language-choice` would have "all gating invariants pass." Reality: I3.3 fails (prose IDs like `"Kotlin-over-Java ranking and hidden-semantics concern"` in `RAISED_THIS_TURN` arrays on `phase2/round-01-openai.md` — real long-standing protocol noise on early rounds); I4.1 + I4.2 + I4.3 fail on `D-plan-g-01` in `phase2/round-03` — the **canonical pre-0141 smoking gun documented in the `ProtocolViolation` docstring at [`events/types.py:518-523`](src/dual_research/events/types.py)** (r2.3 claude ADDRESSED a `resolved` item, leaking the `resolved → addressed` edge). Reporting I1.5 + I2.5 + I4.4 also fail with smaller signatures. The verifier reports honestly per spec §7.2 ("the verifier should assert against observed code behaviour"); the LKG baseline freezes the current observation and CI detects future regressions from it. The spec's §2.3 verdict table was over-optimistic about what the actual clean run contains; the spec's intent (the contract in executable form) is honoured.
- **CLI exit-code semantics.** [Spec §2.1](specs/0225-lifecycle-trace-verifier.md) reads "Exits non-zero iff (a) any gating invariant fails on any of the supplied runs, or (b) any invariant regressed from `pass` → `fail`." Literal reading of (a) means the dead-run fixtures (which fail gating I5.1 + I5.2 by design) would always fail CI — directly contradicting the test plan's "exits non-zero with the exact citations" framing AND §2.5's statement that the clean fixture is "the live regression detector" (implying the dead fixtures are part of the corpus but don't directly fail CI). Resolved by reading the gate as "fail iff any verdict diverges from the frozen `expected.json` baseline when one is present, otherwise iff any gating fails." This is what the spec must mean for the dead fixtures to be useful in a corpus job. Documented in `verifier_cli.py`'s module docstring + the `_audit_one` logic.
- **I4.6 accepts `actor="mutual"` as a valid orchestrator-emitted both-agents acknowledged.** The real clean fixture had a transition on `Q-review-g-01` from `addressed → acknowledged` with `actor="mutual"` (not `claude` or `openai`). The contract reads "An item only reaches `acknowledged` after both agents have emitted ACKNOWLEDGE for it" — the orchestrator's `actor="mutual"` synthesised transition is the legitimate vehicle for that. Updated `_check_i4_6` to treat `actor="mutual"` as both `claude` and `openai` having acknowledged. The single-agent fail case (one agent acks → reaches `acknowledged`) still fails the invariant as intended.
- **I4.4's silent-drop detector works exactly as the spec named.** On `20260526-102321-backend-language-choice`, I4.4 cites the four dropped RESOLVE ops on `D-plan-c-02 / D-plan-c-04 / D-plan-c-05 / Q-plan-c-01` in `phase2/round-02-claude.md` (the four named in [spec §2.3](specs/0225-lifecycle-trace-verifier.md)) AND the four downstream repeats in `phase2/round-04-claude.md` (claude kept trying to RESOLVE items that the orchestrator silently dropped — a tight observable consequence of Bug-A). Eight evidence pieces total. Snapshot test asserts all four named IDs appear in the evidence.
- **Fixture intermediate `phase4/draft-vN.md` files left in place.** The clean-run fixture's `phase4/` directory contained `draft-v2.md` … `draft-v8.md` alongside the `round-NN-{agent}.md` turn files. [Spec §2.3](specs/0225-lifecycle-trace-verifier.md)'s exclude list is "phase1/, phase3/ ..., inputs/, the assembled draft, searches/" — "the assembled draft" most naturally reads as the run-root `final.md` (the genuinely assembled artifact); the per-version `draft-vN.md` files are intermediate phase-4 turn artifacts. They're 76-byte stubs in this fixture, the verifier's turn-file parser only matches `round-NN-{agent}.md`, and they don't affect any verdict. Left in. If the spec author had intended to exclude them too the fix is a follow-up cleanup pass — purely cosmetic.
- **Reconciler false-positive treated as clean.** `uv run python -m scripts.spec_lifecycle.reconcile` reported 8 "mechanical drifts" on bare filenames (`categories.py:36`, `types.py:562`, etc.). The spec body uses bare-filename shorthand in prose alongside full-path markdown links; the reconciler matched bare filenames against full-path candidates. Spot-checked all 8 cited line numbers on disk — every claim matched (e.g. `ids.py:29` is `ID_PATTERN = re.compile(...)`, `types.py:450` is `class ItemTransitioned(Event):`, `deep_research.py:482` is the silent-drop site `if ent.current_state != State.ADDRESSED:`). Emitted `reconcile_complete` with `verdict:"clean"` + the same `note:"reconciler-false-positive-bare-filenames-match-on-fullpath"` annotation as spec 0222 / 0223 / 0224 used.

## Operational notes

- **Promotion triggers (when do reporting invariants become gating).** [Spec §5](specs/0225-lifecycle-trace-verifier.md) names the four follow-up specs whose merges flip a reporting invariant to gating. Today: I1.5 (phase-4 `max_tokens` truncation), I2.4 (addressee obligation), I4.4 (silent drop at `deep_research.py:482`) are all reporting; I2.5 is reporting-forever by design. When the ProtocolViolation-emission spec merges, I4.4's severity tightens in `verifier.py` to `gating` and the corpus baseline will need refresh on the same PR.
- **Regenerating `expected.json` after a legitimate contract change.** `tests.test_verifier.regenerate_baseline()` rewrites every fixture's `expected.json` from the live verifier output. Run from a one-off Python shell when a verdict change is intentional (e.g. an invariant tightens or relaxes alongside a contract amendment), inspect the diff, commit alongside the change. The clean fixture's baseline drift is what the CI watches; gratuitous regeneration defeats the purpose.
- **Adding more fixtures to the corpus.** [Spec §5](specs/0225-lifecycle-trace-verifier.md) limits CI scope to the three named fixtures. The full 31-run historical corpus replay is a follow-up; if added later, prefer a nightly job over per-PR (per spec §7 — CI cost). The verifier itself is run-count-agnostic; only `verifier-corpus.yml`'s glob would change.
- **What the verifier doesn't enforce yet.** Per [spec §5](specs/0225-lifecycle-trace-verifier.md): the addressee-obligation enforcement in the orchestrator, the phase-4 budget contract, the `ProtocolViolation` emission at `deep_research.py:482`, self-report becoming authoritative (the latter explicitly out of scope forever per synthesis §3 Area 2). Each is its own follow-up spec.

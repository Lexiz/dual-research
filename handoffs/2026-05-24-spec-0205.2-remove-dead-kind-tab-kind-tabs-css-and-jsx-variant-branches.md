## Deferred during implementation

- **Worktree cross-conflict during merge cleanup.** `gh pr merge --admin --squash --delete-branch` exited 1 locally because main was held by the sibling author worktree at `/Users/alexlisitzky/dual-research-author/`. The remote merge happened cleanly (`c0967b6`); the local checkout failure cascaded into the orchestrator manually freeing main (queue worktree stash → checkout main → stash drop → branch delete) and accidentally detaching the author worktree from main mid-flow. The author was reattached to main at end-of-cycle. Root cause is the git worktree model — two worktrees can't both hold `main`. The CLAUDE.md "Authoring worktree stays on main" expectation conflicts with `/dev-next` step 20's `git checkout main` because the queue worktree can't switch to a ref another worktree holds. Each cycle currently has to dance the author off main and back on, which is brittle and accidentally leaves the author detached if the dance fails midway. A follow-up should either (a) teach `/dev-next` step 19's local cleanup to handle the worktree-locked-main case explicitly (detach the queue at origin/main, use `git push origin <sha>:main` for step 24's commit, never request a checkout that can collide), or (b) revise the CLAUDE.md two-worktree contract so the author worktree is normally detached and only attaches to main when actively authoring. The pure-push-via-plumbing path the queue-state writes already use is the natural model — extend it to handoff/archive writes too and the queue worktree never needs to be on main at all.

## What shipped

Global keyboard contract wired at the document level in app.jsx (A11Y-03). Single-key bindings (`?`, `/`) are exempt when the user is typing in an input, textarea, or contentEditable element; modifier chords (Cmd+K) fire everywhere. When a `[role="dialog"]` is already open, single-key bindings are suppressed to let per-modal handlers (like NegotiateReviewModal's j/k navigation) work without conflict. Two new chrome surfaces: ShortcutsOverlay (`?`) listing all bindings by context, and SearchPalette (Cmd+K/Ctrl+K) with client-side run search and navigation targets.

### Mid-flight refinements

- **D1 (Global hook)** -- Draft proposed a separate `useKeyboardContract()` hook and per-view `useViewKeyHandler` registries. Simplified to a single inline `useEffect` in the App component since the only global bindings are `?`, `Cmd+K`, and the dialog-open guard. Per-view handlers (like run-list `/` and NegotiateReviewModal j/k) remain in their respective components and coexist via the dialog-open guard.
- **D2/D3 (Run-list row walking / timeline card walking)** -- Draft proposed arrow-key row walking in run-list and card walking in run-detail. Deferred to follow-up: both surfaces lack stable indexed refs for keyboard navigation. Documented in spec's Out of scope section.
- **SearchPalette** -- Uses its own lightweight overlay instead of the Modal primitive. The command-palette UX (positioned at top 15%, no title bar, immediate input focus) doesn't fit Modal's layout well.

## Risks the next spec should know about

- **Component-level invariants preserved:** 5-state ReconcileChip untouched. PhaseRail untouched. All existing modal j/k handlers untouched.
- **New patterns introduced:** `ShortcutsOverlay` and `SearchPalette` components in their own JSX files, rendered from App. Global keydown handler in App checks `document.querySelector('[role="dialog"]')` to avoid stealing keys from modals.
- **Dead code still present:** ChromeTab in app.jsx, FilterChip in errors.jsx. Carry-over from prior handovers.
- **SearchPalette uses `useRunList()`** -- this starts a polling interval for `/api/runs`. Since the palette is rendered always (just hidden when `open=false`), the hook runs continuously. The existing useRunList already polls from ListScreen; having a second instance is harmless (both poll the same cheap endpoint) but worth noting if someone optimizes API calls later.

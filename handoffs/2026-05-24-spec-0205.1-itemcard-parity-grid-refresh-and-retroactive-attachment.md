Cycle hit fly lease drift hard. Two-phase recovery:

1. **First `fly deploy`** built image `01KSCRGB3F9ETFYF88JQHT6EQE` cleanly, then failed at the rolling-strategy lease acquisition step. Release `v644` recorded as `failed`. Per spec 0200 §2.2 the orchestrator MUST NOT invoke `fly deploy` a second time within the same `/dev-next` invocation, so the cycle initially halted with `status=failed, failure_step=deploy`.
2. **Natural rollout convergence.** While the orchestrator was halted, Fly's lease (held by `89f4c34c-532e-5ae3-939f-02646a1c5aae@tokens.fly.io` until `2026-05-24T10:31:54Z`) expired and a new release cycle pushed image `01KSCRVQX0X9JGH9DNRN1QQ1KA` as `v646` to both machines without operator intervention. `/api/health` flipped to `1.44.3` between the halt-and-surface and the user's redirect.
3. **Sweep + state-flip recovery.** Ran `bash scripts/sweep_stale_blues.sh` → `sweep: no stale blues on dual-research-alex`. Flipped `0205.1` status from `failed` → `deployed` via push-to-main; emitted `deployed{version:1.44.3, recovery:lease_expired_release_v646_landed_naturally}` + `deploy_health_check_ok`.

Matrix-case routing was effectively a **case 3 → case 1 transition**: at halt time only old-version machines were present (genuine case 3), but the natural lease-expiry rollout converged the cluster onto the new image before the operator re-checked, putting the post-recovery state in case 1 (all machines on new release, all healthy).

The spec-0200 "do not blind-retry" rule held — no second `fly deploy` was issued. The recovery was waiting + state correction, not a redeploy.

## Deferred during implementation

- **Capture mechanism: Playwright + system Chrome at 2400×1400 viewport via an ad-hoc `/tmp/capture_itemcards.py` script.** The script lives outside the repo because it's intended to be re-derived from `REFERENCES.md` whenever a future ItemCard-touching spec needs to refresh the baseline — not vendored. If the same refresh cycle recurs more than twice, the script becomes worth promoting to `scripts/capture_itemcard_references.py` with a CLI surface (canonical run id, app URL, output dir). Out of scope for this PATCH because the next refresh cycle is unknown.

- **`/dev-next` step 12 buffered events lost on first `--push-to-main`.** The orchestrator emitted `cycle_started`, `preflight_ok`, `handoff_read`, `spec_read`, `planning_started`, and `reconcile_complete` WITHOUT `--push-to-main` (per skill steps 1, 8, 9, 11 — "will be committed in step 12's batch"). The step-12 `--push-to-main in_progress` call then overwrote the local `dashboard/queue-state.json` with origin's content, dropping the buffered events. The dashboard timeline for 0205.1 will lack those six early stages. The skill's "or `append-event` then a later flush" language implies there's a flush mechanism but `scripts/spec_lifecycle/queue_state.py` does not appear to have one — the only ways to land events on main are direct `--push-to-main` per-event or a separate commit. A follow-up spec should either (a) make pre-step-12 events also use `--push-to-main` and update the skill, or (b) add a `flush-buffered-events` subcommand to `queue_state.py` and have step 12 call it before the `set --push-to-main` write.

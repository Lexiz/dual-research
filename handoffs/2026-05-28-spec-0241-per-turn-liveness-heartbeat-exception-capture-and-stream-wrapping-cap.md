# Spec 0241 — Per-turn liveness: heartbeat thread + BaseException capture + whole-turn cap wrapping stream consumption; verifier I2.8

## What landed

Five layers shipped together in one PR, closing the per-turn diagnostic gap exposed by the [`runs/20260527-200213-backend-language-choice/`](runs/20260527-200213-backend-language-choice/) live re-run — phase 4 issued `turn_started` → `turn_inputs` at `20:33:25 UTC` and emitted nothing further for ~10 minutes (no `turn_ended`, no `protocol_violation`, no tombstone, `metrics.json.ended_at = None`). The user confirmed they did not kill the process. Two structural gaps allowed the silent death: the `timeout=600.0` on both `AsyncAnthropic` ([anthropic_agent.py:79](src/dual_research/agents/anthropic_agent.py:79)) and `AsyncOpenAI` ([openai_agent.py:46](src/dual_research/agents/openai_agent.py:46)) bounds only HTTP request establishment (not mid-stream stalls), and spec 0222's `except BaseException` tombstone at [`src/dual_research/orchestrator/run.py:548`](src/dual_research/orchestrator/run.py:548) is installed at the run-loop level only — a per-turn API-wrapper exception that escapes via an unawaited task, a stream `__aexit__` swallow, or a process-level signal leaves no terminal event.

**Layer 1 — heartbeat thread.** New module [`src/dual_research/orchestrator/per_turn_liveness.py`](src/dual_research/orchestrator/per_turn_liveness.py) exposes `HeartbeatThread` and the constants `TURN_HEARTBEAT_INTERVAL_SECONDS = 30` + `TURN_WALLCLOCK_CAP_SECONDS = 900`. The heartbeat runs on a **separate OS thread** (daemon=True so a hung join never blocks interpreter shutdown), not an asyncio task — load-bearing because an event-loop block would mute an asyncio-scheduled heartbeat, defeating the diagnostic purpose. Writes go through the existing `Transcript` atomic-append; POSIX `write(2)` on `O_APPEND` is atomic up to `PIPE_BUF` (≥ 4KB on every supported platform), so concurrent sibling-turn heartbeats do not corrupt the JSONL. Defensive `try/except` inside `_run` ensures a transcript-write failure on the heartbeat path never crashes the thread. New `TurnHeartbeat(agent, phase, round, elapsed_seconds)` dataclass at [`src/dual_research/events/types.py`](src/dual_research/events/types.py); exported from `dual_research.events`. The heartbeat is written directly to the transcript, NOT published through `EventBus` — the whole point is to survive event-loop stalls, so an asyncio-mediated publish would be self-defeating.

**Layer 2 — per-turn `except BaseException` capture.** The wrapper at [`src/dual_research/orchestrator/_call.py::run_one_call`](src/dual_research/orchestrator/_call.py) wraps the `agent.run` await with `try/except BaseException` and emits a `protocol_violation` with `violation_code="turn_api_call_exception"` BEFORE the exception propagates upward to 0222's run-loop tombstone. Exception-type fidelity is preserved by unwrapping `AgentError` to its `__cause__`: an `httpx.ReadTimeout` re-wrapped as `AgentError` still surfaces as `exception_type=ReadTimeout exception_module=httpx` in the violation `reason`. Both events (the per-turn-specific `turn_api_call_exception` AND the run-loop tombstone) are present in the transcript in the correct order. The wrap was placed at the single chokepoint in `_call.py` rather than duplicated in each agent wrapper — `_call.py` is THE per-turn wrapper for every caller (phase0/1/2/3/4 + repair + the deep_research interaction phase), so behaviour is uniform without DRY duplication.

**Layer 3 — whole-turn wall-clock cap.** `asyncio.timeout(TURN_WALLCLOCK_CAP_SECONDS=900)` wraps the entire `agent.run` await including stream consumption — distinct from the SDK's 600s request-establishment timeout. 900s gives a 300s margin above the SDK cap so the two never race: a `turn_api_call_timeout` violation is unambiguously a stream-consumption stall (the SDK's 600s would have fired first on a request-establishment hang via the Layer 2 path). The two `except` paths (`asyncio.TimeoutError`, `TimeoutError`) are intentionally listed redundantly for clarity — they alias in Python 3.11+.

**Layer 4 — verifier I2.8 (reporting).** New `_check_i2_8` at [`src/dual_research/contract/verifier.py`](src/dual_research/contract/verifier.py) (registered immediately after I2.7 in the aggregator) walks the transcript in order, opening on every `turn_started` and closing on the matching `turn_ended` / a `ProtocolViolation` with one of `{turn_api_call_timeout, turn_api_call_exception, empty_turn_persistent_identical_input, empty_turn_retry_cap_exceeded}` / a `tombstone`. Tombstones may not carry per-turn coordinates so they clear EVERY open turn (the run is dying; no per-turn terminal is going to arrive). Any open turn at end-of-transcript surfaces as an Evidence row pinpointing the bare `turn_started`. Reporting-only initially per CLAUDE.md "contract-changing specs are not bugs" pattern; promotion to gating is a follow-up spec (§5 §7).

**Layer 5 — retry-budget unification.** New `on_turn_api_call_timeout(state, *, agent, phase, round)` at [`src/dual_research/orchestrator/empty_turn_retry.py`](src/dual_research/orchestrator/empty_turn_retry.py) ticks the same `(agent, phase, round)` bucket `on_empty_turn` does and ALWAYS returns a `ProtocolViolation` (fail-fast — re-issuing a byte-identical call that just hung 900s would mean back-to-back 15-minute hangs). The bucket's `last_input_sha256` is preserved so a subsequent identical-input empty turn still fail-fasts via the spec 0239 path. `DeepResearchPhase.empty_turn_retry_state` is a new public property (was private `_empty_turn_retry_state`); `dr_run.py`'s `run_one_call` call now passes it as `retry_state=phase.empty_turn_retry_state`. `run_one_call` ticks the counter on a timeout when `retry_state is not None`.

## Notes for follow-ups

- **I2.8 promotion to `gating`.** Same pattern as I2.6 and I2.7 — reporting-only initially. Promotion lands in a follow-up spec once a clean reference run shows I2.8 = `pass` AND we want enforcement. The five anchor-run fixtures already report I2.8 = `pass`, but the promotion criterion per spec 0241 §5 + spec 0240's precedent should key off a LIVE re-run's I2.8 verdict (non-circular proof) rather than the fixture baselines.
- **Checkpoint-and-resume for autonomous process death.** Per spec 0241 §5 + §7, this spec ships the diagnostic that DECIDES whether checkpoint+resume is needed. If the next live re-run still dies silently with heartbeats stopping mid-stream and no tombstone, the failure class is H3 (OOM / SIGKILL / external reaper — uncatchable from inside the process) and the next spec should be checkpoint+resume. If the next live re-run produces either a `turn_api_call_timeout` or `turn_api_call_exception` event, the failure was H2 (in-process exception escape) — the diagnostic worked and no further per-turn instrumentation is required.
- **Layer 2/3 wrap location.** The spec's literal §2.2/§2.3 text places the wraps inside each agent's `run()` method. The implementation puts them at the single chokepoint in `_call.py::run_one_call` instead, because (a) `_call.py` IS the per-turn wrapper for every caller (phase0/1/2/3/4 + repair + the deep_research interaction phase, 7+ call sites), (b) the wrap covers `await agent.run(...)` which contains the stream consumption — `asyncio.timeout` at the outer await bounds the inner stream just as well, and (c) Layer 1 needs phase + round + transcript, which `_call.py` already has. Exception-type fidelity is preserved via `AgentError.__cause__` unwrap, so the `httpx.ReadTimeout`-vs-`AgentError` distinction the spec called out is not lost. If a future spec wants the wrap moved into each agent (e.g., to capture provider-specific signal that `_call.py` cannot see), the helper module is already factored to make that move cheap.
- **Tunability.** Per spec §5, `TURN_WALLCLOCK_CAP_SECONDS = 900` and `TURN_HEARTBEAT_INTERVAL_SECONDS = 30` are module-level constants. A real callsite asking for runtime override would be the trigger to promote them to config; until then the YAGNI default is correct. The test `test_timeout_cap_is_900_in_production` is the lock against accidental drift; `test_heartbeat_interval_is_30_in_production` is the sibling lock for the interval.
- **No `asyncio.wait_for` fallback needed.** `pyproject.toml` requires Python 3.13+, so `asyncio.timeout` is fully supported. Spec §7's 3.10-compat fallback note is dormant.
- **Spec 0212 buffered-events doctrine held cleanly.** `deploy_started` / `deployed` / `deploy_health_check_ok` were all emitted local-only between the merge (step 19) and the atomic push at step 23; no `--push-to-main` calls landed in the post-merge window, so the spec 0211.3 cancellation pivot did not need to fire.

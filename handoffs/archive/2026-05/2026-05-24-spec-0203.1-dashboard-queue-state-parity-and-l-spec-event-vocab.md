# Spec 0203.1 — Dashboard live API + L-spec event vocab parity (v1.43.1)

Two regressions had collapsed the live dashboard for every in-flight spec since 0202 + 0186/0192 shipped without follow-up:

1. **`functions/api/data.js` never learned about `dashboard/queue-state.json`.** After 0202 made it authoritative for cycle-mutable state (status, events, timestamps), the Pages Function kept reading frontmatter + sidecars. Every in-flight spec returned with its queue-time snapshot — frozen at `queued` — and an empty events bucket.
2. **`checkpoint_written` / `resume_started` / `promoted_as_next` were rejected as "unknown" steps.** The Cloudflare build printed `warning: spec NNNN has unknown event steps: [...]` on every render; the L-spec sub-progress payload (`next_subsection`, `completed_subsections`) was dropped on the floor.

Net visible failure: the dashboard at `https://dual-research.pages.dev` showed 0203 frozen on `queued` with zero events for the ~80 minutes it was actually in flight, including the spec-0203 checkpoint cycle (`checkpoint_written` → `resume_started`).

## What landed

### §3.1 — Pages Function reads queue-state.json

[functions/api/data.js](functions/api/data.js) — new `QUEUE_STATE_LAYERED_FIELDS` constant mirrors `_QUEUE_STATE_LAYERED_FIELDS` at [scripts/spec_lifecycle/render_dashboard.py:43-52](scripts/spec_lifecycle/render_dashboard.py). The tree walk appends `dashboard/queue-state.json` to `allBlobs` last; the post-fetch dispatch parses it as JSON into `queueState` (defensive — parse failures fall back to legacy path rather than 502'ing). For each spec row, queue-state's per-spec entry overlays cycle-mutable fields. Events: queue-state's `events` array wins over the legacy sidecar bucket. New top-level `queue_state_updated_at` plumbs the freshness anchor through. Still exactly 2 subrequests per spec 0174 (one REST tree, one GraphQL batch).

### §3.2 — stages.py vocabulary

`TOLERATED_NON_STAGE_STEPS` and `STEP_LABELS` at [scripts/spec_lifecycle/stages.py](scripts/spec_lifecycle/stages.py) gain `checkpoint_written` ("checkpoint"), `resume_started` ("resuming"), `promoted_as_next` ("promoted as next"). `compute_stages` no longer classifies them as unknown.

### §3.3 — Feed icons + kickers + details

[scripts/spec_lifecycle/render_dashboard.py](scripts/spec_lifecycle/render_dashboard.py) — `_FEED_STEP_ICON` gets `bookmark_added` / `replay` / `arrow_upward` (all in the loaded Material Symbols catalogue, no DS extension needed). `_FEED_KICKER` gets matching one-word labels. `_feed_detail` gains three branches: `checkpoint_written → §<next> · <N> done`; `resume_started → resumed at §<sub>` via new `_latest_checkpoint_subsection` helper (reads the most-recent checkpoint, since the `resume_started` event's own payload is empty per [scripts/spec_lifecycle/checkpoint.py:188](scripts/spec_lifecycle/checkpoint.py)); `promoted_as_next → was <prior_id>`.

### §3.4 — L-spec sub-progress chip on in-flight hero

`_render_hero_inflight` injects a chip between "currently · …" and the staleness chip when `spec.status == "in_progress"` AND the spec has a `checkpoint_written` event. Chip text: `§<next> · <N> subsections done`. Carries `data-checkpoint-next` and `data-checkpoint-done` attributes for in-place bootstrap updates without a re-paint.

### §3.5 — Bootstrap JS parity (broader scope than spec assumed)

`DASHBOARD_BOOTSTRAP_JS` — `STEP_LABELS` JS dict gets the three new entries.

**Bootstrap feed parity was broader than the spec body implied.** Spec §3.5 read "Mirror `_feed_detail`'s new branches" as if the bootstrap already had icon/kicker plumbing for existing events. It didn't — the existing `renderFeed` rendered every row with a neutral icon + raw step name, silently degrading the rich server-rendered first paint at the 5s repaint. Achieving spec scenario 3 ("the feed row uses the `bookmark_added` Material Symbol AND kicker text 'checkpoint'") required adding two new mirror dicts (`FEED_STEP_ICON`, `FEED_KICKER`) and a `feedDetail` builder that ports all Python branches, not just the new ones. The bootstrap feed now matches the server feed end-to-end for all event types — fixing the new-event surfacing AND a pre-existing display regression in one change.

`renderHeroInflight` mirrors §3.4's chip-injection branch with the same `data-*` attributes.

## Deferred during implementation

- **`current_queue` reads stale frontmatter — picks wrong queue head post-0202.** `scripts/spec_lifecycle/pick_next_number.py:current_queue` filters specs by `fm.get("status") == "queued"`. Post-0202 frontmatter is frozen at queue time and never re-written, so a spec whose live status (per `dashboard/queue-state.json`) is `deployed` still shows up as `queued` in `current_queue`. Caught live during this cycle: the first `current_queue()` call at /dev-next step 6 returned `0203` as the head even though 0203 was already deployed (true head was `0203.1`). Symptom mirrors §2.1 of this spec — frontmatter and queue-state.json disagree on cycle-mutable status — but the affected surface is the `/dev-next` orchestrator, not the dashboard. The fix is the same shape: `current_queue` should overlay queue-state.status before filtering. Scope was outside spec 0203.1's stated `## 3. Fix` sections (which were dashboard-focused), so logged here rather than expanded inline. File:line: [scripts/spec_lifecycle/pick_next_number.py](scripts/spec_lifecycle/pick_next_number.py) — `current_queue`. Same fix should review every other `pick_next_number.py` helper that filters or reads spec status from frontmatter.
- **Spec body cited the wrong live dashboard URL.** Spec 0203.1 says `https://dr-dashboard.pages.dev` (§3.1 environment, §1 reproduction). The actual live Cloudflare Pages site is `https://dual-research.pages.dev` (cf. spec 0174). `dr-dashboard.pages.dev` exists but serves an unrelated Flutter app. No code impact, but post-deploy verification almost failed because the wrong URL returned HTML instead of JSON. A follow-up should either (a) sweep the dashboard-related specs and align them to the correct URL, or (b) decommission `dr-dashboard.pages.dev` if it's a dead project of the user's. Files to align: [specs/0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md:35](specs/0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md), [specs/0160-dashboard-live-data-via-pages-function.md:29](specs/0160-dashboard-live-data-via-pages-function.md), [specs/0161-js-test-stack-for-pages-function.md:108](specs/0161-js-test-stack-for-pages-function.md).
- **Early-cycle events lost on this run.** `cycle_started`, `preflight_ok`, `handoff_read`, `spec_read`, `planning_started`, and `reconcile_complete` were emitted at the top of this cycle via `append-event` (no `--push-to-main` flag, following the literal example in `/dev-next` step 8). They wrote to the local file. The next `queue_state set --push-to-main` (step 12) pulled fresh state from origin/main and overwrote the local buffered events. The skill text at step 12 says these events "should already have been emitted via `append-event --push-to-main`" — the example commands at steps 8 / 9 / 11 don't include the flag, contradicting that. Outcome: the dashboard timeline for 0203.1 shows zero-duration pre-flight / read-handoff / read-spec stages. Cosmetic for this run; structural for the skill. Fix should patch the example commands in `~/.claude/skills/dev-next/SKILL.md` steps 8–11 to include `--push-to-main`, OR document that `set --push-to-main` does a destructive pull (and add a "flush local events first" step before any `set --push-to-main` call).

# Spec 0240 — Fixture regen machinery + I2.6 verdict flip on the 142625 + 054652 fixtures

## What landed

New module [`tests/_fixture_regen.py`](tests/_fixture_regen.py) exposes two callables. `regenerate_transcript(run_dir)` walks each raisable phase (0, 2, 4) of `run_dir/phase{N}/round-NN-{claude,openai}.md`, replays the turn files through `parse_turn_v2` + `DeepResearchPhase.apply_turn` + `process_round_end` to regenerate the parser-derived event stream (`item_raised` / `item_transitioned` / `closeout_urged` / `closeout_violation` / `protocol_violation` / `empty_turn_detected`), then splices those events back into the captured envelope at each round's last `turn_ended` boundary. The original `transcript.jsonl` is snapshotted to `transcript.captured.jsonl` on the first call (idempotent — never overwrites an existing snapshot, preserving spec 0239's I2.7 captured-transcript evidence). Regenerated parser events carry no `ts` field — replay has no real runtime timestamp; synthesising one would either drift across passes or fabricate a time bracket. The verifier's I5.3 tolerates `ts is None` on non-terminal events, so the regenerated transcripts pass through unchanged. `regenerate_baseline(run_dir)` recomputes `expected.json` from the live verifier output.

Applied the regen to the two named failing fixtures: [`tests/fixtures/anchor-runs/20260527-142625-backend-language-choice/`](tests/fixtures/anchor-runs/20260527-142625-backend-language-choice/) (phase 2 r1 claude now produces 5 `item_raised` events for the previously-dropped slug-shaped IDs; I2.6 flips `fail` → `pass`) and [`tests/fixtures/anchor-runs/20260527-054652-backend-language-choice/`](tests/fixtures/anchor-runs/20260527-054652-backend-language-choice/) (phase 2 r1 claude now produces 6 `item_raised` events; I2.6 flips `fail` → `pass`). The three clean fixtures (010637, 135006, 102321) had their `expected.json` refreshed via `regenerate_baseline` only to backfill the spec 0239 I2.7 invariant entry; their `transcript.jsonl` files were not touched.

Snapshot tests flipped in lock-step at [`tests/test_verifier.py`](tests/test_verifier.py): `test_snapshot_142625_i2_6_slug_drop_fail` → `test_snapshot_142625_i2_6_post_regen_pass`, and the sibling 054652 test. Both now assert `I2.6.verdict == "pass"` against the regenerated baseline. The legacy `regenerate_baseline()` at [`tests/test_verifier.py:1004`](tests/test_verifier.py:1004) is preserved as a thin wrapper delegating to `_fixture_regen.regenerate_baseline` so out-of-tree imports don't break.

New tests at [`tests/test_spec_0240_fixture_regen.py`](tests/test_spec_0240_fixture_regen.py) — 7 tests: post-regen `item_raised` count on 142625 (5) + 054652 (6) plus turn-coordinate assertions; idempotency of `regenerate_baseline` on the 3 clean fixtures (locks the gating-promotion precondition against silent verifier drift — `expected.json` + `transcript.jsonl` byte-equality pre/post); two-pass byte-identical idempotency of `regenerate_transcript` + `regenerate_baseline` on the 2 regenerated fixtures (locks against silent non-determinism in `parse_turn_v2` or `apply_turn` going forward).

## Notes for follow-ups

- **The spec §6 test wording named slug-shaped IDs as the expected `item_raised.id` set.** `apply_turn` assigns canonical IDs via `format_id` (the slug shapes are the agent's `RAISED_THIS_TURN` announcement, not the orchestrator-assigned ledger IDs). Spec 0240 §5 explicitly puts `apply_turn` shape changes out of scope, so the implementation asserts the contract that holds: count = 5 (3 D + 2 Q), turn coordinates (phase=2, round=1, raiser=claude), and that the IDs are canonical (`D-plan-c-{01..03}` + `Q-plan-c-{01..02}`). If a future spec wants the agent's slug IDs to round-trip through `apply_turn` as the ledger ID, that's a new-feature spec on the orchestrator side.
- **I2.6 promotion to `gating` remains a separate follow-up.** Per spec 0240 §5 the promotion spec MUST key its readiness check off the next LIVE re-run's I2.6 = `pass` verdict (non-circular proof), not solely off this spec's regenerated baseline — the regen replays the post-fix parser over the exact case the fix was built for, which is mildly circular. The promotion is a one-line `severity=` change on the `InvariantResult` return at [`src/dual_research/contract/verifier.py:760-763`](src/dual_research/contract/verifier.py) once a live re-run reports I2.6 = `pass`.
- **054652's regenerated baseline shows I1.3 and I2.1 flip `pass` → `fail`.** This is expected behaviour of replaying a dead-state fixture: the regen reveals item-state evolution the orchestrator would have seen had the parser been correct at runtime, but the actual turn files weren't aware of those items, so they never get ADDRESSED and remain `open` at phase exit. The verifier correctly surfaces the inconsistency. Spec 0240 §7 documented this risk class and accepted it for the failing fixtures (the clean-fixture idempotency test is the lock against the same drift slipping into the 3 clean baselines). The promotion-to-gating spec referenced above will not key off these per-fixture regenerated verdicts — it keys off the LIVE re-run's I2.6 verdict.
- **Spec 0212's buffered-events doctrine held cleanly.** `deploy_started` / `deployed` / `deploy_health_check_ok` / `handoff_written` all emitted as local-only events between the merge (step 19) and step 23's atomic push; no `--push-to-main` calls landed in the post-merge window, so the spec 0211.3 cancellation pivot did not need to fire.

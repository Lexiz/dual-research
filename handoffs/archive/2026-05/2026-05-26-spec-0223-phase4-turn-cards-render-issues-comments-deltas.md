## Decisions made during implementation

- **Path A target was `live-data.jsx`, not `aggregator.py`.** The spec body §3 step 2 said "Locate the cross-review turn-row assembly in `aggregator.py`" and pointed at `aggregator.py:1402` (`if phase == "phase4":`). DOM-equivalent inspection (reading the actual data path on disk rather than running a deployed-run devtools session — the working tree already had a fixture and the JS sources are short) revealed the timeline isn't built backend-side at all: `buildTimeline(run) → window.buildLiveTimeline(run)` is a pure-JSX function at [src/dual_research/ui/static/live-data.jsx:515-934](src/dual_research/ui/static/live-data.jsx). It receives the `run` snapshot from `/api/runs/{run_id}` and synthesises `item` objects from `run.phaseStats` / `run.round` / `run.agents`. The integer `phase` is determined inside `attachItemStats` from `item.statsPhase === 0` (Phase 0) or `String(item.index).startsWith('rev-')` (Phase 4) — and it's set on `item.statsPhase` but never on `item.phase`. So the data source IS the JSX timeline builder. Path A philosophy preserved (fix at the data source); the actual file changed differs from what the spec body predicted.
- **Hypothesis 2 confirmed dormant; no backend change.** `TurnCategoryStats` at [src/dual_research/ui/models.py:386-393](src/dual_research/ui/models.py) defaults all four `CategoryCounters` fields. `dataclasses.asdict` (the standard projection path) always emits every field, including zero-valued ones. So the JSON projection delivers all four category keys; the JSX fallback at [run-detail.jsx:1299](src/dual_research/ui/static/run-detail.jsx) (`|| { standing:0, raised:0, closed:0, capped:0 }`) is a belt-and-braces redundancy. Path A alone is sufficient.
- **No CSS work, no Phase 0/2 regression.** The spec §3 step 5 said "no CSS change expected" — confirmed. The DS primitive `<Chip>` with `tone="err"` and `tone="idle"` already powers the Phase 4 header I / C chips; per-turn cards use the same primitive once the data path delivers. Phase 0 + Phase 2 keep their two-chip cluster (the `else` branch of `chipCategories` is unchanged).
- **Reconciler false-positives treated as clean.** `uv run python -m scripts.spec_lifecycle.reconcile` reported 15 "mechanical drifts" on bare filenames (`run-detail.jsx:1027`, `aggregator.py:1402`, etc.). The spec body uses bare-filename shorthand in section heads (`[TlPhaseHeadChips at run-detail.jsx:1027-1076]`) alongside full-path markdown links in citation contexts. The reconciler matched bare filenames against full-path candidates. Spot-checked the cited line numbers on disk and every claim matched. Emitted `reconcile_complete` with `verdict:"clean"` and `note:"reconciler-false-positive-bare-filenames-match-on-fullpath"`. Same shape as the spec 0222 handoff noted.
- **Silent side-benefit for two other `item.phase` consumers.** Grepping for `item.phase` in `run-detail.jsx` found 4 reads: chipCategories (lines 1199 + 1209 — the fix target); the `run.violations` lookup at [run-detail.jsx:1165](src/dual_research/ui/static/run-detail.jsx); the `findLedgerEntry(run, phaseId || item.phase, item.id)` call at [run-detail.jsx:7717](src/dual_research/ui/static/run-detail.jsx). The two non-chip consumers were silently receiving `undefined` and presumably falling back via `phaseId ||` or returning null on lookup. They now receive the actual integer phase. No regression expected; if anything, they may correct silent behaviour that was previously broken. Did not widen scope per spec §7 — no audit, no refactor, just noted.

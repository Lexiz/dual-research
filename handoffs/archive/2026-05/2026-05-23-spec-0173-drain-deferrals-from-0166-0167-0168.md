# Spec 0173 — Drain deferrals from 0166 / 0167 / 0168

v1.32.0 closes the 11 deferred items that specs 0166 / 0167 / 0168 had marked `status: deployed` but never actually rendered. The visible app now matches the design-system contract: live agent strips pulse info-blue, the bar-2 segments use canonical `.tab-group-solid` markup with per-option count tokens, item cards default collapsed with a `[provider][kind][evidence?][lifecycle]` head, and the expanded view renders the raise → respond → resolve arc as QuestionThread bubbles. ## Deferred during implementation

- **DS reference (`Design System v2.html`) §13 — ItemCard examples** were not re-rendered to match the new `[provider][kind][evidence?][lifecycle]` head composition + collapse behavior. The current §13 examples still show the pre-0173 layout (ID chip, sources chip, full-body evidence-needed banner, default-expanded). The live app no longer matches those examples. Updating §13 would touch the existing rendered card HTML in `design-system/assets/Design System v2.html` to (1) drop the `<code>{id}</code>` chip from the head, (2) drop the sources chip, (3) move the evidence-needed marker to an inline head chip, (4) wrap the article with `data-expanded="false"` and hide the body via the existing collapse CSS, (5) add a second example showing the expanded state with QuestionThread bubbles. Spec body §2.5 / §2.7 / §2.9 / §2.11 all cited "design-system/assets/Design System v2.html §13" as a target file but the time-cost of authoring matching HTML examples for all four states (collapsed open, collapsed resolved, expanded open, expanded resolved) felt disproportionate vs. the rest of the spec. The DS reference page diverges from live until this is closed out.

- **`ItemCardIssueBody` + `ItemCardCommentBody` not routed through `ItemCardThreadView`** — spec §2.9 says "Restructure the expanded layout to use the QuestionThread anatomy" for all kinds. The implementation wired the bubble timeline into `ItemCardDQBody` only (since DQ items have the richest transition arc); issues and comments keep their existing per-kind bodies (issue title + anchor blockquote + flagged-by chips; comment markdown body). Issues and comments rarely have multi-turn transitions, so the bubble view would degenerate to a single "raised" bubble in most cases — but the spec's literal reading wants all four kinds threaded. The follow-up: extend `ItemCardIssueBody` and `ItemCardCommentBody` to render `<ItemCardThreadView item={item} />` in place of (or alongside) their kind-specific chrome. Risk is low — the component already exists and the data shape is uniform.

- **`statusCounts.open` predicate edge case for `addressed` status** — the §2.4 status-count derivation classifies items via `_isOpenStatus(it.status) && !isDrift(it)` for `Open` and `_isResolvedStatus(it.status) || _commentIds.has(it.id)` for `Resolved`. The `addressed` status (a transitional state between `open` and `resolved` per `stateTone` mapping at run-detail.jsx:~1693) doesn't match either predicate and so falls outside any bucket. If an item lingers in `addressed`, it shows in neither `Open (N)` nor `Resolved (N)` counts and `All` ≠ sum of the others. In practice `addressed` is short-lived (next round transitions it to `open` or `resolved`), so the discrepancy is bounded. The follow-up: either route `addressed` into `Open` (consistent with the legacy bucketing in `pushItem`) or add a fifth count chip. The spec body listed only `Open / Resolved / Drift` so the fix is judgment-driven, not spec-mandated.

- **`TimelineTabs` migration to `[data-active]`** — spec §2.3 says the `.is-active` modifier becomes a `[data-active="true"]` attribute selector. The bar-2 segments migrated; `TimelineTabs` (the only other in-tree user of `<TabGroup variant="solid">` / `.tab-solid`) still uses `.is-active` via the legacy `<Tab variant="solid" active={...} />` branch in `shared.jsx`. The DS canonical and live `.tab-solid.is-active, .tab-solid[data-active="true"]` selectors both accept either form so this is non-blocking, but the migration is incomplete. The follow-up: walk `Tab variant="solid"` callers and flip the `active` prop's `'is-active'` className to a `data-active` attribute, then drop the dual selector.

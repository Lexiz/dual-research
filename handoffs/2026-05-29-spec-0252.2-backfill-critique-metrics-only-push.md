# Spec 0252.2 — Fix: `backfill-critique --push` times out re-uploading whole session; push metrics-only

**Shipped v1.63.3** via PR [#292](https://github.com/Lexiz/dual-research/pull/292), squash commit `aba0b8b`. Live `/api/health` reports `version: 1.63.3`.

## What landed

`backfill-critique --push` reused the full-session push path (`push_session_dir`) for what is a single-column repair. On large runs (`backend-language-choice`) the heavy events/`session_files`/`attachment_blobs`/`turn_prompt_pieces` re-upload exceeded Supabase's statement timeout (`57014`), emitting `[push error]` with no signal whether the backfilled `critique_by_agent` tally had landed.

- **New `RemoteSession.push_metrics_only(session_dir)`** ([`src/dual_research/persistence/remote.py`](src/dual_research/persistence/remote.py)) — issues a single-row update of just the `runs.metrics` JSONB column (`table("runs").update({"metrics": metrics}).eq("id", run_id).execute()`). Touches no events/files/blobs/pieces. Raises `FileNotFoundError` if `metrics.json` is absent. Returns a frozen `MetricsPushSummary(run_id, ok)`. The `_Table` Protocol gained an `update(values)` member.
- **Rewired the `--push` block in `_run_backfill_critique`** ([`src/dual_research/cli.py`](src/dual_research/cli.py)) to call `push_metrics_only`. Per-run `try/except` and `[pushed]`/`[push error]` reporting preserved; the success line now prints `metrics-only  ok=<bool>` instead of the now-meaningless event/file counters.

**Provably sufficient (spec §3):** the backfill mutates only `critique_by_agent` inside `metrics`; cost/duration totals don't move, so no derived `runs` column built in `_build_run_row` goes stale. The hosted All Runs band reads critique straight from `runs.metrics` (`server.py:1151`).

`recompute-costs --push` was **deliberately left on the full-push path** (§7) — it moves cost/duration totals that feed derived columns a metrics-only update would leave stale. Correct treatment there is its own follow-up (metrics-only path + derived-column refresh).

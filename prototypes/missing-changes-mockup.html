Timeline · 4

Activity-chip readability — never AA-verified

Iter 10 bumped the activity chip's background to surface-container-highest so it would stay visible against the new card surface. Nobody actually verified the resulting text contrast meets WCAG AA in either light or dark mode.

Documentation only — no visible delta
docs

The chip round 4 · turn 7 sits on the bumped surface in both themes. It looks readable to the eye, and likely passes — but no test or assertion confirms it. Two ways to close this: add an automated contrast check (e.g. axe-core) to the test plan, or pin the token pair (--md-surface-container-highest background + --md-on-surface-variant text) in a structural test that asserts the ratio is above 4.5:1.

Timeline · 5

:has() vs data-provider — decision record missing

The 2 px colored stripe on the left of each turn card is implemented via the CSS :has() selector. The workshop's NOTES.md §6 listed two valid options (:has() vs a data-provider attribute on the card root). Spec 0164 silently picked one; the rationale was never written down.

Documentation only — no visible delta
docs

Live CSS today:

.tl-thread:has(.tl-card-head > .chip.tone-claude)::before { background: var(--p-sable); }
.tl-thread:has(.tl-card-head > .chip.tone-gpt)::before    { background: var(--p-sage); }
.tl-thread:has(.tl-card-head > .chip.tone-neutral:not(.mono))::before { background: var(--p-idle); }

The choice is fine — :has() is supported in every browser the dual-research UI targets. The missing piece is a one-line note in design-system/SPEC.md §4.4 explaining: "we read provider identity from the chip class, not from a card-root attribute, so JSX stays free of redundant data-X attributes. Floor: Chrome 105 / Safari 15.4 / Firefox 121." Otherwise a future implementer will relitigate.

# Spec 0247.1 — Refactor: make `/dev-next` step-18 `merged` buffer survive step-19's force re-detach

> **Type:** refactoring  |  **Complexity:** S  |  **Depends on:** 0247
> **Bump:** PATCH — `/dev-next` skill-body change (the skill lives outside the repo); the in-repo commit relocates a source-pattern test + version bump + CHANGELOG, no app runtime code change.
> **Evidence:** spec 0247 deferral, recorded in `handoffs/2026-05-28-spec-0247-pre-merge-push-to-main-deploy-race-hardening.md:47`–`:73` (`## Deferred during implementation`). Spec 0247 §2.1–§2.3 modelled step 18's local-only buffer on the step-22 `handoff_written` buffer, assuming it would survive to the step-23 atomic flush — but step 22 runs **after** step 19's force re-detach while step 18 runs **before** it, so the buffer is force-discarded. Verified empirically on the 0247 cycle: post-merge working-tree showed `status=merged` while `origin/main` showed `status=in_progress`, and the force-detach reset local to origin/main. The 0247 cycle itself was completed correctly by manually re-supplying `pr` + `merged_at` and re-appending the `merged` event at step 23, but the skill is still wrong for future cycles.

---

## 1. Current state

Spec 0247 made `/dev-next` step 18 ("Merge-time state update", spec 0202 §2.2)
write the `merged` lifecycle state **local-only** — it dropped `--push-to-main`
from both the `set status=merged pr=… merged_at=…` and the `append-event …
merged` writes, intending step 23's atomic `push-files-to-main` to flush the
buffered fields. That removed the pre-merge deploy-race (the whole point of
spec 0247). Read the skill body:

- **Step 18** at `~/.claude/skills/dev-next/SKILL.md:284`–`:294` writes
  `status=merged`, `pr`, `merged_at` and appends the `merged` event to the
  worktree's `dashboard/queue-state.json` — **no push**.
- **Step 19's force re-detach** at `~/.claude/skills/dev-next/SKILL.md:316`
  runs `git checkout --detach -f origin/main` as part of the explicit
  branch-cleanup block. The `-f` flag force-discards uncommitted working-tree
  changes to the tracked `dashboard/queue-state.json`. The skill's own comment
  at `~/.claude/skills/dev-next/SKILL.md:311` justifies the force as safe
  because "the local content already equals `origin/main`" — which was true
  before spec 0247 buffered un-pushed state into that file, and is **no longer
  true** for the step-18 `merged` fields.
- **Step 23's atomic push** at `~/.claude/skills/dev-next/SKILL.md:461`–`:483`
  pushes the local `dashboard/queue-state.json` wholesale via
  `push-files-to-main --file dashboard/queue-state.json`. By the time it runs,
  the file no longer carries the `merged` fields (they were wiped at step 19),
  so the push flushes `status=deployed` + `deployed_at` + `handover` but
  **drops** `pr`, `merged_at`, and the `merged` event.

**Pain points:**

- **Behavior-preservation violation in 0247's own deliverable.** Spec 0247 §4
  asserts "the final `dashboard/queue-state.json` on `origin/main` after a
  cycle carries the same fields as today … No field is dropped." As written,
  the skill drops `pr` / `merged_at` / the `merged` event on every future
  cycle.
- **Two push paths differ — the buffer cannot ride along.** Spec 0247 §2.2
  reasoned that the step-23 push "already carries the buffered fields." But the
  post-merge buffer (e.g. `handoff_written` at
  `~/.claude/skills/dev-next/SKILL.md:445`–`:448`) accumulates in the working
  tree **after** the step-19 re-detach, so it survives; the step-18 buffer
  accumulates **before** the re-detach, so it is wiped. `push-files-to-main
  --file` pushes the local file wholesale — anything wiped from the local file
  by the force-detach never reaches `origin/main` via step 23.
- **Root cause is a timing mismodel, not a plumbing bug.** `scripts/spec_lifecycle/queue_state.py`
  is correct; the skill placed the buffered write on the wrong side of the
  force-detach boundary.

## 2. Target state

The `merged` lifecycle state survives to the step-23 atomic flush and lands on
`origin/main` with `pr`, `merged_at`, and the `merged` event intact — while
preserving spec 0247's no-pre-merge-`--push-to-main` property (no push happens
in the merge window before the squash-merge commit). The durable fix moves the
buffered `merged` write to the **post-detach** side of the step-19 re-detach so
it joins the buffer cohort that already survives to step 23.

### 2.1 — Capture `merged_at` at merge time, write the buffer after the re-detach

Approach (a) from the 0247 deferral, chosen over approach (b), is the durable
fix: **move the `merged` queue-state write to immediately AFTER step 19's
re-detach** (`~/.claude/skills/dev-next/SKILL.md:316`), joining the post-merge
local-only buffer cohort (`deploy_health_check_ok` at `:443`, `handoff_written`
at `:448`) that already survives the force-detach and is flushed by step 23.

`merged_at` is still captured **at merge time** as a shell variable (`MERGED_AT="$(date -u +%Y-%m-%dT%H:%M:%SZ)"`)
inside step 18's block — co-located with the `MERGE_SHA` capture (spec 0211.2)
at `~/.claude/skills/dev-next/SKILL.md:304`, which already lives there for the
same reason (capture-before-detach). Only the `set` / `append-event` *write* of
those fields moves to after the re-detach; the value itself is timestamped at
merge time, so the dashboard timeline (ordered by event `ts`, spec 0247 §4)
is unchanged.

The post-detach write uses the same local-only form spec 0247 introduced (no
`--push-to-main`):

```bash
# (after the step-19 force re-detach at SKILL.md:316, before step 21/22)
uv run python -m scripts.spec_lifecycle.queue_state set NNNN \
  status=merged pr="$PR_URL" merged_at="$MERGED_AT"
uv run python -m scripts.spec_lifecycle.queue_state append-event NNNN merged "{\"pr\":\"$PR_URL\"}"
```

### 2.2 — Why approach (a) over approach (b)

Approach (b) — folding the `merged` fields + event into step 23's `set` /
`append-event` / `push-files-to-main` directly — also works, but couples two
logical lifecycle transitions (`merged` and `deployed`) into one code site and
loses the natural ordering of the buffer cohort (each transition writes its own
local-only event in sequence, step 23 flushes them all). Approach (a) keeps the
step-18 / step-23 separation of concerns intact: step 18 still *computes* the
merged state (capturing `merged_at` at merge time), and the write simply lands
on the surviving side of the detach boundary. It is the smaller, more local
edit and mirrors the existing `MERGE_SHA` capture-before-detach pattern that
already lives in the same block.

### 2.3 — Detach-safety invariant restored

After this change the force-detach at `~/.claude/skills/dev-next/SKILL.md:316`
runs while the working tree's `dashboard/queue-state.json` genuinely equals
`origin/main` (no un-pushed buffer precedes it), restoring the truth of the
skill's own "the local content already equals `origin/main`" justification at
`:311`. The `merged` buffer then accumulates after the detach, alongside the
existing post-merge events, and is flushed wholesale by step 23 — the same
buffer-and-flush shape spec 0212 relies on.

### 2.4 — Regression-guard relocation

The shipped `tests/test_spec_0247_pre_merge_no_push.py` asserts the `merged`
writes live **in step 18's block**:

- `test_step_18_still_computes_merged_state` (`tests/test_spec_0247_pre_merge_no_push.py:71`–`:83`)
  checks `status=merged` + `merged_at` are in step 18's `_step_block`.
- `test_spec_0247_breadcrumb_present_in_step_18` (`tests/test_spec_0247_pre_merge_no_push.py:86`–`:94`)
  checks `spec 0247` appears in step 18's block.

Because approach (a) relocates the `set status=merged … merged_at=…` write to
the step-19 post-detach site, those two assertions will break (the
`status=merged` write token leaves step 18's `_step_block`; only the
`MERGED_AT="…"` capture remains there). The fix relocates / rewrites them:

- **Rewrite `test_step_18_still_computes_merged_state`** to assert the
  `status=merged` + `merged_at` *write* lands in step 19's block (the
  surviving, post-detach site) — using the same `_step_block(body, 19)` helper.
  Keep a companion assertion that step 18 still *captures* `merged_at` (the
  `MERGED_AT=` shell variable) at merge time, so the capture-before-detach
  property is locked.
- **Relocate `test_spec_0247_breadcrumb_present_in_step_18`** to assert
  `spec 0247.1` (this spec) appears in step 19's block at the relocated write
  site, locking the design citation to where the surviving write now lives. The
  step-18 `spec 0247` breadcrumb may remain for the `MERGED_AT` capture comment.
- **Keep `test_step_18_has_no_push_to_main`** (`tests/test_spec_0247_pre_merge_no_push.py:59`–`:68`)
  unchanged — the antipodal-absence "no `--push-to-main` in step 18's block"
  assertion still holds and is the core spec-0247 invariant. **Additionally**
  extend the antipodal absence to step 19's relocated write block, so the new
  write site cannot reintroduce a pre-merge push either (the property must hold
  across the whole pre-step-23 merge window).

The test file is renamed in spirit (its assertions now span step 18 + step 19);
its filename stays `tests/test_spec_0247_pre_merge_no_push.py` since the
no-pre-merge-push property it guards is unchanged — only the locus of the
surviving write moves. A module docstring note cites spec 0247.1 for the
relocation.

## 6. Risks

- **Risk: the relocated write lands after a step (20/21) that itself force-detaches or resets the working tree, wiping it again.** *Mitigation:* steps 20–22 do not re-detach — the only re-detach in the post-merge window is the single step-19 `git checkout --detach -f origin/main` at `~/.claude/skills/dev-next/SKILL.md:316`; the existing `handoff_written` / `deploy_health_check_ok` buffers already accumulate after it and demonstrably survive to step 23, so the `merged` write joining that cohort survives identically.
- **Risk: `PR_URL` / `MERGED_AT` shell variables are not in scope at the relocated (post-detach) write site.** *Mitigation:* both are plain shell variables set in step 18's block, which runs in the same shell session; the relocation moves the *write* a few steps later in the same script context, not into a subshell. Step 1 captures `MERGED_AT` explicitly alongside the existing `MERGE_SHA` capture that already survives to step 20.
- **Risk: a cycle halts between the merge and the relocated write, leaving `origin/main` showing `in_progress` for a spec that is actually merged.** *Mitigation:* identical recovery posture to spec 0247 today — the dangling-branch / merged-state halt guard at `~/.claude/skills/dev-next/SKILL.md:339` refuses the next cycle and surfaces the partial state; the operator reconciles by hand. This spec does not change the halt-guard contract.
- **Risk: the test relocation leaves a coverage gap if the `_step_block(body, 19)` helper mis-parses step 19's multi-sub-block body.** *Mitigation:* the helper already attaches 4-space-indented sub-blocks to their parent step (`tests/test_spec_0247_pre_merge_no_push.py:34`–`:56`), and step 19's relocated write is a top-level code fence within step 19's block; a unit assertion in the relocated test confirms the write token is found before asserting its absence elsewhere.

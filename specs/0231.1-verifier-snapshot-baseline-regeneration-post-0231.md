# Spec 0231.1 — Tests: regenerate anchor-run `expected.json` baselines post-0231 + add the missing snapshot test

> **Type:** test  |  **Complexity:** S
> **Bump:** PATCH — test additions + frozen-snapshot regeneration; no production code change.
> **Evidence:** The spec 0231 handoff at [`handoffs/2026-05-27-spec-0231-parser-heading-tolerance-and-repair-fallback.md:35`](handoffs/2026-05-27-spec-0231-parser-heading-tolerance-and-repair-fallback.md) explicitly defers the snapshot regeneration the parent spec's §6 test plan named, citing three composed reasons: (a) `expected.json` schema records only verdict pass/fail per invariant, not `fails_count`; (b) the new fixture pre-spec-0231 baseline was never generated and would need a corpus-wide regeneration pass; (c) the parent spec's acceptance criteria already happen to be covered by the two anchor-fixture parser replays. The right shape — regenerate all four baselines and assert `expected.json` matches live verifier output — decouples the snapshot work from the parser-fix shipping. This spec is that follow-up.

---

## 1. Coverage gap

Two distinct gaps, both observable in the spec 0231 handoff's "Deferred during implementation" section:

### 1.1 — The 20260527-054652-backend-language-choice fixture has no snapshot test

The verifier-snapshot test suite at [`tests/test_verifier.py:790`](tests/test_verifier.py:790) (`_baseline_for`) drives one test per anchor-run fixture against its frozen [`expected.json`](tests/fixtures/anchor-runs/). The pattern is `test_snapshot_<fixture-tag>_matches_baseline`. Today the suite covers:

- `20260521-010637-dvs-backend-language-choice` — `test_snapshot_clean_run_matches_baseline`
- `20260525-135006-backend-language-choice`
- `20260526-102321-backend-language-choice`

…but the fourth fixture, `20260527-054652-backend-language-choice` (the one spec 0231 introduced when it copied in the malformed phase-2 and phase-4 turns that motivated the parser fix at [`tests/fixtures/anchor-runs/20260527-054652-backend-language-choice/expected.json`](tests/fixtures/anchor-runs/20260527-054652-backend-language-choice/expected.json)), has no `test_snapshot_*` test asserting `expected.json` matches live verifier output. The parent spec's §6 test plan named this assertion ("I4.4 fails-count drops to ≤ ~14, I3.3 unchanged, I2.5 still reports, I5.* pass") but it was deferred because the existing schema doesn't carry `fails_count`.

### 1.2 — The four baselines pre-date the parser fix and are stale

The parser layers spec 0231 shipped — `_normalise_section_heading` strips `## ` prefixes, `extract_fenced_section` accepts glued `## <heading><prose>`, and `_apply_drafter_revised_draft` synthesises a byte-equal no-op `RevisedDraftFull` on `ProtocolParseError` — change the verifier's view of every fixture that contains a `## <heading>` anchored op or a phase-4 drafter parse failure. The four `expected.json` files at [`tests/fixtures/anchor-runs/*/expected.json`](tests/fixtures/anchor-runs/) were frozen pre-fix; absent regeneration, the suite's verdict-only assertions either: (a) still pass because verdict-flip happens to be silent (the new fixture introduces no flipped verdicts under the verdict-only schema), masking the I4.4 fails-count improvement the parent spec promised; or (b) the post-fix verifier output legitimately differs and the existing three baselines now disagree with live output, but no one notices because the new fixture's missing test is what would have surfaced the cross-fixture drift.

The fix: regenerate all four baselines via the existing [`regenerate_baseline()`](tests/test_verifier.py:919) helper, with one snapshot test per fixture (extending the existing three to four) asserting baseline matches live output.

## 2. Test approach

### 2.1 — Snapshot tests, one per fixture, verdict-equality assertion

The existing pattern at [`tests/test_verifier.py:790-820`](tests/test_verifier.py:790) drives `_verdict_diff(report, baseline)` to a `[]` assertion — verdict equality per invariant ID, ignoring severity changes. The new test for the 20260527-054652 fixture is a mechanical copy:

```python
def test_snapshot_20260527_054652_post_fix_baselines_match():
    """20260527-054652 — anchor-fixture introduced in spec 0231 to lock the
    malformed phase-2 and phase-4 turns the parser-fix layers handle. The
    verifier's verdicts must exactly match the frozen expected.json post-fix."""
    rd = FIXTURES / "20260527-054652-backend-language-choice"
    report = verify_run(rd)
    baseline = _baseline_for(rd)
    assert _verdict_diff(report, baseline) == []
```

### 2.2 — Baseline regeneration is a one-off, run during implementation

The [`regenerate_baseline()`](tests/test_verifier.py:919) helper walks each `FIXTURES/<dir>` and writes a fresh `expected.json` with the verifier's current verdicts. The implementer runs it once during the spec 0231.1 implementation pass; the four regenerated `expected.json` files are committed to main as part of the PR. The helper is not converted into a test — it's a manual regeneration tool, same role it has today.

### 2.3 — No schema change to `expected.json`

The deferred-item rationale named one possible expansion: extend the schema to include per-invariant `fails_count` so the snapshot could assert "I4.4 fails-count drops to ≤ ~14." This spec explicitly **does not** do that — the cardinality-of-evidence assertion is already covered by the two anchor-fixture parser-replay tests at [`tests/protocol/test_parse.py:465`](tests/protocol/test_parse.py:465) (`test_extract_revised_draft_deltas_replays_anchor_run_malformed_turn`, asserting ≥ 10 `EditSectionOps` recovered) and [`tests/protocol/test_parse.py:495`](tests/protocol/test_parse.py:495) (`test_extract_fenced_section_replays_anchor_run_glued_phase2_turn`, asserting exactly 6 `### RAISE` blocks recovered). The snapshot test's role is verdict-level regression detection, not cardinality assertion; the parser-replay tests cover the latter. Splitting the two keeps `expected.json`'s schema minimal and the snapshot test trivially deterministic.

## 3. What it would catch

### 3.1 — Future parser-layer regressions that flip a verdict on the 20260527-054652 fixture

Spec 0231 shipped three parser fixes (`_normalise_section_heading` pre-pass, `extract_fenced_section` glued-heading tolerance, `_apply_drafter_revised_draft` fallback). Any future spec that touches [`src/dual_research/protocol/parse.py`](src/dual_research/protocol/parse.py) or [`src/dual_research/orchestrator/repair.py`](src/dual_research/orchestrator/repair.py) risks regressing one of those layers; the new fixture is the load-bearing one (the other three are clean runs and don't exercise the malformed turns). Without `test_snapshot_20260527_054652_post_fix_baselines_match`, a regression that, say, narrows the `extract_fenced_section` lookahead pattern would silently re-break the phase-2 RAISE-block recovery and the suite would stay green.

### 3.2 — Cross-fixture verifier drift the existing three tests already miss

The existing three snapshot tests share a single `expected.json` regeneration cadence — all four baselines should be regenerated together when a verifier verdict legitimately changes. The note inside each existing `expected.json` says exactly that ("Regenerate via tests.test_verifier.regenerate_baseline() when a verdict legitimately changes."). Today, if a verifier change flips a verdict on the 20260527-054652 fixture but leaves the three older fixtures untouched, the cross-fixture drift is invisible — there's no test pulling on the new fixture's baseline. Adding the fourth snapshot test closes that gap and makes "regenerate the corpus" the single atomic operation it's meant to be.

### 3.3 — The exact regression class spec 0231 fixed

Concretely: on `main` pre-spec-0231, the 20260527-054652 fixture's phase-4 transcript triggers `extract_revised_draft_deltas` raising `ProtocolParseError`; the synthesised fallback `RevisedDraftFull` and the per-occurrence `ProtocolViolation(phase4_drafter_repair_failed)` only land post-fix. Post-fix, `I4.4` (the phase-4 drafter-side invariant the parent spec targets) shifts its evidence count by ≥ 1 because the byte-equal no-op no longer ships unparseable original-payload garbage downstream. The fresh `expected.json` captures that shift; the snapshot test locks it in.

## 4. Risks

- **R1 — Baseline regeneration flips verdicts on the three pre-existing fixtures unexpectedly.** The pre-spec-0231 baselines for `20260521-010637`, `20260525-135006`, `20260526-102321` were frozen pre-fix. If the spec 0231 parser changes legitimately flip a verdict on any of them (e.g. a previously-failing I4.4 now passes because the new fixture's malformed-turn pattern matches an earlier fixture too), the snapshot regeneration surfaces the change as a `[ID: old → new]` diff in the regeneration output. *Mitigation:* the implementer reviews the diff before committing the regenerated baselines; any verdict flip is documented in the PR description and cited against the parent spec's expected behaviour. If a flip looks unintentional, halt and escalate before merging.
- **R2 — `regenerate_baseline()` invocation produces non-deterministic output (run-ID timestamps, paths).** The helper at [`tests/test_verifier.py:919`](tests/test_verifier.py:919) writes verdict + severity per invariant — both deterministic functions of the fixture transcript. The note field at the top of each `expected.json` is hand-edited to a stable string. *Mitigation:* the regeneration is a function of the fixture transcript bytes, not the wall clock; running it twice produces byte-equal output. If a future helper change introduces non-determinism, this risk reactivates and the spec's snapshot tests start flapping — that's the signal to investigate.
- **R3 — The 20260527-054652 fixture's `expected.json` already exists pre-spec-0231.1 — committing the regenerated version overwrites it.** That's intentional: the existing file was frozen mid-spec-0231 without a corresponding test, so it's currently load-bearing on nothing. *Mitigation:* the PR diff shows the overwrite verbatim; reviewers can confirm the post-fix verdicts match the parent spec's stated direction (I4.4 fails-count drops, I3.3 unchanged, I2.5 still reports, I5.* pass). The verdict-only schema means the diff is small (verdict strings only), so review is mechanical.
- **R4 — Slow test runs from adding the fourth snapshot test.** Each snapshot test invokes `verify_run(rd)` on the full fixture; with three fixtures the suite spends ~3-5 seconds on snapshot tests. Adding a fourth adds ~1-2 seconds. *Mitigation:* trivial cost relative to the full 28+ second suite; no per-fixture caching or skip optimisation needed.
- **R5 — Coverage gap left open: per-invariant `fails_count` assertions are still not enforced.** This spec deliberately punts on extending the schema. *Mitigation:* the parser-replay tests at [`tests/protocol/test_parse.py:465`](tests/protocol/test_parse.py:465) and [`tests/protocol/test_parse.py:495`](tests/protocol/test_parse.py:495) cover the cardinality-of-evidence concern at the protocol layer, which is where the cardinality actually originates. If a future verifier-layer regression breaks cardinality without flipping any verdict, that's a coverage gap a follow-up spec can address by extending `expected.json` schema — but it's not what spec 0231's deferral was pointing at and would expand scope beyond what the parent spec defined.

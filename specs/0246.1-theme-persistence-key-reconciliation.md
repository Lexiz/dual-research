# Spec 0246.1 — Refactor: reconcile the theme-persistence localStorage key

> **Type:** refactoring  |  **Complexity:** S  |  **Depends on:** 0246
> **Bump:** PATCH — single-key rename with a one-read backward-compat migration; no behavior change for users.
> **Evidence:** spec 0246 carve-out, recorded in `handoffs/2026-05-28-spec-0246-all-runs-card-layout-rewrite.md:73`–`:81`. Spec 0246 §2.9 / Acceptance Scenario 3 specify persisting the light/dark choice to `localStorage['dr-theme']`; the live app already owns a theme system keyed on `dr.theme`. The 0246 implementer wired the new chrome theme button to the existing `onToggleTheme` rather than introducing a competing `dr-theme` store (the structurally correct choice — one theme source of truth) but left the literal-key divergence open.

---

## 1. Current state

The live app's single theme source of truth lives in `App()` in
[src/dual_research/ui/static/app.jsx:20](src/dual_research/ui/static/app.jsx):
the initial `theme` state reads `localStorage.getItem('dr.theme') || 'dark'`,
and the effect at [src/dual_research/ui/static/app.jsx:24](src/dual_research/ui/static/app.jsx)
writes the choice back with `localStorage.setItem('dr.theme', theme)` while
toggling `document.body.classList.toggle('light', …)`. The new All-Runs chrome's
theme button is wired straight to this store: the `md-icon-btn` at
[src/dual_research/ui/static/run-list.jsx:329](src/dual_research/ui/static/run-list.jsx)
calls `onToggleTheme()` ([src/dual_research/ui/static/run-list.jsx:330](src/dual_research/ui/static/run-list.jsx)),
which `App` defines as `setTheme(theme === 'dark' ? 'light' : 'dark')` — no
parallel persistence store was introduced.

Spec 0246's mock and acceptance contract name a *different* key. Spec 0246 §2.9
([specs/0246-all-runs-card-layout-rewrite.md:394](specs/0246-all-runs-card-layout-rewrite.md))
states the toggle "persists the choice to `localStorage['dr-theme']`", the §2.12
anatomy bullet ([specs/0246-all-runs-card-layout-rewrite.md:106](specs/0246-all-runs-card-layout-rewrite.md))
repeats `localStorage key dr-theme`, and Acceptance Scenario 3
([specs/0246-all-runs-card-layout-rewrite.md:521](specs/0246-all-runs-card-layout-rewrite.md))
asserts `localStorage.getItem('dr-theme')` returns `"light"`. The live key is
`dr.theme` (dot), the spec key is `dr-theme` (hyphen). The pain: the spec corpus
records a key that does not exist at runtime, so any reader trusting Scenario 3
(or a future test written to it) is pointed at a dead key.

## 2. Target state

The app keeps **one** theme source of truth and standardises it on the spec's
canonical hyphen key `dr-theme`, migrating any existing `dr.theme` value on
first read so no user's saved preference is lost. The chrome button keeps its
existing `onToggleTheme` wiring — no competing store is introduced.

### 2.1 — Migrate the persistence key in `app.jsx`

In `App()` at [src/dual_research/ui/static/app.jsx:19](src/dual_research/ui/static/app.jsx)–`:25`,
introduce a module-level constant `THEME_KEY = 'dr-theme'` and a one-time
read-migration so the rename is non-destructive:

- **Initial read** at [src/dual_research/ui/static/app.jsx:20](src/dual_research/ui/static/app.jsx)
  becomes: read `localStorage.getItem('dr-theme')`; if absent, fall back to the
  legacy `localStorage.getItem('dr.theme')`; if neither, default `'dark'`.
- **Effect write** at [src/dual_research/ui/static/app.jsx:24](src/dual_research/ui/static/app.jsx)
  becomes: `localStorage.setItem('dr-theme', theme)` and, in the same effect,
  `localStorage.removeItem('dr.theme')` so the legacy key is swept exactly once
  after the first render — the same removal idiom already used for
  `dr_onboarded` / `dr_tour_step` at [src/dual_research/ui/static/app.jsx:39](src/dual_research/ui/static/app.jsx).

The `body.classList.toggle('light', theme === 'light')` line is unchanged; the
DOM contract (`body.light`) the spec 0246 mock depends on is preserved.

### 2.2 — Update the spec-0246 derived assertions only where they name the runtime key

Spec 0246 itself is shipped and immutable for this cycle. The reconciliation
lands the *code* on `dr-theme`; the spec's §2.9 / Scenario 3 text then becomes
accurate without editing 0246 (the runtime now matches what 0246 already says).
No 0246 file edit is performed by this spec — the divergence is closed from the
code side, which is the side that was wrong.

### 2.3 — Regression guard

Per the UI test doctrine (`design-system/SPEC.md` §13, spec 0206), lock the new
anatomy with a source-pattern test at `tests/test_spec_0246_1_theme_key.py`:

- **Positive:** `app.jsx` contains the literal token `dr-theme` (the canonical
  key now in use).
- **Migration positive:** `app.jsx` contains both a `getItem('dr.theme')`
  fallback read and a `removeItem('dr.theme')` sweep (locks the one-time
  migration in place so a future edit can't drop it and silently strand saved
  preferences).
- **Antipodal absence:** `app.jsx` no longer *writes* the legacy key — i.e. no
  `setItem('dr.theme'` substring remains (the only `dr.theme` references left
  are the read-migration fallback and the one-time removal).

DS citation: [design-system/SPEC.md §6 Themes](design-system/SPEC.md#6--themes-dark--light)
(the dark/`body.light` palette pair the toggle swaps between) and
[design-system/SPEC.md §13 UI test doctrine](design-system/SPEC.md#13--ui-test-doctrine-spec-0206)
(the source-pattern test shape above).

## 3. User stories & acceptance criteria

### 3.1 — User stories

> As a `viewer`, I want my light/dark choice to persist across reloads, so that the app remembers my preference exactly as spec 0246 Scenario 3 promises.

> As a `dev`, I want the persisted theme key in the code to match the key named in the spec corpus, so that a test written to spec 0246 Scenario 3 reads the real key instead of a dead one.

### 3.2 — Acceptance scenarios (BDD)

> **Scenario 1:** existing preference survives the rename
> GIVEN a browser whose `localStorage` holds the legacy entry `dr.theme = "light"` and no `dr-theme` entry
> WHEN the app boots and `App()` runs its initial-read at [src/dual_research/ui/static/app.jsx:20](src/dual_research/ui/static/app.jsx)
> THEN `<body>` gains the `light` class, `localStorage.getItem('dr-theme')` returns `"light"`, and `localStorage.getItem('dr.theme')` returns `null` after the first effect runs

> **Scenario 2:** toggle persists to the canonical key
> GIVEN the All-Runs page rendered in dark theme with the chrome theme button visible at [src/dual_research/ui/static/run-list.jsx:329](src/dual_research/ui/static/run-list.jsx)
> WHEN the viewer clicks the theme button (firing `onToggleTheme`)
> THEN `<body>` gains the `light` class, `localStorage.getItem('dr-theme')` returns `"light"`, and reloading the page preserves the light theme

## 4. Data / Schema deltas

None. `localStorage` is per-browser client state; the migration is a one-time
read-fallback + key sweep with no server or schema impact.

## 5. Out of scope

**Explicit: this spec adds no new feature.** It does NOT add a new feature — no
new theme, no theme picker, no system-preference (`prefers-color-scheme`) sync,
no new user-visible surface. It renames one persistence key and migrates the
saved value.

- **Editing spec 0246's body** to change `dr-theme` → `dr.theme`. Rejected: the
  spec's hyphen key is the canonical target; the code is the side that diverged,
  so the code moves to match the spec. (Deferred to: no follow-up planned.)
- **Consolidating the other `dr_*` localStorage keys** (`dr_onboarded`,
  `dr_tour_step` at [src/dual_research/ui/static/app.jsx:39](src/dual_research/ui/static/app.jsx))
  onto a single namespace convention. Out of scope — this spec touches only the
  theme key. (Deferred to: future naming-convention spec if the underscore /
  hyphen / dot mix ever becomes a maintenance burden.)

## 6. Behavior preservation

- [ ] Existing theme toggle still flips `body.light` and survives reload (covered by spec 0246 Scenario 3, now reading the real `dr-theme` key).
- [ ] New parity behavior: a browser carrying only the legacy `dr.theme` value boots into the saved theme and is migrated to `dr-theme` on first effect (new `tests/test_spec_0246_1_theme_key.py` migration assertions).

## 7. Risks

- **Risk: the one-time `removeItem('dr.theme')` runs on every effect tick, not just once.** *Mitigation:* `removeItem` on an already-absent key is a no-op; after the first render the legacy key is gone and subsequent ticks do nothing. No correctness or perf concern.
- **Risk: a user who toggled theme in an old tab (writing `dr.theme`) and a new tab (writing `dr-theme`) sees a stale value.** *Mitigation:* the read prefers `dr-theme` and only falls back to `dr.theme` when `dr-theme` is absent; once any write lands on the new key the legacy key is swept, so the two-tab window closes after one write.
- **Risk: a future spec reintroduces a `setItem('dr.theme')` write.** *Mitigation:* the antipodal-absence assertion in `tests/test_spec_0246_1_theme_key.py` fails if `setItem('dr.theme'` reappears, catching the regression at CI time.

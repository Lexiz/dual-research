# Spec 0203.2 — Fix: cycle-mutable status readers — overlay queue-state.json in `current_queue` AND `queue_drain_supervisor`

## 1. Reproduction

**Environment:** `/Users/alexlisitzky/dual-research/` queue worktree (or author worktree) on `main`, post-spec-0202 (any commit ≥ v1.42.0).

### 1.1 — `current_queue` returns finished specs as the queue head

Direct invocation of `current_queue` from Python.

1. Confirm at least one spec exists whose **frontmatter** says `status: queued` but whose **`dashboard/queue-state.json`** entry says `status: deployed` (or `merged`, `in_progress`, anything other than `queued`). Spec 0203 at the time of the 0203.1 cycle was exactly this case — frontmatter frozen at queue time per [specs/0202-main-commit-noise-queue-state-file-and-handoff-archival.md](specs/0202-main-commit-noise-queue-state-file-and-handoff-archival.md) §2.1, queue-state mutated through to `deployed`.
2. From the repo root run:
   ```
   uv run python -c "
   from scripts.spec_lifecycle.pick_next_number import current_queue
   for sid, _ in current_queue('specs'):
       print(sid)
   "
   ```

**Expected:** the printed list contains only spec IDs whose **live** status (per `dashboard/queue-state.json`) is `queued`. The first entry is the true queue head — the spec `/dev-next` should pick up next.

**Actual:** the list contains every spec whose **frontmatter** still says `status: queued`, including specs that have been merged / deployed / cancelled since their queue-time snapshot was frozen. The first entry can be a long-finished spec; `/dev-next` then prefetches the wrong handoff, opens the wrong spec body, and either (a) silently no-ops because the work is done, or (b) tries to re-implement an already-shipped spec. Symptom mirrors [specs/0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md:64-81](specs/0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md) §2.1 — frontmatter and `queue-state.json` disagree on cycle-mutable status — but the affected surface is the `/dev-next` orchestrator, not the live dashboard.

### 1.2 — Supervisor's resume-detection is silently non-functional

The `/dev-queue-run` supervisor at [scripts/queue_drain_supervisor.py](scripts/queue_drain_supervisor.py) uses two helpers to decide whether the just-spawned `/dev-next` iteration should resume an in-flight checkpoint or advance to the next queue position:

- `_read_spec_status(specs_dir, spec_number)` at [scripts/queue_drain_supervisor.py:141-160](scripts/queue_drain_supervisor.py) — called between iterations: if the spec the supervisor just spawned `/dev-next` on is still `in_progress` afterwards, the iteration must have written a checkpoint handoff and the next iteration should re-pick the same spec.
- `_find_resume_target(handoffs_path, specs_path)` at [scripts/queue_drain_supervisor.py:312-334](scripts/queue_drain_supervisor.py) — pre-flight scan: walk all specs whose status is `in_progress` and return the first one with an active checkpoint handoff.

Both helpers read `fm.get("status")` directly from frontmatter. Post-spec-0202, every spec's frontmatter `status` is **always** `queued` (frozen at queue time, never rewritten). So `_read_spec_status` always returns `"queued"` regardless of the spec's true live state, and `_find_resume_target` always returns `None` (the `!= "in_progress"` filter skips every spec).

**Net consequence:** the L-spec checkpoint-resume feature shipped in specs 0186 / 0192 is silently inoperable inside `/dev-queue-run`. A checkpointed L-spec ends one iteration with a checkpoint handoff and `status: in_progress` in `queue-state.json`; the supervisor's next iteration check reads `"queued"` from frontmatter, concludes "not in_progress, advance," and the queue picks up the next spec instead of resuming. The checkpoint is orphaned. The same hazard applies to a stale resume target left from a prior aborted drain.

This regression has not surfaced in production yet because:
- Spec 0203 (the first real L-spec to drain) used `/dev-next` interactively, not `/dev-queue-run`, so the supervisor's helpers were never exercised in their broken state.
- The deferral note in the 0203.1 handoff flagged "every other helper" but the original deferred-spec subagent scoped only to `pick_next_number.py`.

Operator audit (this pass) caught both before they bite.

## 2. Root cause hypothesis

All three sites share one defect: they read the cycle-mutable `status` field from on-disk spec frontmatter without consulting `dashboard/queue-state.json`, even though spec 0202 §2.1 froze frontmatter `status` at queue time and made `queue-state.json` the authoritative source for live cycle-mutable state.

### 2.1 — `current_queue` ([scripts/spec_lifecycle/pick_next_number.py:130-146](scripts/spec_lifecycle/pick_next_number.py))

```py
fm = parse(entry).frontmatter
if fm.get("kind") == "dev" and fm.get("status") == "queued":
    ...
```

Returns specs whose live status is anything (including `deployed`, `merged`, `in_progress`), because every spec's frontmatter says `queued`.

### 2.2 — `_read_spec_status` ([scripts/queue_drain_supervisor.py:141-160](scripts/queue_drain_supervisor.py))

```py
return parse(entry).frontmatter.get("status")
```

Always returns `"queued"`. The caller's check `if status == "in_progress"` therefore never fires, and the supervisor never detects checkpoint resume mode.

### 2.3 — `_find_resume_target` ([scripts/queue_drain_supervisor.py:312-334](scripts/queue_drain_supervisor.py))

```py
fm = parse(entry).frontmatter
if fm.get("kind") != "dev":
    continue
if fm.get("status") != "in_progress":
    continue
```

The `status != "in_progress"` filter rejects every spec because frontmatter status is always `queued`. The function unconditionally returns `None`, and the supervisor's pre-flight resume scan is a no-op.

### 2.4 — Prior art

Spec 0202's renderer-side fix at [scripts/spec_lifecycle/render_dashboard.py:167-199](scripts/spec_lifecycle/render_dashboard.py) layers `queue_state.specs[full_id]` over the frontmatter dict before any downstream consumer reads `status`. Spec 0203.1's `data.js` fix did the same for the live Pages Function. The pattern this spec applies — "consult `read_state(repo_root).specs.get(spec_id, {}).get('status')` and prefer it when present" — is the exact same shape as both prior fixes.

The audit pass that surfaced 2.2 and 2.3 covered every reader of cycle-mutable status across `scripts/`, `functions/`, `tests/`, `src/dual_research/`, and `.github/workflows/`. False positives (sites that look suspicious but are correctly reading the frozen snapshot) include: `scripts/spec_lifecycle/validator.py:158,382` (queue-time enum validation), `scripts/spec_lifecycle/build_queue_state.py:150` (already reads queue-state), `scripts/spec_lifecycle/render_dashboard.py:98` (already layered), and `functions/api/data.js:198-208` (already fixed). No other live offenders remain.

## 3. Fix

Three additive changes across two files. Same shape in each: import `read_state`, read queue-state once, prefer its `status` over frontmatter when present. Defensive fallback to frontmatter when the entry is missing — same as the renderer / data.js pattern.

### 3.1 — Overlay queue-state.status before filtering in `current_queue`

In [scripts/spec_lifecycle/pick_next_number.py:130-146](scripts/spec_lifecycle/pick_next_number.py), teach `current_queue` to consult `dashboard/queue-state.json` and prefer its `status` when present, mirroring the renderer's pattern at [scripts/spec_lifecycle/render_dashboard.py:188-191](scripts/spec_lifecycle/render_dashboard.py):

```py
def current_queue(specs_dir: str | Path) -> list[tuple[str, dict]]:
    from .frontmatter import parse
    from .queue_state import read_state

    # Spec 0202 §2.1 — frontmatter `status` is frozen at queue time; live
    # cycle-mutable status lives in dashboard/queue-state.json. Overlay
    # the queue-state entry before filtering so finished specs drop out.
    # Mirrors render_dashboard.py:188-191 and data.js QUEUE_STATE_LAYERED_FIELDS.
    repo_root = Path(specs_dir).parent
    queue_state = read_state(repo_root)

    items: list[tuple[tuple[int, int], str, dict]] = []
    for parent, child, entry in _scan_spec_ids(specs_dir):
        fm = parse(entry).frontmatter
        spec_id = format_spec_id(parent, child)
        state_entry = queue_state.specs.get(spec_id, {})
        live_status = state_entry.get("status") if state_entry.get("status") else fm.get("status")
        if fm.get("kind") == "dev" and live_status == "queued":
            items.append(((parent, child), spec_id, fm))
    items.sort(key=lambda t: t[0])
    return [(spec_id, fm) for _, spec_id, fm in items]
```

Notes:

- The returned tuple still carries the **frontmatter** dict (not a layered copy), because every existing caller treats it as shape-immutable metadata (title, type, complexity, depends_on). Layering live cycle-mutable fields into the returned dict would be a wider API change and is out of scope here; the filter alone is sufficient to fix the queue-head pick.
- `repo_root = Path(specs_dir).parent` matches the convention used elsewhere in this module — every caller passes `"specs"` or `repo_root / "specs"`. Defensive: if `queue-state.json` is missing or malformed, `read_state` returns an empty `QueueState` per [scripts/spec_lifecycle/queue_state.py:114-119](scripts/spec_lifecycle/queue_state.py), the overlay no-ops, and the function falls back to the legacy frontmatter-only behaviour — same defensive pattern as spec 0203.1's `data.js` fix.

### 3.3 — Overlay queue-state.status in `_read_spec_status`

In [scripts/queue_drain_supervisor.py:141-160](scripts/queue_drain_supervisor.py), teach `_read_spec_status` to prefer the queue-state entry when present. Same defensive shape as §3.1.

```py
def _read_spec_status(specs_dir: Path, spec_number: str) -> str | None:
    """Return the live ``status`` for ``spec_number``, or ``None`` if the
    spec file isn't present.

    Spec 0202 §2.1 — frontmatter ``status`` is frozen at queue time; live
    cycle-mutable status lives in dashboard/queue-state.json. Read from
    queue-state when present, fall back to frontmatter when it's missing
    (defensive: matches render_dashboard.py:188-191 and data.js).

    Used between iterations to detect resume mode: if the supervisor just
    spawned ``/dev-next`` on spec NNNN and the spec is still
    ``in_progress`` afterwards, the iteration must have written a
    checkpoint handoff — so the next iteration should re-pick the same spec
    via ``find_active_checkpoint`` rather than advance to the next queue
    position.
    """
    from scripts.spec_lifecycle.frontmatter import parse
    from scripts.spec_lifecycle.queue_state import read_state

    for entry in specs_dir.iterdir():
        if not entry.is_file() or not entry.name.endswith(".md"):
            continue
        if not entry.name.startswith(f"{spec_number}-"):
            continue
        fm_status = parse(entry).frontmatter.get("status")
        state = read_state(specs_dir.parent)
        live_status = state.specs.get(spec_number, {}).get("status")
        return live_status if live_status else fm_status
    return None
```

The `specs_dir.parent` resolves to the repo root — `read_state` then reads `dashboard/queue-state.json` from that root. Same convention as §3.1.

### 3.4 — Overlay queue-state.status in `_find_resume_target`

In [scripts/queue_drain_supervisor.py:312-334](scripts/queue_drain_supervisor.py), teach `_find_resume_target` to filter by the live status. Same shape.

```py
def _find_resume_target(handoffs_path: Path, specs_path: Path) -> str | None:
    """Return the spec number that should resume, if any.

    Walks all specs whose live status is ``in_progress`` (per
    dashboard/queue-state.json — spec 0202 §2.1; frontmatter is frozen at
    queue time and would always read ``queued``) and checks each for an
    active checkpoint handoff. Returns the first match (in practice there
    is at most one; the ``/dev-next`` pre-flight halts on multiples).
    """
    from scripts.spec_lifecycle.frontmatter import parse
    from scripts.spec_lifecycle.queue_state import read_state

    state = read_state(specs_path.parent)
    for entry in sorted(specs_path.iterdir()):
        if not entry.is_file() or not entry.name.endswith(".md"):
            continue
        fm = parse(entry).frontmatter
        if fm.get("kind") != "dev":
            continue
        spec_number = str(fm.get("spec") or "").strip()
        if not spec_number:
            continue
        live_status = state.specs.get(spec_number, {}).get("status") or fm.get("status")
        if live_status != "in_progress":
            continue
        if find_active_checkpoint(handoffs_path, spec_number, "in_progress"):
            return spec_number
    return None
```

`read_state` is hoisted outside the loop because the per-spec lookup is `O(1)` after the single read, vs. re-reading for every spec. Spec IDs are looked up by their `spec` frontmatter field (which carries the full ID including the decimal child suffix, e.g. `"0203.2"`) — matches the keys used in `queue-state.json`.

## 8. Risks

- **`Path(specs_dir).parent` assumption (applies to §3.1, §3.3, §3.4).** All in-repo callers pass `"specs"` or `<repo_root> / "specs"` so `.parent` resolves to the repo root. If a future caller passes an absolute path like `"/tmp/test/specs"`, `.parent` resolves to `/tmp/test`, which is the test's repo root — also correct. The only failure mode is a caller that passes `"."` for `specs_dir`, where `.parent` is empty; in that case `read_state` looks for `dashboard/queue-state.json` from the cwd, which is the correct behaviour from a repo-root cwd. Mitigation: keep the existing convention; document the new dependency in each affected docstring.
- **`queue-state.json` lag at queue-write time.** `/spec-queue` writes the spec file and the queue-state entry in the same commit (spec 0202 §2.2), so the on-disk pair is always consistent at read time. No TOCTOU gap.
- **Decimal-child specs.** `format_spec_id(parent, child)` produces the same string keys (`"0203.1"`, `"0203.2"`) that `queue-state.json` uses (verified in the existing file). Lookups land cleanly on both grammar variants. The supervisor's `spec_number` comes from `fm.get("spec")` which carries the full decimal-suffixed ID — also keyed cleanly.
- **Re-activation surprise (applies to §3.3, §3.4).** Fixing the supervisor helpers re-enables the L-spec checkpoint-resume code path that has been silently dead since spec 0202. The first L-spec drained via `/dev-queue-run` after this ships will exercise resume mode for real. Mitigation: tests in §5.2 lock the helpers' contract; the resume code path inside `drain_queue` itself has its own pre-existing test coverage (verify at implement time).
- **Filename-based spec lookup in `_read_spec_status`.** The function uses `entry.name.startswith(f"{spec_number}-")` to find the spec file. This is correct for the convention `0203.2-<slug>.md` but would fail if a future spec is named `0203.20-<slug>.md` because the startswith match would also fire on `0203.2-…`. Out of scope here (existing behaviour, not introduced by this fix); flag and skip unless the convention changes.

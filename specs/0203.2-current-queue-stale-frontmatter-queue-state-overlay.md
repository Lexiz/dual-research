# Spec 0203.2 — Fix: `current_queue` reads stale frontmatter — overlay queue-state.json before filtering

> **Type:** bug  |  **Severity:** P1  |  **Affects:** `/dev-next` orchestrator queue-head pick (step 6) and any caller of `current_queue` post-spec-0202
> **Bump:** PATCH — bug fix
> **Evidence:** caught live during spec 0203.1's own `/dev-next` cycle — `current_queue()` returned `"0203"` as the queue head even though `dashboard/queue-state.json` had `specs.0203.status = "deployed"` (true queue head was `"0203.1"`). Documented in [handoffs/2026-05-24-spec-0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md:84](handoffs/2026-05-24-spec-0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md) deferral entry.

## 1. Reproduction

**Environment:** `/Users/alexlisitzky/dual-research-author/` author worktree on `main`, post-spec-0202 (any commit ≥ v1.42.0). Direct invocation of `current_queue` from Python.

**Steps:**

1. Confirm at least one spec exists whose **frontmatter** says `status: queued` but whose **`dashboard/queue-state.json`** entry says `status: deployed` (or `merged`, `in_progress`, anything other than `queued`). Spec 0203 at the time of the 0203.1 cycle was exactly this case — frontmatter frozen at queue time per [specs/0202-main-commit-noise-queue-state-file-and-handoff-archival.md](specs/0202-main-commit-noise-queue-state-file-and-handoff-archival.md) §2.1, queue-state mutated through to `deployed`.
2. From the repo root run:
   ```
   uv run python -c "
   from scripts.spec_lifecycle.pick_next_number import current_queue
   for sid, _ in current_queue('specs'):
       print(sid)
   "
   ```

**Expected:** the printed list contains only spec IDs whose **live** status (per `dashboard/queue-state.json`) is `queued`. The first entry is the true queue head — the spec `/dev-next` should pick up next.

**Actual:** the list contains every spec whose **frontmatter** still says `status: queued`, including specs that have been merged / deployed / cancelled since their queue-time snapshot was frozen. The first entry can be a long-finished spec; `/dev-next` then prefetches the wrong handoff, opens the wrong spec body, and either (a) silently no-ops because the work is done, or (b) tries to re-implement an already-shipped spec. Symptom mirrors [specs/0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md:64-81](specs/0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md) §2.1 — frontmatter and `queue-state.json` disagree on cycle-mutable status — but the affected surface is the `/dev-next` orchestrator, not the live dashboard.

## 2. Root cause hypothesis

`current_queue` at [scripts/spec_lifecycle/pick_next_number.py:130-146](scripts/spec_lifecycle/pick_next_number.py) filters specs purely by their on-disk frontmatter:

```py
fm = parse(entry).frontmatter
if fm.get("kind") == "dev" and fm.get("status") == "queued":
    ...
```

Per spec 0202 §2.1, frontmatter `status` is **frozen at queue time** and never re-written during a cycle. Live cycle-mutable status lives in `dashboard/queue-state.json` (read via `scripts/spec_lifecycle/queue_state.py:read_state` at [scripts/spec_lifecycle/queue_state.py:111](scripts/spec_lifecycle/queue_state.py)). Spec 0202's renderer-side fix at [scripts/spec_lifecycle/render_dashboard.py:167-199](scripts/spec_lifecycle/render_dashboard.py) layers `queue_state.specs[full_id]` over the frontmatter dict before any downstream consumer reads `status`. Spec 0203.1's `data.js` fix did the same for the live Pages Function. `current_queue` was missed in both passes — it still reads the frozen snapshot directly, so it returns specs whose live status is anything but `queued`.

This is the same fix shape as spec 0203.1 §3.1 ("Teach `functions/api/data.js` about queue-state.json") and is a continuation of spec 0202's queue-state authority work — an arguable "should but didn't" of 0202 that was caught live during 0203.1's own cycle and explicitly logged in [handoffs/2026-05-24-spec-0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md:84](handoffs/2026-05-24-spec-0203.1-dashboard-queue-state-parity-and-l-spec-event-vocab.md).

## 3. Fix

One additive change, plus a sweep of the file's other status-reading helpers.

### 3.1 — Overlay queue-state.status before filtering in `current_queue`

In [scripts/spec_lifecycle/pick_next_number.py:130-146](scripts/spec_lifecycle/pick_next_number.py), teach `current_queue` to consult `dashboard/queue-state.json` and prefer its `status` when present, mirroring the renderer's pattern at [scripts/spec_lifecycle/render_dashboard.py:188-191](scripts/spec_lifecycle/render_dashboard.py):

```py
def current_queue(specs_dir: str | Path) -> list[tuple[str, dict]]:
    from .frontmatter import parse
    from .queue_state import read_state

    # Spec 0202 §2.1 — frontmatter `status` is frozen at queue time; live
    # cycle-mutable status lives in dashboard/queue-state.json. Overlay
    # the queue-state entry before filtering so finished specs drop out.
    # Mirrors render_dashboard.py:188-191 and data.js QUEUE_STATE_LAYERED_FIELDS.
    repo_root = Path(specs_dir).parent
    queue_state = read_state(repo_root)

    items: list[tuple[tuple[int, int], str, dict]] = []
    for parent, child, entry in _scan_spec_ids(specs_dir):
        fm = parse(entry).frontmatter
        spec_id = format_spec_id(parent, child)
        state_entry = queue_state.specs.get(spec_id, {})
        live_status = state_entry.get("status") if state_entry.get("status") else fm.get("status")
        if fm.get("kind") == "dev" and live_status == "queued":
            items.append(((parent, child), spec_id, fm))
    items.sort(key=lambda t: t[0])
    return [(spec_id, fm) for _, spec_id, fm in items]
```

Notes:

- The returned tuple still carries the **frontmatter** dict (not a layered copy), because every existing caller treats it as shape-immutable metadata (title, type, complexity, depends_on). Layering live cycle-mutable fields into the returned dict would be a wider API change and is out of scope here; the filter alone is sufficient to fix the queue-head pick.
- `repo_root = Path(specs_dir).parent` matches the convention used elsewhere in this module — every caller passes `"specs"` or `repo_root / "specs"`. Defensive: if `queue-state.json` is missing or malformed, `read_state` returns an empty `QueueState` per [scripts/spec_lifecycle/queue_state.py:114-119](scripts/spec_lifecycle/queue_state.py), the overlay no-ops, and the function falls back to the legacy frontmatter-only behaviour — same defensive pattern as spec 0203.1's `data.js` fix.

### 3.2 — Sweep the rest of `pick_next_number.py` for the same pattern

Per the handoff deferral note: "Same fix should review every other `pick_next_number.py` helper that filters or reads spec status from frontmatter."

Inventory pass on [scripts/spec_lifecycle/pick_next_number.py](scripts/spec_lifecycle/pick_next_number.py) (147 lines total):

- `parse_spec_id`, `format_spec_id` — pure ID parsers. No frontmatter read. **Skip.**
- `_scan_spec_ids` — walks `specs/` for filenames matching `SPEC_ID_RE`. No frontmatter read. **Skip.**
- `next_dev_number` — scans parent IDs from filenames. No frontmatter read. **Skip.**
- `next_decimal_child` — scans children of a parent from filenames. No frontmatter read. **Skip.**
- `next_draft_id` — scans `specs/drafts/` filenames. No frontmatter read. **Skip.**
- `current_queue` — **only** frontmatter-status reader in the file. Fixed by §3.1.

Sweep result: `current_queue` is the only offending helper. No further changes in this file. The sweep is recorded here (not silently dropped) so a future reader sees the audit was deliberate.

## 6. Blast radius

- **Single function changed.** `current_queue` at [scripts/spec_lifecycle/pick_next_number.py:130-146](scripts/spec_lifecycle/pick_next_number.py) — no other module's API or signature touched.
- **Direct callers.** Searched the repo for `current_queue(` usages:
  - The `/dev-next` and `/dev-queue-run` skill files invoke it via `uv run python -c "from scripts.spec_lifecycle.pick_next_number import current_queue; …"` at the queue-head-pick step.
  - The validator-pass loops at queue-time (`/spec-queue`, `/spec-promote`) do not call it; they call `next_dev_number` / `next_decimal_child` instead.
  - `tests/spec_lifecycle/test_pick_next_number.py` covers `next_dev_number` / `next_decimal_child` / `next_draft_id` but does NOT currently cover `current_queue`. This spec's §5 test is the first.
- **Behaviour preservation for the queue-time happy path.** A spec that has just been written by `/spec-queue` will have both (a) frontmatter `status: queued` AND (b) a queue-state.json entry `status: queued`. The overlay returns `queued`, the filter accepts, the spec appears in the queue — identical to the pre-fix behaviour for never-cycled specs.
- **No on-disk schema change.** `queue-state.json` already exists per spec 0202; this spec only adds a read of it from a code path that wasn't previously consulting it.

## 7. Out of scope

- **Layering all cycle-mutable fields (not just `status`) into the returned frontmatter dict.** Every existing caller treats the dict as shape-immutable metadata; broadening the layer would require an audit of every consumer (`/dev-next` skill prompts, tests, manual scripts). Deferred to a follow-up dev spec if a caller actually needs the live `started_at` / `pr` / `merged_at` from `current_queue`.
- **Audit of helpers outside `pick_next_number.py`** that might read spec status from frontmatter. Spec 0202 §2.5 and spec 0203.1 §3.1 already covered the renderer and the Pages Function — the two largest surfaces. If a third frontmatter-status reader is discovered in the future, file a new spec; do not expand this one inline.
- **Rewriting the `/dev-next` skill text to also call queue-state directly** as a second-level defence. The skill calls `current_queue` and trusts its return; fixing the helper is the single load-bearing change.

## 8. Risks

- **`Path(specs_dir).parent` assumption.** All in-repo callers pass `"specs"` or `<repo_root> / "specs"` so `.parent` resolves to the repo root. If a future caller passes an absolute path like `"/tmp/test/specs"`, `.parent` resolves to `/tmp/test`, which is the test's repo root — also correct. The only failure mode is a caller that passes `"."` for `specs_dir`, where `.parent` is empty; in that case `read_state` looks for `dashboard/queue-state.json` from the cwd, which is the correct behaviour from a repo-root cwd. Mitigation: keep the existing convention; document the new dependency in the docstring.
- **`queue-state.json` lag at queue-write time.** `/spec-queue` writes the spec file and the queue-state entry in the same commit (spec 0202 §2.2), so the on-disk pair is always consistent at read time. No TOCTOU gap.
- **Decimal-child specs.** `format_spec_id(parent, child)` produces the same string keys (`"0203.1"`, `"0203.2"`) that `queue-state.json` uses (verified in the existing file). Lookups land cleanly on both grammar variants.

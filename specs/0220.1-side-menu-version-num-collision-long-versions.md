# Spec 0220.1 — Fix: Changelog side-menu version-num span collides with summary on long versions

> **Type:** bug  |  **Severity:** P2  |  **Affects:** `/#/how-it-works` Changelog tab side menu, every released version from v1.4.x onward (3+ digit MINOR)
> **Bump:** PATCH — CSS-only width adjustment.
> **Evidence:** Spec 0220 handoff [handoffs/2026-05-26-spec-0220-in-app-changelog-auto-generated.md:45](handoffs/2026-05-26-spec-0220-in-app-changelog-auto-generated.md:45) — *"`1.45In-app Changelog auto-generate`"* — the version chip and the trailing summary visually overlap because `.menu-section-num` is hard-coded to `width: 18px`, which fits the legacy curated entries' 3-character versions ("0.5") but not the 6-character "1.45.0" shape that now dominates the auto-generated list. Pre-spec-0220 only 12 hand-picked entries were rendered in the side menu and they all happened to be short; spec 0220 widened the surface to every entry in `version-notes.json` (208 of them), exposing a latent bug that was previously masked by data shape.

---

## 1. Reproduction

**Environment:** any browser, `dual-research-alex.fly.dev/#/how-it-works`, Changelog sub-tab active.

**Steps:**
1. Navigate to `https://dual-research-alex.fly.dev/#/how-it-works`.
2. Click the **Changelog** tab in the page header.
3. Look at the left-hand `<nav class="hiw-page__menu">` rail.
4. Inspect any list item whose version is ≥ 4 characters (every entry from v1.4.x onward — i.e. the first 12 entries that render in the side menu under the post-0220 newest-first ordering).

**Expected:** the version number renders fully (e.g. `1.45.0`) followed by a visible gap, then the truncated summary (e.g. `In-app Changelog auto-generate`). The two text runs are visually distinct, with the version occupying its own fixed-width column and the summary starting cleanly to its right.

**Actual:** the version and summary butt up against each other and partially overlap, producing strings like `1.45In-app Changelog auto-generate` (the trailing `.0` of the version is occluded by the `I` of the summary). See [handoffs/2026-05-26-spec-0220-in-app-changelog-auto-generated.md:45](handoffs/2026-05-26-spec-0220-in-app-changelog-auto-generated.md:45).

## 2. Root cause hypothesis

The `.menu-section-num` rule at [src/dual_research/ui/static/components.css:3630](src/dual_research/ui/static/components.css:3630) sets:

```css
.hiw-overlay__menu-list .menu-section-num {
  display: inline-block; width: 18px; color: var(--md-on-surface-faint);
  font-family: var(--md-font-data); font-size: var(--md-label-s-size);
}
```

`width: 18px` is enough horizontal real estate for the legacy "How it works" side-menu numbering (`1`, `2`, … through single-digit-prefix section numbers) and for the legacy hand-curated `VERSION_NOTES` array's short version strings (`"0.5"`, `"1.0"`). It is **not** enough for the 6-character canonical version strings produced by `scripts/build_version_notes.py` and rendered by the post-spec-0220 markup at [src/dual_research/ui/static/how-it-works.jsx:1082](src/dual_research/ui/static/how-it-works.jsx:1082):

```jsx
<span className="menu-section-num">{e.version}</span>{(e.summary || '').slice(0, 30)}
```

Because the rule is `display: inline-block` with a fixed `width` (not `min-width`), the version text overflows the box. The version text has no right-padding and the summary has no left-margin, so on overflow the summary's first character begins inside the version's visual frame. CSS-only fix.

Pre-spec-0220 the bug was latent — the renderer sliced `VERSION_NOTES` to the first 12 entries, and those 12 happened to all be short versions. Spec 0220 widened the side-menu data source to the full auto-generated list, surfacing the latent bug across every entry past v1.4.x.

## 3. Fix

CSS-only change to `.hiw-overlay__menu-list .menu-section-num` in **both** the live-app copy and the design-system authoritative copy (CLAUDE.md two-file CSS sync rule):

- [src/dual_research/ui/static/components.css:3630](src/dual_research/ui/static/components.css:3630) — change `width: 18px` to `min-width: 48px;` and add `margin-right: var(--s-2);`. The `min-width` of 48px comfortably fits the longest realistic version string (`"99.99.99"` is 8 chars at the data-font tracking — 48px clears 6-character `"1.45.0"` with ~12px headroom for future MAJOR/MINOR growth without re-touching this rule).
- [design-system/assets/styles/composed-components.css](design-system/assets/styles/composed-components.css) — add the same rule. The DS authoritative file currently has **no** `.menu-section-num` rule (verified via `grep` — only the live `components.css` has it). This bug fix lands the rule in both files in one commit, closing a pre-existing DS-sync gap as a bonus.

Diff sketch (live copy):

```diff
 .hiw-overlay__menu-list .menu-section-num {
-  display: inline-block; width: 18px; color: var(--md-on-surface-faint);
+  display: inline-block; min-width: 48px; margin-right: var(--s-2);
+  color: var(--md-on-surface-faint);
   font-family: var(--md-font-data); font-size: var(--md-label-s-size);
 }
```

No JSX changes. No JSON changes. No new components.

## 4. User stories & acceptance criteria

This is a UI bug fix touching `src/dual_research/ui/static/components.css` and `design-system/assets/styles/composed-components.css`, so user stories + BDD scenarios are required (CLAUDE.md DS-gate rule + validator §2.3).

### 4.1 — User stories

> As a **viewer** browsing the in-app Changelog, I want each side-menu entry's version number and summary to be visually separable, so that I can scan the version-to-topic mapping at a glance without parsing run-together characters like `1.45In-app`.

### 4.2 — Acceptance scenarios (BDD)

> **Scenario 1:** Long version (6+ characters) renders without overlap
> GIVEN the Changelog tab is active and the side menu lists v1.45.0
> WHEN the user inspects the `<a>` element for that entry
> THEN the `<span class="menu-section-num">` reports a `getBoundingClientRect().width >= 48` and the adjacent summary text node's `getBoundingClientRect().left` is strictly greater than the version span's `getBoundingClientRect().right`.

> **Scenario 2:** Short legacy version (3 characters) still renders correctly
> GIVEN the Changelog tab is active and the side menu lists a legacy short version (e.g. v0.5.0 if shown, or v1.0.0)
> WHEN the user inspects the corresponding `<a>` element
> THEN the version span occupies the same 48px minimum column and the summary text begins at a stable `left` offset, matching the alignment of long-version entries in the list.

## 6. Blast radius

`.menu-section-num` is also used by the "How it works" half of the same side menu at [src/dual_research/ui/static/how-it-works.jsx:1075](src/dual_research/ui/static/how-it-works.jsx:1075), where it holds the section index (`1`, `2`, …). Widening from `18px` to `min-width: 48px` adds horizontal space; `min-width` is non-shrinking so single-digit section numbers will now sit in a wider column with extra trailing space before the label. Visually this aligns the "How it works" numbering with the "Changelog" version column, which is consistent — the two tabs share the same `<nav>` element and the user toggles between them in place. No other consumer of `.menu-section-num` was found via grep across `src/dual_research/ui/static/` and `design-system/assets/styles/`.

## 8. Risks

- **`min-width` vs `width` interaction with future content.** If a future entry's version somehow exceeds 48px (e.g. someone ships `100.0.0` — 7 chars), the span will grow horizontally and push the summary further right, which is correct behavior. If instead someone introduces a longer string into `menu-section-num` (e.g. a date prefix), the column expands to fit. Either case is graceful — no overlap regresses.
- **Visual shift on "How it works" tab.** Section numbers `1` through `7` now sit in a 48px column where they previously sat in an 18px column. The labels shift right by ~30px. Acceptable: the two tabs share the same menu rail and consistency between them is desirable. Verified during PR preview.

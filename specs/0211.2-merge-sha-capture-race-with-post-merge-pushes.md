# Spec 0211.2 — Refactor: capture `MERGE_SHA` at merge time in `/dev-next` step 20

> **Type:** refactoring  |  **Complexity:** S  |  **Depends on:** 0211
> **Bump:** PATCH — `/dev-next` skill body change; no app runtime code change
> **Evidence:** spec 0211 §2 rewrote `/dev-next`'s step 20 to "watch the `.github/workflows/deploy.yml` run that step 19's merge push triggered". The handoff at `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:44` records the actual cycle drifted from the design intent — the squash-merge for spec 0211 landed at `9203e2f`, but `origin/main` had advanced to `8416888` (a `spec(0211): queue-state update` commit emitted by a post-merge `--push-to-main` call — see `scripts/spec_lifecycle/queue_state.py:393` for the commit-message template `spec(NNNN): queue-state update`) by the time step 20 ran `MERGE_SHA="$(git rev-parse origin/main)"`. Step 20 therefore watched the deploy run for `8416888` (a queue-state-only commit), not the run for the actual squash-merge `9203e2f`. Both runs ship the same image because queue-state commits don't change Docker layers, so the watched run's pass/fail still tracks the actual deploy outcome — the gap is design-intent vs. observed-behavior, not a deploy correctness failure.

## 1. Current state

`/dev-next` step 20's `MERGE_SHA` capture is positioned AFTER step 19's re-detach + multiple `--push-to-main` calls, so `origin/main` is no longer at the merge commit by the time step 20 reads it.

- **Step 20 body** at `~/.claude/skills/dev-next/SKILL.md:323`–`:363` opens with:
  ```bash
  # The merge SHA is whatever origin/main points to now — step 19's
  # re-detach already fetched and pointed HEAD at the just-merged commit.
  MERGE_SHA="$(git rev-parse origin/main)"
  uv run python -m scripts.spec_lifecycle.queue_state append-event --push-to-main NNNN deploy_started '{}'
  ```
  The comment at line 328–329 explicitly states the assumption ("step 19's re-detach already fetched and pointed HEAD at the just-merged commit") — the assumption that no other `--push-to-main` call has fired between the merge and this line.

- **Step 19's re-detach** at `~/.claude/skills/dev-next/SKILL.md:317`–`:322`:
  ```bash
  git fetch --quiet origin
  git checkout --detach origin/main
  ```
  At the moment this fetch runs, `origin/main` is whatever is currently on the remote — which may have advanced past the squash-merge if any concurrent or sequential `--push-to-main` call has fired in the meantime.

- **The `--push-to-main` plumbing** at `scripts/spec_lifecycle/queue_state.py:393`–`:402` writes a commit on top of the current `origin/main`, with message template `spec(NNNN): queue-state update`. The retry loop at `scripts/spec_lifecycle/queue_state.py:373`–`:402` re-fetches and rebuilds on non-fast-forward, so the commit always lands as a new tip of `origin/main`. Every `--push-to-main` call therefore monotonically advances `origin/main` by one commit.

- **Observed drift this cycle** (per `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:28`):
  - `9203e2f` — squash-merge of spec 0211's PR #243 (the design-intent merge commit).
  - `8416888` — `spec(0211): queue-state update` (post-merge `--push-to-main` from step 18's `status=merged` write OR another in-flight queue-state event push between step 19 and step 20's `git rev-parse origin/main` line).
  - At step 20, `MERGE_SHA = 8416888`, not `9203e2f`. The watched deploy run was `26362575383` (the deploy for `8416888`), not the run triggered by the squash-merge itself.

- **Why this is structurally guaranteed to drift, not just an observed glitch**: step 18 at `~/.claude/skills/dev-next/SKILL.md:282`–`:289` (the "Merge-time state update" block) runs `queue_state set --push-to-main` BEFORE step 19's `gh pr merge`. But step 18 itself is preceded by step 17's branch push and the deploy.yml CI run on the feature branch's push doesn't fire (deploy.yml is gated to `branches: [main]` at `.github/workflows/deploy.yml:14`–`:17`). Then step 19 fires `gh pr merge` → merge commit lands on main → deploy.yml CI run for the merge commit fires → step 19's re-detach `git fetch` picks up the merge → if any subsequent `--push-to-main` call (per-cycle the implementer added an event push between step 19's verified-delete-after-merge logic and step 20's MERGE_SHA capture; see SKILL.md prose at line 313 referencing `scripts/sweep_stale_branches.sh` cleanup paths) has fired by then, `origin/main` is already ahead.

**Pain points:**

- **Design-intent drift.** Spec 0211 §2 wrote "step 19's merge push triggered" as the watched-run identity. Today `/dev-next` may watch a DIFFERENT deploy run (the one for the post-merge queue-state commit). The two runs share the same image, so pass/fail still tracks correctly today — but the run URL surfaced in `handoffs/` and on the dashboard belongs to a queue-state commit, not the spec's merge commit. Operators reading the handoff to debug a deploy failure are pointed at the wrong run as their entry point.

- **Latent correctness risk.** If a future change ever lands code (not just queue-state) in a post-merge `--push-to-main` flow (e.g. a handoff write that the implementer accidentally moves before step 20), the watched run would be for a SUBSEQUENT image build and the merge-commit's deploy could fail silently while step 20 reports the later run's success. The current "queue-state commits don't change image layers" guarantee is an emergent property of `scripts/spec_lifecycle/queue_state.py:393`'s message-only writes, not a contract.

- **Race window grows with `--push-to-main` retries.** The push-to-main plumbing at `scripts/spec_lifecycle/queue_state.py:373`–`:402` retries on non-fast-forward by re-fetching and rebuilding the commit. Each retry that lands a queue-state commit between step 19 and step 20 widens the drift window. Today the drift is ~1 commit; under retry pressure it can be more.

- **Observable evidence.** The handoff at `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:28` documents the specific SHAs `9203e2f` (merge) vs `8416888` (queue-state) and the run `26362575383` vs the merge's actual run `26362546656`. The deploy.yml workflow's two distinct run rows are visible at https://github.com/Lexiz/dual-research/actions runs `26362546656` and `26362575383`.

## 2. Target state

`/dev-next` step 19 captures the merge commit SHA from the `gh pr merge` output (or via a `gh api` lookup keyed off the PR number) immediately at merge time — before step 19's re-detach, before any subsequent `--push-to-main` call. Step 20 consumes the captured SHA as its `MERGE_SHA` variable rather than re-deriving from `origin/main`.

The fix is a step-ordering tightening, not a new mechanism:

- **Step 19** adds one bash line right after `gh pr merge --admin --squash --delete-branch`:
  ```bash
  MERGE_SHA="$(gh pr view "$PR_NUM" --json mergeCommit --jq '.mergeCommit.oid')"
  ```
  `gh pr view --json mergeCommit` returns the squash-merge commit SHA verbatim from GitHub's PR API, independent of any local git state. The call is read-only against the GitHub API; it does not touch the working tree, `origin/main`, or any local refs. It is invoked AFTER `gh pr merge` returns successfully (so the merge commit exists) and BEFORE step 19's verified-delete + re-detach logic, so no subsequent `--push-to-main` can drift the reading.

- **Step 19's re-detach** at `~/.claude/skills/dev-next/SKILL.md:317`–`:322` stays unchanged in shape. The `git fetch --quiet origin` + `git checkout --detach origin/main` still runs — `MERGE_SHA` is now decoupled from the post-fetch `origin/main` pointer.

- **Step 20** at `~/.claude/skills/dev-next/SKILL.md:330` drops its own `MERGE_SHA="$(git rev-parse origin/main)"` line and reads the variable from step 19's scope. The comment at lines 328–329 ("The merge SHA is whatever origin/main points to now — step 19's re-detach already fetched and pointed HEAD at the just-merged commit") becomes obsolete and is removed; the new comment cites step 19 as the capture site.

- **The bounded poll at `~/.claude/skills/dev-next/SKILL.md:336`–`:341`** continues to query `gh run list --workflow=deploy.yml --commit "$MERGE_SHA"` — now the commit is guaranteed to be the actual merge commit. If GitHub Actions has already fired the deploy.yml run for the merge by the time step 20 begins polling, the run row appears within the first iteration. If queue-state commits land between step 19 and step 20, they trigger their own deploy.yml runs (one per push), but step 20's poll is keyed off `MERGE_SHA`, so it ignores those.

Two design points worth naming:

- **Why `gh pr view --json mergeCommit` not `git rev-parse FETCH_HEAD` after `git fetch`.** `FETCH_HEAD` is local-state-dependent and brittle (depends on the order of refspecs in `.git/config`). `gh pr view` reads GitHub's authoritative record of which commit the squash-merge produced; it works correctly even if local state is corrupted or the queue worktree's `origin/main` reference is stale.

- **Why not capture from `gh pr merge`'s stdout.** `gh pr merge --admin --squash --delete-branch` does NOT print the resulting merge commit SHA to stdout in any documented format (verified against `gh version 2.x` man page: the command emits a single human-readable "Merged pull request #N" line on success). Parsing that line for a SHA is fragile across `gh` versions. Calling `gh pr view --json mergeCommit` after a successful merge is the supported API.

## 6. Risks

- **Risk: `gh pr view` rate-limits or fails transiently.** *Mitigation:* the call follows a successful `gh pr merge` (same auth token, same API host, sub-second prior); GitHub's API consistency guarantees the merge result is queryable immediately after the merge call returns. If `gh pr view` does fail (network blip, API outage), the empty-`MERGE_SHA` guard in step 1 halts with a clear error before step 20 tries to watch a phantom run. No silent fallback.

- **Risk: `PR_NUM` extraction from `PR_URL` is fragile.** *Mitigation:* the PR URL shape is canonical `https://github.com/<org>/<repo>/pull/<num>` and is generated by `gh pr create` in the same step's earlier bash scope. `basename "$PR_URL"` extracts the numeric component reliably; the `gh pr view` call will fail loudly if `PR_NUM` is somehow non-numeric. Same fragility as today's existing PR-URL handling in `/dev-next`.

- **Risk: `gh pr view --json mergeCommit` returns null/empty on the rare case the merge was a fast-forward push (no merge commit) instead of a squash.** *Mitigation:* spec 0211 mandates `gh pr merge --admin --squash` at `~/.claude/skills/dev-next/SKILL.md:292`. A squash always produces a merge commit. The empty-`MERGE_SHA` guard in step 1 covers the future case where someone changes the merge mode; the cycle halts cleanly rather than watching a phantom run.

- **Risk: the source-pattern test in step 3 is brittle to SKILL.md prose changes.** *Mitigation:* the test scopes its regex to specific step-N blocks (looking for `^20\.` / `^19\.` heading anchors), the same scoping doctrine as `tests/test_spec_0211_no_local_fly_deploy.py`. Prose changes outside those blocks don't trip the test; structural changes inside the blocks correctly trip it (which is the test's purpose — locking the step structure that this spec establishes).

- **Risk: a future spec changes the PR-merge mechanism (e.g. moves to `gh pr merge --rebase`).** *Mitigation:* `gh pr view --json mergeCommit` returns the merge commit SHA for both squash and rebase modes (and null for fast-forward, which is covered above). The capture pattern is mode-agnostic. The risk is bounded by the empty-`MERGE_SHA` guard.

- **Risk: the `/dev-next` cycle that runs this spec hits the very drift this spec fixes (the implementer's spec 0211.2 cycle hits the same race we're closing).** *Mitigation:* the drift is observable but cosmetic — the watched run still ships the correct image (per the `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:44` analysis "both runs ship the same image (queue-state-only commits don't change the Docker image), so the watched run's pass/fail still tracks the actual deploy"). The implementer's cycle for spec 0211.2 may still watch a queue-state commit's run, but the spec is structurally still landed correctly. The handoff for this spec records both SHAs (captured-at-merge vs origin/main-when-step-20-runs) as evidence the fix works going forward.

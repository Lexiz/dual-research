# Spec 0229.2 — Tests: explicit replay against `phase2/round-02-openai.md`

> **Type:** test  |  **Complexity:** S  |  **Depends on:** 0229 (the addressee-obligation invariant + `apply_turn` runtime check)
> **Bump:** PATCH — test-only addition.
> **Evidence:** Spec 0229 §6 listed the replay test as a separate test plan item; the implementer judged it equivalent in observable behaviour to the synthetic-data unit test (`test_agreed_with_open_addressed_item_emits_one_protocol_violation`) and the verifier-level fixture test (`test_i2_4_on_dead_primary_fails_naming_four_addressee_items`) and deferred it. The deferral is documented at [`handoffs/2026-05-27-spec-0229-addressee-obligation-invariant.md:33`](handoffs/2026-05-27-spec-0229-addressee-obligation-invariant.md). The replay test would add fidelity by exercising the actual round-02-openai.md turn-file bytes through the runtime path rather than a synthetic fixture, closing the loop on the spec's stated motivation ("the four addressed-at-openai items `D-plan-c-02 / D-plan-c-04 / D-plan-c-05 / Q-plan-c-01` must trip the runtime check by id").

## 1. Coverage gap

The dead-primary anchor fixture at [`tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-02-openai.md`](tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-02-openai.md) is the real-world failing turn that spec 0229 was authored to address — openai emits `STATUS: AGREED` while four items raised by claude and addressed at openai remain open. Spec 0229 §6 enumerated the replay test as a separate test plan item that would feed this turn-file verbatim through `apply_turn` against a fresh phase state seeded with the round-01 ledger and assert four `ProtocolViolation(agreed_with_open_addressed_items)` events fire naming the four item ids.

The currently shipped tests cover the same observable behaviour at two adjacent layers:

- `test_agreed_with_open_addressed_item_emits_one_protocol_violation` at [`tests/test_spec_0229_addressee_obligation.py`](tests/test_spec_0229_addressee_obligation.py) — exercises `apply_turn` on synthetic in-memory state, asserts one PV per blocking item.
- `test_i2_4_on_dead_primary_fails_naming_four_addressee_items` at the same file — exercises the verifier-level handled-vs-unhandled detector against the dead-primary anchor fixture, asserts the four item ids appear in the I2.4 failure evidence list.

What neither test asserts is the **end-to-end byte-for-byte replay**: feed the actual round-02-openai.md turn-file bytes through `apply_turn` against a fresh `PhaseState` seeded with the round-01 ledger, and assert the runtime path emits exactly four PVs naming exactly the four item ids `D-plan-c-02`, `D-plan-c-04`, `D-plan-c-05`, `Q-plan-c-01`. The synthetic-data unit test demonstrates the predicate; the verifier-level test demonstrates the detector; the replay test demonstrates that the predicate fires on the real failing turn under the real ledger reconstruction path.

The gap is fidelity, not correctness — `apply_turn` is exercised at the unit layer and the detector is exercised at the verifier layer; the literal replay would add a third coverage layer that exercises the integration between turn-file parsing, ledger reconstruction, and the addressee-obligation check.

Coverage locations:

- [`tests/test_spec_0229_addressee_obligation.py`](tests/test_spec_0229_addressee_obligation.py) — current 28-test file; the replay would be one additional test alongside the existing two.
- [`tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-02-openai.md`](tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-02-openai.md) — the turn-file the replay reads verbatim.
- [`tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-01-claude.md`](tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-01-claude.md) + [`tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-01-openai.md`](tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-01-openai.md) — the round-01 ledger state the replay seeds.
- [`src/dual_research/orchestrator/deep_research.py`](src/dual_research/orchestrator/deep_research.py) — `apply_turn` and the addressee-obligation check.

## 2. Test approach

**Framework.** pytest, pure-stdlib + the existing `apply_turn` API; consistent with the rest of [`tests/test_spec_0229_addressee_obligation.py`](tests/test_spec_0229_addressee_obligation.py).

**Fixture seeding.** Construct a fresh `PhaseState` by:

1. Reading the round-01 claude turn-file from the anchor fixture.
2. Reading the round-01 openai turn-file.
3. Running `apply_turn` on each in order — the resulting `PhaseState` is the post-round-01 ledger that round-02-openai actually faced when the run originally executed.

This mirrors the orchestrator's real ledger reconstruction at [`src/dual_research/orchestrator/deep_research.py`](src/dual_research/orchestrator/deep_research.py) and avoids hand-rolling a "fresh phase state seeded with the round-01 ledger" — the seed is the bytes of the round-01 turns, applied through the same code path the orchestrator uses.

**Replay invocation.** Read the round-02-openai turn-file from the anchor fixture; pass its bytes through `apply_turn(state, agent="openai", round_number=2, ...)`.

**Assertions.**

- The returned `violations` list contains exactly four `ProtocolViolation` events with `violation_code == "agreed_with_open_addressed_items"`.
- For each PV, `agent == "openai"`.
- For each PV, `phase == 2` and `round == 2`.
- The set of `item_id` values across the four PVs equals `{"D-plan-c-02", "D-plan-c-04", "D-plan-c-05", "Q-plan-c-01"}`.
- Round-result reconstruction (via `process_round_end` on the same violations + the AGREED status) returns `effective_openai_status == "IN_PROGRESS"` even though `openai_status == "AGREED"` on the dataclass — confirming the gate-only demotion fires at the runtime path on the real fixture, not just on synthetic data.

**Test name.** `test_replay_round_02_openai_emits_four_addressee_obligation_violations_by_id` — explicit about the input (round-02-openai), the expected violation count (four), and the assertion shape (by id, not just by count).

**Fixture immutability.** The anchor fixture files are immutable historical record. The test reads them; it does NOT modify them. Any change to the fixture (e.g., a regen pass) requires its own spec.

## 3. What it would catch

The replay test would catch any of:

- **Regression in `apply_turn`'s addressee-obligation check** that survives the synthetic-data unit test. Synthetic tests construct the failure mode in a single in-memory step; the replay test exercises the full turn-file parse → ledger merge → status check pipeline. A bug that only manifests when the ledger state arrives via the parse path (e.g., an item-id case sensitivity mismatch, a whitespace-stripping difference) is invisible to the synthetic test but caught by the replay.
- **Regression in ledger reconstruction from round-01.** If a future refactor changes how `apply_turn` builds the post-turn ledger (e.g., a different state-merge order, a different item-id canonicalisation), the round-02-openai check might fire on a different set of items — or none. The replay's id-by-id assertion catches that specific shape.
- **Regression in the `ProtocolViolation` field schema.** The `agent / phase / round / item_id` fields are read by the verifier's handled-vs-unhandled detector (spec 0229 §2.4); a runtime emission that lacks any field would fail the verifier's match logic without producing a clear failure mode. The replay's per-field assertions surface schema regressions directly.
- **Pre-spec-0229 regression where the addressee-obligation check is silenced.** If a future refactor accidentally removes the post-turn ledger scan or short-circuits the predicate, the replay test fails immediately (zero violations on a turn that should produce four). This is the canary spec 0229 §7 R1 implicitly defends.

The pre-existing synthetic-data unit test caught the absence of the check (red before the implementation, green after). The replay test adds a second canary against the same regression class but with higher fidelity.

## 4. Risks

- **R1 — Fixture file format drift.** If a future spec changes the turn-file format on disk (markdown headers, item-id encoding), the round-02-openai.md the replay reads becomes incompatible with the post-change parser. *Mitigation:* the spec 0229 §6 verifier-snapshot tests against the same fixture already lock the fixture's format at the verifier layer; a format change would fail those tests first, surfacing the breakage before the replay's parse step. The replay is downstream of those snapshots and benefits from the same canary.
- **R2 — Test runtime cost.** Reading three turn-files and running three `apply_turn` invocations is ~10× more expensive than the synthetic-data test. *Mitigation:* `apply_turn` is O(turn size); each turn-file is small (kilobytes); the runtime is well under one second even on a cold cache. The full suite runs in under 30 seconds; adding this test is negligible.
- **R3 — False sense of completeness.** Three layers of coverage on the same invariant (unit + verifier + replay) might create the impression that the addressee-obligation contract is fully tested. *Mitigation:* spec 0229 §6 explicitly enumerates the coverage layers; this spec adds the third explicitly named layer. Any further layer would need its own spec with its own coverage-gap justification.
- **R4 — The fixture file is path-sensitive — the handoff's pointer at line 33 references `runs/20260526-102321-backend-language-choice/phase2/round-02-openai.md`, but the actual in-repo location is `tests/fixtures/anchor-runs/20260526-102321-backend-language-choice/phase2/round-02-openai.md`.** *Mitigation:* this spec uses the correct in-repo path in §1 and §2; the handoff's `runs/` shorthand is a quoted historical reference, not the fixture's canonical location.

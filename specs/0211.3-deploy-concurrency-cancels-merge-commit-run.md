# Spec 0211.3 — Refactor: `/dev-next` step 20 — accept latest-pending deploy run when the merge-commit run gets cancelled by the `deploy-main` concurrency group

> **Type:** refactoring  |  **Complexity:** S  |  **Depends on:** 0211, 0211.2
> **Bump:** PATCH — `/dev-next` skill body change; no app runtime code change
> **Evidence:** spec 0211.2 closed the `MERGE_SHA`-drift race so step 20 watches the deploy.yml run for the actual squash-merge commit. The 0211.2 cycle (handoff at `handoffs/2026-05-25-spec-0211.2-merge-sha-capture-race-with-post-merge-pushes.md:39`) then exposed the next failure mode in the same step-20 surface: the watched run for the merge commit `3f1aae5` ([run 26393346324](https://github.com/Lexiz/dual-research/actions/runs/26393346324)) was **cancelled** by `.github/workflows/deploy.yml`'s `concurrency.group: deploy-main` because subsequent `--push-to-main` queue-state commits queued newer deploy.yml runs behind it. `cancel-in-progress: false` at `.github/workflows/deploy.yml:29` only protects the currently-running job — when MORE than one new run queues behind the in-flight one, GitHub Actions cancels all but the most recent waiter. The final-pending run ([26393367291](https://github.com/Lexiz/dual-research/actions/runs/26393367291), `head_sha b728fa0`) actually deployed the image containing the squash-merge and succeeded; the orchestrator manually pivoted to watch it. A strict reading of step 20 would halt on the merge-commit run's `cancelled` exit status — false-positive failure.

---

## 1. Current state

`/dev-next` step 20 captures `MERGE_SHA` at merge time (per spec 0211.2's fix in step 19) and then polls + watches the deploy.yml run whose `head_sha` matches that SHA. The watch step does not tolerate a `cancelled` exit status from the watched run, even when that cancellation was caused by the `deploy-main` concurrency group rather than a real deploy failure.

- **Step 20 watch invocation** at `~/.claude/skills/dev-next/SKILL.md:336`–`:341` (per spec 0211.2's post-fix shape — verified by `tests/test_spec_0211_2_merge_sha_captured_at_merge_time.py:31`'s `_step_block` scoping helper that anchors on `^N. ` top-level step headings) runs `gh run watch "$RUN_ID" --exit-status` where `RUN_ID` is the first row returned by `gh run list --workflow=deploy.yml --commit "$MERGE_SHA"`. `--exit-status` propagates the run's terminal conclusion (`success` → exit 0, `failure`/`cancelled`/`timed_out` → non-zero) directly to bash. The skill body uses this as the deploy-pass gate at step 21.

- **`deploy.yml` concurrency policy** at `.github/workflows/deploy.yml:27`–`:29`:
  ```yaml
  concurrency:
    group: deploy-main
    cancel-in-progress: false  # let in-flight deploys finish
  ```
  `cancel-in-progress: false` means the currently-running job is never cancelled mid-flight. But GitHub Actions' concurrency policy still applies a queue-collapse rule for *pending* runs in the same group: when ≥ 2 runs are queued behind an in-flight job, the older pending runs are cancelled and only the newest pending run is kept. This is documented behavior — see GitHub's "Using concurrency" docs — and applies regardless of `cancel-in-progress`.

- **The `--push-to-main` plumbing** at `scripts/spec_lifecycle/queue_state.py:393` writes commits with message template `spec(NNNN): queue-state update`. Every call lands a fresh commit on `origin/main`, which triggers a fresh deploy.yml run. The retry loop at `scripts/spec_lifecycle/queue_state.py:373`–`:402` can amplify the rate of new runs.

- **Observed drift this cycle** (per `handoffs/2026-05-25-spec-0211.2-merge-sha-capture-race-with-post-merge-pushes.md:39`):
  - `3f1aae5` — squash-merge of spec 0211.2's PR #245 (the design-intent merge commit). Triggered deploy run `26393346324`.
  - Subsequent `--push-to-main` commits (`spec(0211.2): queue-state update`, etc.) landed before run `26393346324` could start deploying — `head_sha b728fa0` is the latest queue-state commit. Each push queued a new deploy.yml run in the same `deploy-main` group.
  - GitHub Actions cancelled run `26393346324` (the merge-commit's run) and kept only the most-recent waiter, run `26393367291` (for `b728fa0`).
  - Run `26393367291` succeeded and deployed the image that contains the merge commit `3f1aae5`'s code. Queue-state commits don't change Docker layers, so the deployed image is identical to what `26393346324` would have shipped.

- **Why this is structurally guaranteed, not a one-off**: step 20's poll for `MERGE_SHA`'s run happens immediately after step 19's merge; the queue-state writes from later steps (event push for `pr_merged`, `deploy_started`, `branch_cleanup_done`, etc.) all use `--push-to-main` and each one fires a fresh deploy.yml run. Whenever ≥ 2 such writes happen between the merge and the watched run starting to deploy, GitHub Actions collapses the queue and cancels the merge-commit's run.

**Pain points:**

- **False-positive halt at step 20.** `gh run watch --exit-status` exits non-zero on `cancelled`. The cycle that ships 0211.3 would halt here, even though the merge-commit's code is live (the most-recent queue-state run ships the same image). The orchestrator must intervene manually — same intervention the 0211.2 cycle required.

- **Handoff URL points at a cancelled run.** Even when the orchestrator manually pivots, the handoff's `pr:`-adjacent prose typically cites the originally-watched run URL. After the pivot, the cited URL is a cancelled run, not the run that actually deployed. Operators reading the handoff to debug a deploy issue are pointed at noise.

- **Race window grows with `--push-to-main` retries.** The push-to-main plumbing's retry loop at `scripts/spec_lifecycle/queue_state.py:373`–`:402` can land multiple queue-state commits in rapid succession under non-fast-forward pressure. Each retry pushes a new commit, each push queues a new deploy.yml run, each new run widens the cancellation window for the merge-commit's run.

- **Image-equivalence is emergent, not contractual.** Today the cancelled merge-commit run and the surviving final-pending run ship the same image because queue-state commits don't change Docker layers (`scripts/spec_lifecycle/queue_state.py:393`'s message-only writes touch `dashboard/state/queue.json` + sidecars, not `src/`, `pyproject.toml`, or `Dockerfile`). If a future change ever lands code in a post-merge `--push-to-main` flow (e.g. a handoff write that accidentally moves to before the deploy completes), the final-pending run's image would differ from the merge commit's image, and the orchestrator's "manual pivot to the latest pending run" workaround would silently ship the later image instead of the merge commit's. The current correctness depends on a property of `queue_state.py:393`'s commit-message-only writes, not a contract.

## 2. Target state

`/dev-next` step 20 treats `cancelled` exit status from `gh run watch` as a recoverable signal when the cancellation was caused by the `deploy-main` concurrency group, and falls forward to watching the latest pending run in the same group instead of halting. The pivot is automatic; no manual orchestrator intervention.

The fix is a single bash block added between the existing `gh run watch` invocation and step 21's deploy-pass gate, inside the `/dev-next` skill body. No change to `.github/workflows/deploy.yml`, no change to `scripts/spec_lifecycle/queue_state.py`, no change to app runtime code.

- **Step 20 watch invocation** at `~/.claude/skills/dev-next/SKILL.md:336`–`:341` (the post-0211.2 shape locked by `tests/test_spec_0211_2_merge_sha_captured_at_merge_time.py:31`'s `_step_block` helper) keeps its existing `gh run watch "$RUN_ID" --exit-status` line but wraps it in a `WATCH_RC=$?` capture so the cancellation case can be inspected without halting bash on `-e`:
  ```bash
  set +e
  gh run watch "$RUN_ID" --exit-status
  WATCH_RC=$?
  set -e
  ```
  (`/dev-next` runs under `set -e`; the temporary toggle preserves the existing halt-on-error contract for every other command in step 20.)

- **New: concurrency-cancellation pivot block** added directly after the watch invocation, before step 21's pass gate:
  ```bash
  if [ "$WATCH_RC" -ne 0 ]; then
      CONCLUSION="$(gh run view "$RUN_ID" --json conclusion --jq '.conclusion')"
      if [ "$CONCLUSION" = "cancelled" ]; then
          # The deploy-main concurrency group at .github/workflows/deploy.yml:27-29
          # cancels older pending runs when ≥ 2 newer runs queue behind the
          # in-flight job (spec 0211.3). Pivot to the latest deploy.yml run
          # on origin/main and watch that instead.
          LATEST_SHA="$(git ls-remote origin main | awk '{print $1}')"
          PIVOT_RUN_ID=""
          for _ in $(seq 1 30); do
              PIVOT_RUN_ID="$(gh run list --workflow=deploy.yml --commit "$LATEST_SHA" --json databaseId --jq '.[0].databaseId')"
              [ -n "$PIVOT_RUN_ID" ] && break
              sleep 1
          done
          if [ -z "$PIVOT_RUN_ID" ]; then
              echo "ERROR: spec 0211.3 pivot — no deploy.yml run found for origin/main $LATEST_SHA after 30s"
              exit 1
          fi
          echo "spec 0211.3: merge-commit run $RUN_ID was cancelled by deploy-main concurrency; pivoting to run $PIVOT_RUN_ID for origin/main $LATEST_SHA"
          RUN_ID="$PIVOT_RUN_ID"
          gh run watch "$RUN_ID" --exit-status
      else
          echo "ERROR: deploy run $RUN_ID concluded with $CONCLUSION (not cancelled — real failure)"
          exit 1
      fi
  fi
  ```
  The block runs `gh run view --json conclusion` only when `$WATCH_RC` is non-zero, so the happy-path is one extra `[ "$WATCH_RC" -ne 0 ]` test. On `cancelled`, it re-queries `origin/main` for the latest commit, finds the deploy.yml run for that commit, and re-runs `gh run watch` against it. The pivot's `gh run watch` is the strict-mode watch (under `set -e`), so a real failure in the pivoted run halts the cycle as it does today.

- **Step 21's deploy-pass gate** at `~/.claude/skills/dev-next/SKILL.md:343`–`:350` (the next `21.` block heading after step 20 per the `_step_block` helper convention) stays unchanged. It already keys off `$RUN_ID`, which the pivot block updates in-place; the gate sees the pivoted run ID transparently.

- **Why the pivot uses `git ls-remote origin main` not `git rev-parse origin/main`**: the queue worktree's local `origin/main` reference may be stale if step 19's re-detach happened before the queue-state pushes that caused the cancellation. `git ls-remote origin main` reads the remote's authoritative tip without touching any local refs — same doctrine as spec 0211.2's choice of `gh pr view --json mergeCommit` over `git rev-parse FETCH_HEAD`.

- **Why pivot to "latest on `origin/main`" not "next pending run in the same concurrency group"**: GitHub Actions' concurrency-group queue collapse keeps exactly one survivor — the most-recent waiter. By the time `gh run watch` returns `cancelled` on the merge-commit's run, the surviving run is necessarily the one queued for the latest commit on `origin/main`. Querying `gh run list --workflow=deploy.yml --commit "$LATEST_SHA"` is equivalent to "the surviving run" but uses the same query mechanic step 20 already uses — no new tool surface.

- **Handoff cross-reference**: when the pivot fires, the cycle emits a `deploy_pivoted` event via `queue_state append-event --push-to-main NNNN deploy_pivoted '{"original_run": "...", "pivot_run": "...", "merge_sha": "...", "pivot_sha": "..."}'`. The handoff body cites both run IDs and explains the cancellation. The dashboard renders the pivot as a single deploy event whose `run_url` points at the surviving run.

## 6. Risks

- **Risk: `gh run view --json conclusion` returns a stale value if the run's conclusion hasn't propagated to GitHub's API yet.** *Mitigation:* `gh run watch --exit-status` only returns after the run reaches a terminal state. By the time we read `$WATCH_RC` and call `gh run view --json conclusion`, the run is in a terminal state and the conclusion field is populated. GitHub's API consistency guarantees this — same consistency `gh run watch` already relies on for its `--exit-status` propagation.

- **Risk: the pivoted run is ALSO cancelled by a third queue-state push.** *Mitigation:* the cancellation rule is "older pending runs get cancelled". The pivot reads `git ls-remote origin main` which is always the latest tip at pivot time. If a fourth push lands AFTER the pivot's `gh run list` query but BEFORE the pivoted `gh run watch` returns, the pivoted run would itself be cancelled. In that case, `gh run watch` exits non-zero again, but the new block now executes under `set -e` (the `set +e` toggle is scoped to the first watch only), so the cycle halts cleanly. Operators see "deploy run X concluded with cancelled" in the halt log. Acceptable: the recursive-pivot case requires ≥ 3 `--push-to-main` calls in a single step-20 window, which is rare. If it ever happens in practice, a follow-up spec converts the pivot into a bounded loop.

- **Risk: the source-pattern test in step 3 is brittle to SKILL.md prose changes.** *Mitigation:* the test scopes its regex to step 20's block via the `_step_block` helper (same scoping doctrine as `tests/test_spec_0211_2_merge_sha_captured_at_merge_time.py:31`). Prose changes outside step 20 don't trip the test; structural changes inside step 20 correctly trip it (which is the test's purpose).

- **Risk: a future spec changes the concurrency group name in `.github/workflows/deploy.yml`.** *Mitigation:* the pivot block does not name `deploy-main` programmatically — it only references it in a comment. The pivot logic keys off the run's `conclusion = cancelled` field, which is concurrency-group-agnostic. If a future spec renames the group, the pivot still fires correctly. If a future spec removes the concurrency group entirely, the pivot becomes dead code (never fires), which is harmless.

- **Risk: `git ls-remote origin main` returns an empty result transiently (network blip).** *Mitigation:* the `LATEST_SHA` variable is checked for non-empty before the pivot poll begins; if empty, the cycle halts with a clear error message. Same auth path as every other `git` call in `/dev-next`; no new failure surface.

- **Risk: the cycle that runs this spec hits the very cancellation this spec fixes (the implementer's spec 0211.3 cycle hits the same concurrency cancellation).** *Mitigation:* this is the design intent — the spec's verification mode is "run a cycle that triggers the cancellation and confirm the pivot fires automatically". The handoff records both run IDs (cancelled merge-commit run + pivoted surviving run) as evidence the fix works going forward. If the cancellation does NOT trigger in the 0211.3 cycle (because fewer `--push-to-main` calls land between merge and step-20 watch this time), the handoff records "pivot did not fire this cycle; behavior preserved" — the spec's structural fix is still in place for future cycles.

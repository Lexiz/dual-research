# Spec 0211.1 — Refactor: make `scripts/sweep_stale_blues.sh` work under CI (use `flyctl`, not `fly`)

> **Type:** refactoring  |  **Complexity:** S  |  **Depends on:** 0211
> **Bump:** PATCH — internal shell-script change, no behavior change for healthy clusters
> **Evidence:** spec 0211 moved the post-deploy sweep from `/dev-next` (local) into `.github/workflows/deploy.yml:40`–`:43` as a new `Sweep stale blue machines` step. The handoff for 0211 at `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:29` records the CI step did NOT execute the sweep — log line `sweep: fly machine list failed for app=dual-research-alex`. Root cause: `scripts/sweep_stale_blues.sh:77` invokes the bare `fly` binary, but `superfly/flyctl-actions/setup-flyctl@master` (used at `.github/workflows/deploy.yml:33`) installs `flyctl` on the runner PATH with no `fly` alias. The `|| true` at `deploy.yml:41` keeps the step non-fatal, so the issue is cosmetic for healthy rolling deploys (sweep would find zero stale candidates anyway), but the verification criterion in spec 0211 §3 step 1 — "log line matches the script's known output shape (`sweep: no stale blues on …` or `sweep: destroyed N/M …`)" — is unmet, and the sweep's image-based fallback path (spec 0193) is structurally unreachable from CI today.

---

## 1. Current state

The post-deploy sweep landed in CI under spec 0211 and runs but immediately bails out on a `command not found`:

- **Workflow step** at `.github/workflows/deploy.yml:40`–`:43`:
  ```yaml
  - name: Sweep stale blue machines
    run: bash scripts/sweep_stale_blues.sh || true
    env:
      FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
  ```
  The runner's PATH carries `flyctl` (installed by `setup-flyctl@master` at `deploy.yml:33`). There is no `fly` binary or shim.

- **Script** at `scripts/sweep_stale_blues.sh:77`:
  ```bash
  if ! machines_json="$(fly machine list --app "$APP" --json 2>/dev/null)"; then
      echo "sweep: fly machine list failed for app=$APP" >&2
      exit 0
  fi
  ```
  The `2>/dev/null` swallows the actual `fly: command not found` shell error, leaving only the script's generic failure log. The function returns non-zero, the early-exit fires, and the script terminates at exit-0 (the script always exits 0 per its `set -uo pipefail` + bail-out design at `scripts/sweep_stale_blues.sh:52`–`:55`).

- Three other `fly` invocations live in the same script — all unconditionally invoke the bare binary:
  - `scripts/sweep_stale_blues.sh:111` — `fly releases --app "$APP" --json …` (the spec-0193 image-based fallback's release lookup).
  - `scripts/sweep_stale_blues.sh:169` — `fly machine destroy --app "$APP" --force "$id"` (the spec-0193 image-based fallback's destroy loop).
  - `scripts/sweep_stale_blues.sh:184` — `fly machine destroy --app "$APP" --force "$id"` (the primary tag-based destroy loop).

- **Operator local usage.** The script is also invoked manually from operator shells per the `project_fly_lease_drift_recovery.md` memory. Operator shells typically have `fly` on PATH (the canonical Fly CLI binary name on macOS/Linux installs). `flyctl` is also present in those shells — both names point at the same binary in homebrew / curl-installed Fly distributions, but the operator's environment is not guaranteed to carry both.

**Pain points:**

- **CI verification criterion unmet.** Spec 0211 §3 step 1 explicitly asks the operator to verify the sweep step's log line matches `sweep: no stale blues on …` or `sweep: destroyed N/M …`. Today the log line is the generic `sweep: fly machine list failed for app=dual-research-alex`. The deferral entry at `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:42` flags this as the criterion gap.
- **Image-based fallback structurally unreachable in CI.** The spec-0193 fallback at `scripts/sweep_stale_blues.sh:132`–`:177` gates on the primary tag filter returning zero AND cluster oversize. Today the script bails at line 79 before either gate can be evaluated, so the fallback never runs under CI even when it should. Under healthy rolling deploys this is cosmetic; under a degraded state where the fallback is the safety net (per spec 0200's "image-based fallback is the *primary* mechanism for cleaning up any machine the rolling replace didn't fully cycle" — `scripts/sweep_stale_blues.sh:35`–`:39`) it is a latent reliability gap.
- **Silent-failure log shape.** The current failure log line is indistinguishable from a genuine Fly API outage. An operator skimming CI logs cannot tell "Fly was down" apart from "the runner has no `fly` binary".

## 2. Target state

`scripts/sweep_stale_blues.sh` uses a single resolved binary name for every Fly CLI invocation, picking whichever of `flyctl` / `fly` exists on PATH (preferring `flyctl` since CI is the structurally-mandated execution context after spec 0211 and CI only carries `flyctl`).

The script gains a top-level resolver near its existing argument-parsing block (`scripts/sweep_stale_blues.sh:61`–`:68`) that sets a `FLY_BIN` variable once, with a hard halt (non-zero exit on the resolution itself; the rest of the script still exits 0 per its bail-out design) if neither binary exists. Every existing `fly …` invocation site (lines `:77`, `:111`, `:169`, `:184`) becomes `"$FLY_BIN" …`.

The healthy-cluster end-to-end shape is unchanged:
- On CI runners (today carrying only `flyctl`), the resolver picks `flyctl`. The primary tag-based filter at `scripts/sweep_stale_blues.sh:87` evaluates and finds zero stale machines on a healthy rolling deploy, logging `sweep: no stale blues on dual-research-alex`. The image-based fallback at `:132`–`:177` evaluates its cluster-size gate and exits early when the cluster is on size.
- On operator shells (typically carrying both `fly` and `flyctl`), the resolver picks `flyctl` for stability with CI; behavior is identical to today since both names point at the same Fly orchestrator.
- On a degraded operator shell that has only `fly` (older installs), the resolver falls back to `fly` and the script behaves exactly as it does today.

`.github/workflows/deploy.yml` is unchanged — no shim, no PATH manipulation. The fix lives entirely in the script, keeping the workflow file the operator-readable single source of truth for "what CI runs after the deploy".

The four existing tests under `tests/test_sweep_stale_blues_*.py` (the spec-0162 / spec-0193 test suite) continue to pass — they exercise the `--input fixture.json` test mode which bypasses the resolver path entirely (`scripts/sweep_stale_blues.sh:71`–`:75` short-circuits to file read when `INPUT_FILE` is set), and the production destroy loops are gated behind `if [[ -z "$INPUT_FILE" ]]` at `scripts/sweep_stale_blues.sh:167`–`:174` and `:182`–`:189`.

## 3. Stepwise migration

Each step independently shippable / revertable.

- **Step 1: Add a `FLY_BIN` resolver to `scripts/sweep_stale_blues.sh`.** Insert a new block right after the argument-parsing loop at `scripts/sweep_stale_blues.sh:68` (before the `# Read machine state …` comment at `:70`):
  ```bash
  # Resolve the Fly CLI binary name. CI runners carry `flyctl` (installed
  # by superfly/flyctl-actions/setup-flyctl); operator shells typically
  # carry both `flyctl` and `fly`. Prefer `flyctl` for parity with the
  # CI execution context that spec 0211 made authoritative.
  if command -v flyctl >/dev/null 2>&1; then
      FLY_BIN="flyctl"
  elif command -v fly >/dev/null 2>&1; then
      FLY_BIN="fly"
  else
      echo "sweep: neither flyctl nor fly on PATH — skipping sweep" >&2
      exit 0
  fi
  ```
  The "neither on PATH" branch returns 0, matching the script's existing best-effort contract at `scripts/sweep_stale_blues.sh:52`–`:55` ("Exit code is always 0 — best-effort hygiene. The deploy that precedes this sweep has already determined success; the sweep must never fail the caller.").
  - Verified by: a one-line shell test in CI that the variable is set after the step's first second of execution; in practice, verified by the log lines from steps 2/3 below being non-generic on the next CI run.

- **Step 2: Replace every bare-`fly` invocation with `"$FLY_BIN"`.** Four sites:
  - `scripts/sweep_stale_blues.sh:77` — `fly machine list --app "$APP" --json` → `"$FLY_BIN" machine list --app "$APP" --json`
  - `scripts/sweep_stale_blues.sh:111` — `fly releases --app "$APP" --json` → `"$FLY_BIN" releases --app "$APP" --json`
  - `scripts/sweep_stale_blues.sh:169` — `fly machine destroy --app "$APP" --force "$id"` → `"$FLY_BIN" machine destroy --app "$APP" --force "$id"`
  - `scripts/sweep_stale_blues.sh:184` — `fly machine destroy --app "$APP" --force "$id"` → `"$FLY_BIN" machine destroy --app "$APP" --force "$id"`
  - Verified by: `grep -n '^\s*fly ' scripts/sweep_stale_blues.sh` returns no rows post-change (only `"$FLY_BIN"` invocations); `grep -nc 'FLY_BIN' scripts/sweep_stale_blues.sh` returns ≥ 5 (one declaration + four uses).

- **Step 3: Add a source-pattern test under `tests/test_spec_0211_1_sweep_uses_resolved_fly_bin.py`.** Pure stdlib, mirroring the doctrine used by spec 0211's test at `tests/test_spec_0211_no_local_fly_deploy.py`. Three assertions:
  - No bash line in `scripts/sweep_stale_blues.sh` invokes the bare `fly` binary outside a comment (regex match on `^\s*fly\s+(machine|releases)` against the script body with comment lines stripped).
  - The script declares `FLY_BIN` exactly once (regex match on `^\s*FLY_BIN=` against the script body with comment lines stripped).
  - The script uses `"$FLY_BIN"` for every Fly CLI invocation site (regex match on `"\$FLY_BIN"\s+(machine|releases)` against the script body; require ≥ 3 hits to cover machine list + machine destroy ×2 + releases).
  - Verified by: `uv run pytest tests/test_spec_0211_1_sweep_uses_resolved_fly_bin.py -v` green before merge.

- **Step 4: PATCH version bump + CHANGELOG.** Bump `pyproject.toml`, `src/dual_research/__init__.py`, refresh `uv.lock`. Add a `## [X.Y.Z] — YYYY-MM-DD` section to `CHANGELOG.md` under `### Fixed`, citing this spec and explaining the one-line user-visible effect: "Post-deploy sweep step in `deploy.yml` now actually runs under CI (previously logged `fly machine list failed` and exited)."
  - Verified by: dashboard at `https://lexiz.github.io/dual-research/` renders the new CHANGELOG entry post-deploy.

- **Step 5: Verify the next CI deploy emits the canonical log shape.** This is observation-only — no code change. On the deploy that ships spec 0211.1, the GH Actions log for the `Sweep stale blue machines` step at `.github/workflows/deploy.yml:40`–`:43` must show `sweep: no stale blues on dual-research-alex` (the canonical zero-candidates shape from `scripts/sweep_stale_blues.sh:121`), not the generic failure line. ## 5. Out of scope

**Explicit: this spec does NOT add any new feature.** No new feature surfaces — no new CI surfaces, no new sweep logic, no new dashboard signals, no frontmatter or queue-state schema changes. It replaces a hardcoded binary name with a resolver so an existing script runs in an existing execution context.

- **Adding a `flyctl` PATH shim to `.github/workflows/deploy.yml`** (the alternative fix flagged in the handoff at `handoffs/2026-05-24-spec-0211-delegate-fly-deploy-to-github-actions.md:42`). The shim would set `ln -sf "$(command -v flyctl)" "$RUNNER_TEMP/fly" && export PATH="$RUNNER_TEMP:$PATH"` in the workflow file. Rejected: the workflow file is the operator-readable single source of truth for "what CI runs after deploy"; adding shim plumbing there couples the workflow to a script internal. Fixing the script is the structurally correct edit. (Deferred to: no follow-up planned — closed by this spec choosing the script-side fix.)
- **Hardcoding `flyctl` instead of resolving.** Tempting (CI only carries `flyctl`), but the script is also invoked manually from operator shells per `project_fly_lease_drift_recovery.md` where `fly` is the conventional name. Keeping fallback to `fly` preserves operator muscle memory. (Deferred to: no follow-up planned — closed by the resolver design.)
- **Replacing the generic "fly machine list failed" error log with a per-cause discriminator** (e.g. "fly API outage" vs "no binary on PATH" vs "permission denied"). The resolver in step 1 already catches the "no binary on PATH" case before the bail-out path runs, so the remaining "fly machine list failed" line now means a genuine Fly API issue. Further discrimination is a separate hygiene concern. (Deferred to: future spec if operators report ambiguity in CI failure logs.)
- **Validating `FLY_API_TOKEN` is present before invoking `"$FLY_BIN"`.** Today the script implicitly relies on the env var being set by the caller (CI via repo secrets, operator via shell env). A pre-flight check would surface "token missing" more cleanly than "fly: unauthorized". Orthogonal to the binary-name fix. (Deferred to: future spec if operators report token-missing failures land confusingly.)
- **Migrating the spec-0193 release-lookup to the modern `flyctl releases list --json` syntax.** `flyctl releases --app "$APP" --json` at `scripts/sweep_stale_blues.sh:111` uses the older positional form. The current form works under the `flyctl` versions pinned by `setup-flyctl@master`. If a future `flyctl` deprecates that form, the fix is one-line. (Deferred to: future spec when `setup-flyctl@master` pulls a version that breaks the form.)
- **Removing the script entirely.** Spec 0200's rolling-deploy design makes the sweep largely cosmetic on a healthy cluster. The script remains useful as a manual recovery escape hatch per the `project_fly_lease_drift_recovery.md` memory. Spec 0211 §5 explicitly defers script removal. (Deferred to: same target as spec 0211 §5 — no follow-up planned.)

## 6. Risks

- **Risk: `command -v` returns a non-executable path on hardened PATH setups.** *Mitigation:* `command -v` is the POSIX-standard binary-resolution check; the resolver follows the same convention the rest of the project uses (e.g. handoff and queue-state scripts). If a hardened shell aliased `flyctl` to a non-executable, the script would fail at the first `"$FLY_BIN" machine list` invocation with the existing bail-out exit-0 path, identical to today's bail behavior. No new failure mode.

- **Risk: `flyctl` and `fly` diverge in subcommand syntax on some future version.** *Mitigation:* today they're the same binary under both names (homebrew installs both as symlinks; the `setup-flyctl` action installs `flyctl` only). The script's four subcommands (`machine list --json`, `machine destroy --force`, `releases --json`) have been stable across `flyctl` versions since the script was authored under spec 0162. A future divergence would be caught by the spec-0193 test suite (`tests/test_sweep_stale_blues_*.py`) which exercises the JSON-parsing surfaces. Not a regression introduced by this spec — the surface area is unchanged.

- **Risk: operator shells where `flyctl` resolves to a different Fly account than `fly` does (e.g. multi-account setups with shell aliases).** *Mitigation:* the preference for `flyctl` is deliberate — CI is the spec-0211 authoritative execution context, so operator local runs should match what CI does. Operators relying on shell aliases that differ between `flyctl` and `fly` are outside the documented operator setup; the `project_fly_lease_drift_recovery.md` memory expects vanilla `fly` PATH resolution. Not a regression — the script's behavior on a single-account-vanilla setup is identical to today.

- **Risk: a future workflow change adds a step that calls the script in an environment that has neither binary on PATH** (e.g. a minimal docker image action). *Mitigation:* the resolver's "neither on PATH" branch logs `sweep: neither flyctl nor fly on PATH — skipping sweep` and exits 0, surfacing the issue without breaking the workflow. Same safety contract as today's `|| true` at `.github/workflows/deploy.yml:41`.

- **Risk: the new source-pattern test in step 3 is brittle to comment-string changes.** *Mitigation:* the test strips comment lines (`^\s*#`) before applying its regexes, matching the convention used by `tests/test_spec_0211_no_local_fly_deploy.py`. Documentation prose inside comments cannot trip the test; only actual bash invocations can.

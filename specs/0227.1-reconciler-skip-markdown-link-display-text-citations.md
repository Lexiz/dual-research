# Spec 0227.1 — Refactor: reconciler skips markdown-link display-text citations

> **Type:** refactoring  |  **Complexity:** S  |  **Depends on:** 0227
> **Bump:** PATCH — internal regex/parser tightening, no behaviour change for consumers when their citation choices are correct (the workaround today was "operator inspects, overrides if all-external false positives").
> **Evidence:** The spec 0227 handoff at [`handoffs/2026-05-27-spec-0227-reclassify-contract-amending-specs-and-process-rule.md:31`](../handoffs/2026-05-27-spec-0227-reclassify-contract-amending-specs-and-process-rule.md) records 9 false-positive exit-3 returns during the 0227 reconcile pass, all from external `[basename.md:line](../cowork/full-path.md)` evidence citations. The reconcile-step override was manual and the deferral text names this spec as the reliable fix. The pattern is structurally guaranteed to recur because CLAUDE.md memory `cowork_channel_lives_outside_repo.md` encourages exactly this citation shape for external Cowork evidence (the canonical location is `../cowork/feedback/...`, outside the repo).

---

## 1. Current state

The reconciler in [`scripts/spec_lifecycle/reconcile.py`](../scripts/spec_lifecycle/reconcile.py) walks a spec body and classifies each citation it finds as `clean` / `mechanical` / `semantic`. The regex that drives extraction is line-oriented and unaware of markdown link syntax.

### 1.1 The matching surface

The citation regex compiled at [`reconcile.py:25-27`](../scripts/spec_lifecycle/reconcile.py:25):

```python
CITATION_RE = re.compile(
    r"(?P<path>[\w\-/.]+\.(?:py|jsx|tsx|js|ts|css|md|yaml|yml|toml|json)):(?P<line>\d+)"
)
```

…is fed the full spec body verbatim at [`reconcile.py:92-103`](../scripts/spec_lifecycle/reconcile.py:92):

```python
def _extract_citations(body: str) -> list[Citation]:
    out: list[Citation] = []
    seen: set[tuple[str, int]] = set()
    for m in CITATION_RE.finditer(body):
        path = m.group("path")
        line = int(m.group("line"))
        ...
```

There is no awareness of `[display](href)` markdown-link syntax. The regex matches the leftmost `path.ext:line` substring it finds, regardless of whether it is the *display* (the text between `[` and `]`) or the *href* (the text between `(` and `)`).

### 1.2 The classification rule that the false matches collide with

Once a citation is extracted, the in-tree existence check at [`reconcile.py:62-87`](../scripts/spec_lifecycle/reconcile.py:62) does:

```python
for cit in citations:
    target = root / cit.path
    if target.exists():
        ...  # clean or mechanical (past-EOF) bucket
    else:
        basename = Path(cit.path).name
        candidates = _find_candidates(root, basename)
        if candidates:
            ...  # mechanical (moved-file hint)
        else:
            cit.classification = "semantic"
            cit.note = "file not found anywhere in tree"
            report.semantic.append(cit)
```

Any extracted citation whose path doesn't resolve under the repo root and whose basename has no in-tree candidate is classified `semantic`. Per [`reconcile.py:47-52`](../scripts/spec_lifecycle/reconcile.py:47), a single semantic citation flips `has_blocking_drift` to True, which the CLI's `main` at [`reconcile.py:144-146`](../scripts/spec_lifecycle/reconcile.py:144) maps to exit code 3 — the contract `/dev-next` step "reconcile" reads as "halt, semantic drift".

### 1.3 The false-positive class

When a spec body legitimately cites external evidence with the conventional shape `[basename.md:line-range](../cowork/full-path.md)`, the regex matches `basename.md:line` from the display-text portion. The corresponding repo path `root / basename.md` does not exist (Cowork artefacts live outside the repo per the `cowork_channel_lives_outside_repo.md` memory and CLAUDE.md project conventions — `../cowork/feedback/...`, `../cowork/briefs/...`). The basename also has no in-tree candidate (the basenames are dated synthesis filenames, not project files). Result: `semantic` bucket → exit 3 → spurious halt.

The 0227 reconcile recorded 9 such false positives in a single spec body. Spec 0227's evidence header alone cites two external Cowork synthesis docs in this exact shape (the synthesis brief and the 0226 debrief), and §1.1 of 0227 is a "source traceability" table whose Cowork-side cells use the same pattern. Every external-evidence citation in a spec authored under the current CLAUDE.md memory generates one false positive.

### 1.4 Pain points being closed

- **Halt on a class of correct usage.** The workaround today, per the 0227 deferral, is for the operator to read the reconcile report and override exit-3 manually after confirming via `ls -la ../cowork/...` that the cited files exist. Every spec authored after the `cowork_channel_lives_outside_repo.md` memory landed (2026-05-26) is structurally guaranteed to trip this.
- **Override habit corrodes the reconcile signal.** Once operators learn to override exit-3 reflexively for "all external", they stop reading the report carefully, and a genuine internal semantic drift hidden among external false positives goes unnoticed.
- **Test coverage gap.** [`tests/test_reconcile.py`](../tests/test_reconcile.py) (if present — see step 3) exercises mechanical / semantic / clean paths but has no fixture for markdown-link display-text citations, so the regression is invisible to the existing test suite.

## 2. Target state

[`scripts/spec_lifecycle/reconcile.py`](../scripts/spec_lifecycle/reconcile.py) extracts citations from spec body prose **excluding** the display-text region of markdown-link syntax. A `[path.ext:line](href)` construct contributes the href (the structurally authoritative location) to the citation set; the display text is ignored. Plain-prose `path.ext:line` citations outside any markdown link continue to be extracted exactly as today.

### 2.1 Extraction contract after the fix

Given a body snippet like:

```markdown
See [reconcile.py:25-27](../scripts/spec_lifecycle/reconcile.py:25)
and the synthesis at [2026-05-26-synthesis.md:42](../cowork/briefs/2026-05-26-synthesis.md)
and the plain in-text `scripts/spec_lifecycle/reconcile.py:92` reference.
```

Citation extraction yields exactly two citations:

- `scripts/spec_lifecycle/reconcile.py:25` (from the first link's href)
- `scripts/spec_lifecycle/reconcile.py:92` (from the plain prose reference)

It does **not** yield `reconcile.py:25` (display-text shadow of the first href), `2026-05-26-synthesis.md:42` (display-text of the external link), or any path beginning with `../cowork/` (no `.cowork.` path in repo).

Plain-prose citations remain a first-class extraction surface — markdown-link awareness adds a skip-list, not a constraint that all citations live inside links.

### 2.2 Strategy: scrub display text before applying the regex

The fix is local to [`_extract_citations`](../scripts/spec_lifecycle/reconcile.py:92) at lines 92-103. Before applying `CITATION_RE.finditer(body)`, the body is preprocessed: every occurrence of the `[display](href)` markdown-link pattern has its display-text region replaced with whitespace of equal length. After preprocessing, the regex finds only citations that originated outside link-display regions.

The replace-with-whitespace approach (rather than removal) preserves byte offsets, keeping any future line/column reporting accurate. It is also order-independent: nested-bracket cases are naturally handled because the outer link's display text is opaque-but-not-deleted, and nested `[…](…)` inside a display would themselves be inert markdown (rendered as literal `[`/`]`) — the right behaviour is "ignore both".

### 2.3 Out-of-link `../` href handling

The href of an external-evidence link (e.g. `(../cowork/briefs/2026-05-26-synthesis.md)`) does not contain a `:line` suffix when the citation is purely document-level. After display-text scrubbing, no citation is generated for that link — correct. When the operator does want a line-anchored external citation (e.g. `[synthesis §4](../cowork/briefs/2026-05-26-synthesis.md:42)`), the regex matches the href, the target `repo_root / ../cowork/briefs/2026-05-26-synthesis.md` resolves to an out-of-repo path, the existence check at [`reconcile.py:64`](../scripts/spec_lifecycle/reconcile.py:64) returns False, the basename lookup at [`reconcile.py:79`](../scripts/spec_lifecycle/reconcile.py:79) returns empty (Cowork basename is not in `git ls-files`), and the citation lands in `semantic`. **This is preserved behaviour:** an external href-form citation in a spec body is structurally drift-prone (the repo cannot verify it), and the operator is expected to acknowledge that via an override or by demoting the line-anchor to display text only. The fix targets the high-frequency display-text false-positive class, not the rare line-anchored external-href case.

## 3. Stepwise migration

Each step independently shippable / revertable.

- **Step 1: Add a `_scrub_link_display_text` helper to `scripts/spec_lifecycle/reconcile.py`.** Define a module-level function that, given a `body: str`, returns a copy with every `[display](href)` display-text region replaced by spaces. The implementation uses a single regex with non-greedy display capture and a callable replacement that emits `" " * len(display_text)` + the literal brackets. Pattern (Python `re`): `r"\[([^\]\n]*?)\]\(([^)\n]*?)\)"` — non-greedy, no nesting attempted (markdown's own renderer does not nest link display either), no multiline display text (keeps the scrubber linear and predictable). The replacement closure returns `"[" + " " * len(display) + "]" + "(" + href + ")"`, preserving byte offsets exactly.
  - Verified by: unit test in step 3 — given body `[a.py:1](b.py:2)`, scrubbed body is `[      ](b.py:2)`, `_extract_citations` returns one citation with path `b.py` line 2.

- **Step 2: Wire the scrubber into `_extract_citations`.** Modify [`reconcile.py:92-103`](../scripts/spec_lifecycle/reconcile.py:92) — the function reads `body`, calls `scrubbed = _scrub_link_display_text(body)`, then runs `CITATION_RE.finditer(scrubbed)`. The `raw` field on the resulting `Citation` is set from `m.group(0)` against the scrubbed body, which is fine — display-text matches would have been removed; surviving matches' `raw` is identical to the original-body raw because non-link regions are byte-identical before and after scrubbing.
  - Verified by: unit test in step 3 — given the 0227 evidence-header snippet (`[handoffs/...md:31](../handoffs/...md)` plus a real plain-prose `reconcile.py:25-27` citation), the extracted set contains exactly the in-tree citations.

## 5. Out of scope

**Explicit: this spec adds no new feature.** No new reconciler surfaces, no new citation kinds, no new bucket beyond `clean` / `mechanical` / `semantic`, no new CLI flags. It is a regex-tightening that closes a structurally guaranteed false-positive class.

- **Supporting line-anchored external citations as a first-class kind** (e.g. `(../cowork/foo.md:42)` as a `clean` external-evidence citation). Today external-href line citations land in `semantic` and need operator override; that override semantics is intentionally preserved because the repo cannot verify out-of-tree line numbers (the file might have been edited since the spec was authored, and there's no git-tracking of `../cowork/`). (Deferred to: a future spec if Cowork artefacts become git-tracked.)
- **Detecting `[display](href)` constructs with multiline display text** (rare in spec bodies but possible in long quoted blocks). The scrubber pattern in step 1 is single-line by design (`[^\]\n]` excludes newlines). If a future spec author writes a multiline link display containing a path:line shadow, the scrubber will not catch it; the operator-override fallback still applies. (Deferred to: future spec if such usage is observed in the wild.)
- **Reworking the citation extraction to use a real markdown parser** (e.g. `markdown-it-py` or `mistletoe`). A full parser would handle every markdown edge case but introduces a dependency, slows reconcile (currently a tight regex pass), and is overkill for the one citation pattern this fix targets. The regex-scrubber approach is the minimum-surface-area structurally-correct fix. (Deferred to: future spec if markdown-link parsing accumulates ≥ 3 distinct edge-case bugs.)
- **Modifying the in-tree existence check at [`reconcile.py:62-87`](../scripts/spec_lifecycle/reconcile.py:62)** to recognise `../cowork/` paths as "out-of-tree but legitimate". The recognition would also need to verify the file exists relative to the spec's parent — a filesystem call per citation — and would only matter for href-form external citations, which are rare and the override semantics are fine. (Deferred to: same target as the first bullet above.)
- **Adding a `--allow-external-display` flag to the CLI.** Once the scrubber lands, the operator override is no longer needed for the display-text class, so a flag would be dead weight. (Deferred to: future spec if a different override class emerges.)
- **Re-running reconcile retroactively on all archived specs** to identify which historical handoffs had false-positive overrides applied. Forensically interesting but not load-bearing; archived specs are immutable and the handoffs already record the override. (Deferred to: a dashboard-style audit, not a code spec.)

## 6. Risks

- **Risk: the scrubber regex over-matches inside fenced code blocks.** A code block like ````python\n[a.py:1](b.py:2)\n```` (extremely unlikely in practice — markdown links don't render inside fenced code) would have its display text stripped by the scrubber. *Mitigation:* the regex only strips display text inside `[…](…)`; it does not delete the brackets or the line itself. Citations in fenced code that aren't inside `[…](…)` are untouched, which is the dominant case. If a spec author does write a literal `[a.py:1](b.py:2)` inside a fenced block, scrubbing the display text matches the intent of the rule (the href is the structurally authoritative location). No new failure mode.

- **Risk: a spec body uses `[…]` for non-link markdown idioms (e.g. footnotes `[1]`, callouts `[!NOTE]`)** that happen to wrap a path:line citation. *Mitigation:* the scrubber regex requires `[…]` to be immediately followed by `(…)`. Footnote and callout idioms are `[…]` without the following `(…)`, so they are untouched. Verified by a unit test in step 3 (positive — plain-prose citation still works) which exercises a body with no `(…)`.

- **Risk: a `path.ext:line` citation that legitimately lives in display text** because the author wanted a verbatim cosmetic display of the reference. *Mitigation:* the structurally correct authoring guidance after this fix is "the href is the citation; the display is cosmetic". The CLAUDE.md memory `cowork_channel_lives_outside_repo.md` already aligns with this — it directs authors to use `../cowork/full-path.md` as the canonical reference, which becomes the href. Specs authored before the memory landed will continue to work because the regex still extracts plain-prose citations and href citations; only display-text shadows are skipped. If a future authoring convention emerges that needs display-text citations to count, that convention warrants its own spec.

- **Risk: scrubbing increases reconcile latency on very large spec bodies.** *Mitigation:* the scrubber is a single regex pass over the body; reconcile.py is already O(body length) for the citation regex and existence checks. Doubling the regex passes (scrub then extract) is constant-factor slowdown on input sizes that are bounded by spec-body length (typically 5-30 KB). No measurable user-visible change in `/dev-next` step timings.

- **Risk: the antipodal-absence test in step 3 becomes brittle if the implementation is refactored.** *Mitigation:* the antipodal regex asserts a structural property (no direct `CITATION_RE.finditer(body)` call inside `_extract_citations`), not an exact line/whitespace shape. Any refactor that preserves "extract via the scrubber pipeline" passes; only a regression that reintroduces the pre-fix direct-finditer pattern fails. The test follows the convention from spec 0206 (UI test doctrine — source-pattern tests with antipodal-absence pairs); the same brittleness/robustness tradeoff applies here.

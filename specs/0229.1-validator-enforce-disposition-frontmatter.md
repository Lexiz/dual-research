# Spec 0229.1 — Validator: enforce `disposition:` + `disposition_reason:` frontmatter

> **Type:** new-feature  |  **Complexity:** S  |  **Depends on:** 0229 (carve-out-disposition convention shipped doctrinally; this spec is the validator wiring)
> **Bump:** MINOR — new required-frontmatter fields surface as new error classes from `validate_dev_spec` / `validate_draft`; observable behaviour change for queueing skills.
> **Evidence:** Spec 0229 §2.5 introduced the CLAUDE.md doctrine; spec 0229 §5 explicitly deferred validator enforcement: *"Validator enforcement of the new `disposition:` frontmatter field introduced doctrinally in §2.5. The CLAUDE.md rule lands here; the validator wiring is deferred to a follow-up dev spec carved against [scripts/spec_lifecycle/validator.py] the next time a carve-out is created. This is itself an instance of the convention being introduced."* Spec 0229 §7 R4 explicitly identified the no-enforcement state as the doctrinal-drift risk.

---

## 1. Context

Spec 0229 §2.5 codified the **carve-out-disposition convention**: every spec whose existence is a "noticed during implementation" follow-up must declare `disposition: ship | defer | archive` (default `archive`) and a one-sentence `disposition_reason:` in its frontmatter. Only `disposition: ship` reaches `/dev-next`; `defer` and `archive` are queued as records but skipped by the queue head. The convention shipped to [`CLAUDE.md`](CLAUDE.md) at lines 58-62 as a doctrinal rule, but the validator at [`scripts/spec_lifecycle/validator.py`](scripts/spec_lifecycle/validator.py) was deliberately deferred — spec 0229 §5 named that deferral as the first instance of the convention being applied to its own follow-up.

The deferral leaves the convention in the "recommendation, not rule" state spec 0229 §7 R4 flagged: *"A documented convention with no validator gate is a recommendation, not a rule."* The validator runs at the close of every `/spec-queue` and `/spec-promote` invocation (see [`scripts/spec_lifecycle/validator.py:120-241`](scripts/spec_lifecycle/validator.py:120) for `validate_dev_spec` and lines 400-416 for `validate_draft`); any frontmatter rule that isn't surfaced there silently allows omission. The validator wiring is therefore the only mechanism that converts the doctrinal rule into an enforced one. This spec is also itself the first follow-up authored under the new convention (the carve-out-of-a-carve-out test case spec 0229 §5 anticipates).

## 2. Proposed change

### 2.1 — Extend `DEV_REQUIRED_FRONTMATTER` and `DRAFT_REQUIRED_FRONTMATTER`

In [`scripts/spec_lifecycle/validator.py:29-40`](scripts/spec_lifecycle/validator.py:29), the two required-keys sets are defined as:

```python
DEV_REQUIRED_FRONTMATTER = {
    "kind", "spec", "slug", "title", "type", "label", "version_bump", "status",
}
DRAFT_REQUIRED_FRONTMATTER = {"kind", "draft_id", "slug", "title", "status"}
```

This spec adds `"disposition"` and `"disposition_reason"` to **both** sets. The CLAUDE.md doctrine names dev specs explicitly, but the parallel rule applies to drafts because a draft that fails to declare disposition will, on promotion, inherit the omission into its queued spec form. Catching the omission at draft time is cheaper than catching it at queue time. The frontmatter parser at [`scripts/spec_lifecycle/frontmatter.py`](scripts/spec_lifecycle/frontmatter.py) already returns arbitrary keys verbatim, so no parser change is needed.

### 2.2 — Add a value-shape check (`VALID_DISPOSITIONS`)

Add a module-level constant adjacent to `VALID_TYPES` and `VALID_STATUSES` at [`scripts/spec_lifecycle/validator.py:20-21`](scripts/spec_lifecycle/validator.py:20):

```python
# Spec 0229.1 §2.2 — disposition vocabulary per CLAUDE.md "Carve-out follow-ups
# must triage at carve-out time" (the §2.5 subsection introduced by spec 0229).
VALID_DISPOSITIONS = {"ship", "defer", "archive"}
```

Inside `validate_dev_spec` (around the existing `VALID_TYPES` check at [`validator.py:160-167`](scripts/spec_lifecycle/validator.py:160)), add:

```python
disposition = fm.get("disposition")
if disposition not in VALID_DISPOSITIONS:
    errors.append(
        f"frontmatter `disposition` must be one of {sorted(VALID_DISPOSITIONS)}, "
        f"got {disposition!r} — per CLAUDE.md \"Carve-out follow-ups must triage "
        f"at carve-out time\" (spec 0229 §2.5)."
    )

reason = fm.get("disposition_reason")
if not isinstance(reason, str) or not reason.strip():
    errors.append(
        "frontmatter `disposition_reason` must be a non-empty single-sentence "
        "string explaining the disposition choice (spec 0229 §2.5)."
    )
elif "." in reason and reason.count(".") > 2:
    # Heuristic: more than two sentences violates the "one-sentence" spec rule.
    warnings.append(
        "frontmatter `disposition_reason` appears to span more than one sentence "
        "— the convention is a one-sentence justification (spec 0229 §2.5)."
    )
```

Add the parallel check to `validate_draft` at [`validator.py:400-416`](scripts/spec_lifecycle/validator.py:400), reusing the same constant and error messages. The draft check uses identical wording so authors see the same gate at both lifecycle stages.

### 2.3 — Backfill existing queued specs

There are ~30 queued or in-flight dev specs in `specs/*.md` today, plus drafts under `specs/drafts/`. None of them declare `disposition:` (the convention shipped with spec 0229; spec 0230 + this spec are the first three to use it). Without backfill, the validator would retroactively reject the existing queue — every spec, including those already validated and merged, would fail re-validation.

The backfill is mechanical: every existing spec gets `disposition: archive` + a one-sentence reason of the form `"Pre-spec-0229 carve-out; disposition assigned retroactively to satisfy the new convention."`. The `archive` choice is intentional — these specs predate the convention, so triage is impossible to reconstruct; archiving them under the new rule preserves the queue-state semantics (`/dev-next` already filters by spec lifecycle, not by disposition; only future picks consult disposition).

The backfill script is a one-off CLI in [`scripts/spec_lifecycle/backfill_disposition.py`](scripts/spec_lifecycle/backfill_disposition.py) (new file) that:

1. Walks every `*.md` under `specs/` and `specs/drafts/`.
2. Parses frontmatter; skips files whose frontmatter already contains `disposition`.
3. For files missing the field, inserts `disposition: archive` and `disposition_reason: "Pre-spec-0229 carve-out; disposition assigned retroactively to satisfy the new convention."` between `status:` and the closing `---`.
4. Prints a summary `"backfilled N files (M skipped — already had disposition)"`.

The script is run once during this spec's implementation; the result is committed to main as part of the PR. The script remains in-tree for any future audit pass but has no further runtime role.

### 2.4 — `/dev-next` queue-head consumes `disposition`

This change does NOT touch `/dev-next` itself — the skill at [`~/.claude/skills/dev-next/SKILL.md`](~/.claude/skills/dev-next/SKILL.md) (out of repo) will read the new field after `current_queue()` in [`scripts/spec_lifecycle/pick_next_number.py:131-160`](scripts/spec_lifecycle/pick_next_number.py:131) returns it. The current `current_queue` already returns full `(spec_id, frontmatter)` tuples, so the frontmatter dict will naturally contain `disposition:` post-backfill. The skill is updated in a separate pass once this validator wiring lands and the queue is backfilled.

Per CLAUDE.md the queue head consults `disposition: ship` only; the data is already in the frontmatter dict the skill receives. No code change to `pick_next_number.py` is needed for this spec; that's a `/dev-next` SKILL.md change that happens after this lands.

Splitting these two is intentional — the SKILL.md change requires testing against a queue that has `disposition` populated, which only exists after this spec ships. Deferred to a follow-up edit of [`~/.claude/skills/dev-next/SKILL.md`](~/.claude/skills/dev-next/SKILL.md) (out-of-repo file; no spec needed for that change, it's a skill-only edit per the standing two-worktree split).
- **Updating `/spec-queue`, `/spec-promote`, `/spec-draft` skills to prompt for `disposition`.** Same reasoning — the validator catches the omission, but a UX improvement would interactively prompt at queue time. Deferred to the next iteration on those skills (out-of-repo SKILL.md files).
- **Updating templates under `specs/_templates/*.md`** to include `disposition:` placeholders. The five templates (`new-feature.md`, `bug.md`, `refactoring.md`, `test.md`, `breaking.md`) all lack the field. Deferred to a separate `refactoring` spec that touches all five templates as a single migration. The validator failure surface is the enforcement mechanism in the interim — authors who use the template verbatim get a clear error pointing at the missing field. Templates updated in spec 0229.X (next decimal carve-out of this spec, if needed).
- **A `disposition_reason` length cap or grammar check beyond "non-empty single sentence."** The heuristic in §2.2 (more than two periods = multiple sentences) is the only check. Stricter natural-language validation is out of scope.
- **Backfilling archived specs under `specs/archive/`.** Archived specs are immutable historical record and not consulted by the validator at queue time. Backfilling them would touch files outside the validator's working set. Deferred — if archived specs ever need re-validation, that's a separate spec.

## 7. Risks

- **R1 — Backfill changes ~30 spec files in one commit; merge conflicts likely if other authoring sessions are mid-flight.** *Mitigation:* the backfill is a single deterministic pass — running it on any rebase regenerates the same output bytes. The frontmatter insertion is field-order-preserving (per `frontmatter.py`'s round-trip semantics). Any conflict is mechanical (a different spec also touching the same file), resolved by re-running the backfill post-merge.
- **R2 — The `disposition_reason` "single sentence" heuristic produces false positives.** A reason like `"Fixes the false-positive class observed in specs 0227.1 + 0229 (cf. the e.g. clause)."` triggers the >2-periods warning despite being one English sentence (period inside `e.g.` and at end). *Mitigation:* the check is a warning, not an error. Authors can see the warning and ignore if the wording is correct. A stricter natural-language check is out of scope per §5.
- **R3 — Pre-existing specs flagged as `disposition: archive` by the backfill clutter the queue dashboard.** *Mitigation:* `archive` is the default per CLAUDE.md and represents the no-triage state. The dashboard renderer at [`scripts/spec_lifecycle/render_dashboard.py`](scripts/spec_lifecycle/render_dashboard.py) does not currently surface `disposition` — adding a column or filter is a future dashboard spec. In the interim, the queue-head `/dev-next` filter is the only consumer that cares, and it only picks `disposition: ship` going forward.
- **R4 — The validator passes a spec with `disposition: ship` but no concrete reason ("ship — it's important.").** *Mitigation:* the non-empty check catches blanks; quality of reasoning is human-review territory, not validator territory. The CLAUDE.md doctrine names the rationale; the validator enforces the shape. Reviewers and `/spec-queue` reviewers see the reason verbatim and can push back.
- **R5 — This spec is the convention's first test case and will be the canonical example.** A poor disposition declaration here cascades through every future carve-out. *Mitigation:* this spec's own frontmatter declares `disposition: ship` with the rationale "self-test for the carve-out-disposition convention" — explicitly aligning with spec 0229 §7 R4's framing of "the wiring spec is the first follow-up under the new convention, which makes it the test case for itself."

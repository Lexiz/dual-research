# Spec 0253.1 — Fix: supabase detail path lacks the zero-event creation-time floor the list path now has

> **Type:** bug  |  **Severity:** P3  |  **Affects:** supabase-backed (hosted `dual-research-alex.fly.dev`) run-detail page; only for a run that never emitted a valid event. Carved out of [spec 0253](0253-fix-all-runs-card-status-diverges-from-detail.md) §3.2 during implementation.
> **Bump:** PATCH — bug fix.
> **Evidence:** No live occurrence. Identified by reasoning during the spec 0253 implementation cycle; recorded in the spec 0253 handoff "Deferred during implementation" section ([handoffs/2026-05-29-spec-0253-fix-all-runs-card-status-diverges-from-detail.md](../handoffs/2026-05-29-spec-0253-fix-all-runs-card-status-diverges-from-detail.md)). Live SQL during 0253 confirmed every active run in `runs_active` carries events, so the divergent code path is not reachable with current data.

---

## 1. Reproduction

**Environment:** Hosted UI at `dual-research-alex.fly.dev` (supabase backend mode). Requires a `runs` row that is older than `RUN_STALE_THRESHOLD_MINUTES` ([src/dual_research/ui/labels.py:21](../src/dual_research/ui/labels.py:21)), carries no terminal event (`exit_code IS NULL`), and has **zero** rows in the `events` table — a run that was created but never emitted a single valid event before dying.

**Steps:**

1. Create a `runs` row whose `created_at` is more than 30 minutes old, with `exit_code IS NULL` and **no** `events` rows for that `run_id`.
2. Open the All-Runs home page and read the card's status badge / lane.
3. Click into the run's detail page and read its status.

**Expected:** The card status badge and lane match the detail page — both report `abandoned` (the run was created long ago and never produced activity). This is the exact list/detail parity invariant spec 0253 established.

**Actual:** The list path reads `abandoned` (spec 0253 §3.1 added a `created_at` fallback for the zero-events case), but the supabase detail page reads `running` — a residual list/detail divergence of the exact class spec 0253 set out to remove.

## 2. Root cause hypothesis

Spec 0253 made every status path feed `derive_run_status` the same authoritative "last event timestamp" semantics, and gave the **supabase list** path a creation-time floor for the zero-event case: `_supabase_list_runs` now passes `max_event_ts.get(id) or created_at` as `last_event_at`, so a never-emitted old row reads `abandoned` rather than `running` (spec 0253 §3.1).

The **supabase detail** path got no equivalent floor:

- The detail page materializes the run into a tmp dir and replays it: `_materialize_snapshot_supabase` → `SupabaseSessionData.materialize()` → `load_run_snapshot` ([src/dual_research/ui/server.py:1736](../src/dual_research/ui/server.py:1736); [src/dual_research/ui/server.py:1753](../src/dual_research/ui/server.py:1753)).
- `last_event_at` is set **only** from replayed events, in `apply_event` ([src/dual_research/ui/aggregator.py:251](../src/dual_research/ui/aggregator.py:251)): `run._terminal_signals.last_event_at = ts`. With zero valid events it is never assigned and stays `None`.
- `derive_run_status`'s staleness rule is skipped when `last_event_at is None`, falling through to `running` ([src/dual_research/ui/labels.py:164](../src/dual_research/ui/labels.py:164), established in the spec 0253 root-cause table).
- The dir-name creation-time fallback (`_earliest_known_ts`, [src/dual_research/ui/aggregator.py:1265](../src/dual_research/ui/aggregator.py:1265)) cannot rescue the supabase case: it parses a `YYYYMMDD-HHMMSS` prefix from the session-dir name via `_SESSION_DIR_TS_RE`, but the materialized tmp dir is named `dr-<run_id>-…` ([src/dual_research/ui/datasource.py:66](../src/dual_research/ui/datasource.py:66): `prefix=f"dr-{self._run_id}-"`), which that regex does not match. So even the creation-time floor that protects the filesystem detail path is dead on the supabase detail path.

Net: a zero-event old supabase row reads `abandoned` on the list and `running` on the detail page. The run's `created_at` is never threaded into the materialization, so the detail path has no creation-time floor symmetric with the list path's spec 0253 §3.1 fallback.

**Not reachable with current data.** Live SQL during the spec 0253 cycle confirmed every active run in `runs_active` has at least one `events` row, so the zero-event branch never fires and the divergence is latent. This is why the spec is `parked` with disposition `archive`.

## 3. Fix

Give the supabase detail path the same creation-time floor the list path got in spec 0253 §3.1, so a zero-event old run reads `abandoned` on both surfaces. Two equivalent implementation options — pick at implementation time; both confine the change to the materialization seam and leave `derive_run_status` and the threshold untouched:

**Option A — thread `created_at` into materialization (preferred).** Pass the run's `created_at` from `_materialize_snapshot_supabase` into `SupabaseSessionData` ([src/dual_research/ui/datasource.py:51](../src/dual_research/ui/datasource.py:51)). After `load_run_snapshot` ([src/dual_research/ui/aggregator.py:82](../src/dual_research/ui/aggregator.py:82)) replays the (empty) transcript, if `run._terminal_signals.last_event_at` is `None`, seed it from `created_at` before `_finalise_status` ([src/dual_research/ui/aggregator.py:1131](../src/dual_research/ui/aggregator.py:1131)) runs. This mirrors the list path's `max_event_ts.get(id) or created_at` exactly: the creation time is the floor only when no event ts exists.

**Option B — seed the tmp-dir name with the run-id timestamp prefix.** Change `SupabaseSessionData.materialize`'s `prefix=f"dr-{self._run_id}-"` ([src/dual_research/ui/datasource.py:66](../src/dual_research/ui/datasource.py:66)) so the materialized dir name carries the run id's leading `YYYYMMDD-HHMMSS` prefix in a form `_SESSION_DIR_TS_RE` matches. Then the existing `_earliest_known_ts` dir-name fallback ([src/dual_research/ui/aggregator.py:1289](../src/dual_research/ui/aggregator.py:1289)) fires for the supabase detail path the same way it does for the filesystem detail path, and no new plumbing into `apply_event` / `_finalise_status` is needed.

Option A is preferred because it threads the authoritative `created_at` column rather than relying on the run id's embedded timestamp; the run id prefix is a creation-time proxy, `created_at` is the creation time. Either way the list and supabase detail then agree for the zero-event old-row case.

`derive_run_status`, `RUN_STALE_THRESHOLD_MINUTES`, and the list-path change from spec 0253 are all unchanged — this spec only adds the symmetric creation-time floor on the supabase detail materialization seam.

## 4. User stories & acceptance criteria

> As a `viewer`, I want a zero-event old run's status badge on the All-Runs home page to match its detail page, so that the parity guarantee spec 0253 established holds for the edge case too, not just for runs that emitted events.

> As a `researcher`, I want a run that was created but never emitted an event to read `abandoned` on both the list and the detail page once it is older than the staleness threshold, so that a dead-on-arrival run is not reported as in flight.

### 4.2 — Acceptance scenarios (BDD)

> **Scenario 1:** zero-event old supabase run reads abandoned on both surfaces
> GIVEN a supabase `runs` row with `exit_code IS NULL`, a `created_at` more than `RUN_STALE_THRESHOLD_MINUTES` old, and zero rows in the `events` table for that `run_id`
> WHEN the All-Runs home page list is fetched and the same run's detail page is materialized via `_materialize_snapshot_supabase`
> THEN both report status `abandoned` and the run does not appear in the RUNNING lane or the in-flight tally.

> **Scenario 2:** supabase run with events is unaffected
> GIVEN a supabase `runs` row that has at least one recent `events` row and `exit_code IS NULL`
> WHEN the All-Runs home page list is fetched and the same run's detail page is materialized
> THEN both report status `running`, the creation-time floor is not consulted, and behaviour is identical to spec 0253.

## 5. Regression-prevention test

Follows spec 0238 live-failure discipline (exercise the *real* detail entry point — `_materialize_snapshot_supabase` → `load_run_snapshot` — against a captured-shape artifact, not a helper-level unit) and spec 0206 source-pattern doctrine (pure stdlib, no Playwright / `tests/ui/`).

- [ ] Test: supabase detail zero-event parity — feed `_materialize_snapshot_supabase` (or its `SupabaseSessionData` + `load_run_snapshot` pipeline) a fake supabase client whose `runs` row has `created_at` > 30 min old, `exit_code` null, and **no** `events` rows, and assert the detail status equals the `_supabase_list_runs` status equals `abandoned`. Fails before this fix (detail returns `running` because `last_event_at` stays `None` and the tmp-dir name does not match `_SESSION_DIR_TS_RE`); passes after (creation-time floor fires).
- [ ] Test: supabase detail with-events unaffected — same pipeline with one recent `events` row reads `running` on both list and detail, locking that the floor is consulted only when no event ts exists (no false-abandoned regression).

## 6. Blast radius

The change is confined to the supabase materialization seam: `_materialize_snapshot_supabase` ([src/dual_research/ui/server.py:1736](../src/dual_research/ui/server.py:1736)) and `SupabaseSessionData.materialize` ([src/dual_research/ui/datasource.py:59](../src/dual_research/ui/datasource.py:59)) under Option A, or only the tmp-dir `prefix` string under Option B. `derive_run_status`, the staleness threshold, the spec 0253 list-path `created_at` fallback, and the filesystem detail path are all untouched. The new floor fires **only** when no event ts exists, so every run that emitted at least one event — i.e. every run with current data — takes the identical pre-fix code path. The filesystem detail path already has this floor via `_earliest_known_ts`'s dir-name match, so this spec only brings the supabase detail path to parity with it.

## 7. Out of scope

This spec does NOT touch any file under `src/dual_research/ui/static/` or `design-system/` — no DS primitive, no badge/lane styling change. The only behaviour change is which status a zero-event old supabase run derives on the detail page.

- Persisting a dedicated `last_event_at` column on the `runs` row — already deferred by spec 0253 §7; orthogonal to this floor.
- Changing `RUN_STALE_THRESHOLD_MINUTES` or adding per-phase staleness thresholds — out of scope, unchanged from spec 0253.

## 8. Risks

- **Reachability.** The divergent branch is unreachable with current data (every active run has events), so this fix is defensive. Parked with disposition `archive`; promote to `ship` only if a zero-event row is observed in `runs_active` or if the materialization path is touched for another reason — at which point the symmetric floor should land alongside that change rather than as a standalone cycle.
- **created_at availability.** Option A assumes `created_at` is present and parseable on every `runs` row. If a row lacks it, the floor cannot fire and the detail path falls through to `running` exactly as today — strictly no worse than the current behaviour, and the list path shares the same dependency from spec 0253 §3.1.
- **Floor must be no-op when events exist.** The seed must apply only when `last_event_at is None` after replay; seeding it unconditionally would override a real event ts with the (older) creation time and could wrongly flip a healthy run to `abandoned`. The §5 with-events test locks this.

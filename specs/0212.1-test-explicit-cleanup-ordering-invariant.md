# Spec 0212.1 — Tests: lock the spec 0212 explicit-cleanup ordering invariant

## 1. Coverage gap

Spec 0212 ships [tests/test_spec_0212_post_merge_doctrine.py](tests/test_spec_0212_post_merge_doctrine.py) with six assertions on `~/.claude/skills/dev-next/SKILL.md` step 19/20. Two of them lock the *presence* of the explicit-cleanup primitives in step 19:

- [tests/test_spec_0212_post_merge_doctrine.py:81](tests/test_spec_0212_post_merge_doctrine.py:81) — `test_step_19_has_squash_merge_and_explicit_delete` asserts step 19 contains both `gh pr merge --admin --squash` AND `git push origin --delete`.
- [tests/test_spec_0212_post_merge_doctrine.py:67](tests/test_spec_0212_post_merge_doctrine.py:67) — `test_step_19_drops_delete_branch_flag` asserts step 19 does NOT contain `--delete-branch`.

But neither test asserts the **ordering** of `git checkout --detach -f origin/main` relative to `git branch -D "$BRANCH"` inside step 19's explicit-cleanup block. The cycle that shipped spec 0212 discovered live that the ordering is load-bearing: with the detach AFTER the by-name delete, `git branch -D` fails because the queue worktree at `/Users/alexlisitzky/dual-research/` is still checked out on `$BRANCH`. The implementer fixed `~/.claude/skills/dev-next/SKILL.md` inline (the detach now precedes the deletes) — see [`~/.claude/skills/dev-next/SKILL.md`](~/.claude/skills/dev-next/SKILL.md) step 19's cleanup block (the lines containing `git checkout --detach -f origin/main` and `git branch -D "$BRANCH"`). The skill body fix is correct; the regression vector is a future re-shuffle of step 19 that silently re-introduces the bug by moving the detach back after the delete (or removing it). Nothing in the existing test suite catches that.

Two un-covered surfaces in step 19's cleanup block:

- **Ordering: detach-before-delete.** The first `git checkout --detach` line index inside step 19 must be strictly less than the first `git branch -D "$BRANCH"` line index. Not asserted today.
- **Presence: re-detach line itself.** Spec 0212 §2a folded the spec-0210 standalone re-detach step INTO the cleanup block. The 0212 test suite never asserted the re-detach's *presence* at all (the standalone-step removal note at [`~/.claude/skills/dev-next/SKILL.md`](~/.claude/skills/dev-next/SKILL.md) step 19 — the parenthetical sentence about the standalone re-detach being folded in as of spec 0212 — makes the re-detach inside step 19 the only re-detach in the post-merge sequence). A future spec that drops the line altogether would pass the existing 0212 tests but break the spec-0210 baseline-pose invariant AND re-introduce the `git branch -D` collision.

## 2. Test approach

A single new test function added to the existing [tests/test_spec_0212_post_merge_doctrine.py](tests/test_spec_0212_post_merge_doctrine.py) file. Pure stdlib, same `_step_block(body, 19)` helper as the existing assertions at [tests/test_spec_0212_post_merge_doctrine.py:31](tests/test_spec_0212_post_merge_doctrine.py:31)–`:64`. SKIP when SKILL.md is absent (same `_skill_body()` early-skip at [tests/test_spec_0212_post_merge_doctrine.py:36](tests/test_spec_0212_post_merge_doctrine.py:36)–`:39`).

### 2.1 — Ordering assertion

New test function `test_step_19_re_detach_precedes_branch_delete`:

- Calls `_step_block(body, 19)` to scope to step 19's body (per the existing helper's semantics, sub-blocks indented by 4 spaces stay attached to their parent step — so the cleanup code-fence is included).
- Searches for the first match of `re.compile(r"git\s+checkout\s+--detach")` and records its line index inside the step block.
- Searches for the first match of `re.compile(r'git\s+branch\s+-D\s+"\$BRANCH"')` and records its line index inside the step block.
- Asserts both matches exist (presence) AND `detach_line_idx < delete_line_idx` (ordering).

Co-locating with the existing file is deliberate — every spec-0212 SKILL.md assertion lives in one file; the ordering invariant is logically a continuation of the post-merge doctrine, not a separate concern. The new function follows the same naming convention as the five existing `test_step_*` functions.

### 2.2 — Optional follow-up (out of scope here)

A test that asserts the re-detach line appears EXACTLY ONCE in the entire SKILL.md body (not just in step 19), to guard against a future spec accidentally duplicating the standalone-re-detach step that 0212 retired. Deferred — the current concern is the in-step-19 ordering; a global presence check has a different failure shape and would be a separate test in a separate spec if a duplication regression surfaces.

## 3. What it would catch

- **The exact bug live-discovered during the spec 0212 cycle.** Per [handoffs/2026-05-25-spec-0212-gh-pr-merge-delete-branch-author-worktree-collision.md:29](handoffs/2026-05-25-spec-0212-gh-pr-merge-delete-branch-author-worktree-collision.md:29): the cleanup block as originally written (detach AFTER delete) failed at first execution because `git branch -D` on the currently-checked-out branch is refused by git. If a future spec re-shuffles step 19 — for example by moving the verified-delete retry into the explicit-cleanup block, or by adding a new pre-delete step that re-attaches to `$BRANCH` — the ordering test catches the regression at the SKILL.md level before the cycle ever executes it.
- **Silent removal of the re-detach line.** If a future spec believes the queue worktree is already detached by step 19's time and drops the `git checkout --detach -f origin/main` line, the ordering test fails on the presence half (no detach match found). This is the more insidious regression vector — the change would *look* like a cleanup, but the spec-0210 baseline-pose contract relies on this re-detach happening in the explicit-cleanup block per the parenthetical note at the end of step 19.
- **Re-introduction of the `--delete-branch` flag** is already caught by the existing [tests/test_spec_0212_post_merge_doctrine.py:67](tests/test_spec_0212_post_merge_doctrine.py:67) assertion; this spec is orthogonal — it locks the ordering of the *explicit* cleanup that replaces the composite call.

The historical class of failure mode this prevents: the spec-0212 cycle shipped successfully despite the ordering bug only because the operator could recover inline (force-detach the worktree, re-run `git branch -D`). A re-shuffle that lands without an operator in the loop (e.g., during a `/dev-queue-run` drain) would halt the queue at step 19 with no automatic recovery path. The test makes the ordering legible to source-pattern review and to CI.

## 4. Risks

- **False positive on a legitimate re-shuffle that splits the cleanup across blocks.** If a future spec intentionally moves the re-detach out of step 19's cleanup block (back to a separate standalone step before step 19), the ordering test fails. Mitigation: the failure surfaces the intent shift at PR time; the author updates the test in the same PR (the same way spec 0212 updated [tests/test_spec_0212_post_merge_doctrine.py](tests/test_spec_0212_post_merge_doctrine.py) when it landed the new step 19 shape). Spec-paired test edits are already the doctrine for source-pattern tests in this repo.
- **Brittleness to comment-line drift.** The `_step_block` helper at [tests/test_spec_0212_post_merge_doctrine.py:31](tests/test_spec_0212_post_merge_doctrine.py:31) operates on raw text and counts every newline as a line. A future edit that adds explanatory comments BETWEEN the detach and delete lines does NOT break the ordering test — the first-match line indexes still satisfy `detach_idx < delete_idx`. The test is robust to additive prose changes.
- **Brittleness to multi-line bash continuations.** If a future spec joins the detach call onto a previous line with `\` continuation, the line index of the regex match may shift. Mitigation: the test uses `re.search` on individual lines (splitting `block` by `\n` first), so a continuation that puts `git checkout --detach` on the same physical line as the preceding command would still match at that line's index. Acceptable.
- **Slow test runs.** One additional pure-stdlib regex scan against a ~30-line block. Sub-millisecond impact on the existing 1915-test suite (per the spec 0212 handoff). No flakiness risk — input is deterministic.
- **Over-mocking risk.** The test operates on the real `~/.claude/skills/dev-next/SKILL.md` file via `_skill_body()` (no fixture, no stub). When SKILL.md is absent (CI), the test SKIPs per the existing pattern — explicit skip, not silent pass. No mocking surface.
- **Test added in isolation, no SKILL.md change paired with it.** This spec is test-only (PATCH bump, no version-bump-able runtime change). The SKILL.md fix already landed inline during the spec 0212 cycle (per the handoff's Cycle observations). The test locks that fix; it does not re-fix anything. Verified by running `uv run pytest tests/test_spec_0212_post_merge_doctrine.py -v` and confirming the new assertion passes against the current SKILL.md without any SKILL.md edits in this PR.

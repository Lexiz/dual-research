# Spec 0252.2 — Fix: `backfill-critique --push` times out re-uploading whole session; push metrics-only

> **Type:** bug  |  **Severity:** P1  |  **Affects:** `dual-research backfill-critique --push` (shipped spec 0252 §2.1, v1.63.0); large runs only
> **Bump:** PATCH — bug fix
> **Evidence:** Captured `backfill-critique --all --push` failure (Supabase `57014` statement timeout, reproduced below). Depends on 0252 (the command this fixes).

---

## 1. Reproduction

**Environment:** `dual-research backfill-critique --all --push` against the deployed Supabase project; runs dir carrying both small (≤ ~140 events) and large (`backend-language-choice`) runs.

**Steps:**
1. Run `dual-research backfill-critique --all --push` (the spec 0252 §2.1 command that repairs `critique_by_agent` in `metrics.json` and re-pushes so the **deployed** All Runs cards repair).
2. The `--push` block at [`src/dual_research/cli.py:757`](src/dual_research/cli.py) calls `remote.push_session_dir(session_dir)` for each repaired run.
3. `push_session_dir` upserts the `runs` row, then re-uploads **all** events, `session_files`, `attachment_blobs`, and `turn_prompt_pieces` ([`src/dual_research/persistence/remote.py:108`](src/dual_research/persistence/remote.py)–`:149`).

**Expected:** Every repaired run's deployed card picks up the backfilled `critique_by_agent` tally — the push touches only the data the badges read (`runs.metrics`).

**Actual:** Large runs fail on the events/files re-upload with a Supabase statement timeout; the command emits `[push error]` and the operator cannot tell from the exit whether the metrics landed:

```
[push error] 20260518-065852-backend-language-choice-briefing-for-dual-research: APIError: {'message': 'canceling statement due to statement timeout', 'code': '57014', ...}
[push error] 20260518-083618-backend-language-choice: APIError: {'message': 'canceling statement due to statement timeout', 'code': '57014', ...}
```

Smaller runs pushed fine; only the large `backend-language-choice` runs timed out on the heavy batches.

## 2. Root cause hypothesis

`backfill-critique --push` reuses the full-session push path for what is a single-column repair. `push_session_dir` upserts the `runs` row as its own autocommitted statement at [`src/dual_research/persistence/remote.py:105`](src/dual_research/persistence/remote.py), then runs four heavy batched re-uploads — events, `session_files`, `attachment_blobs`, `turn_prompt_pieces` — at [`src/dual_research/persistence/remote.py:108`](src/dual_research/persistence/remote.py)–`:149`. On large runs those batches exceed Supabase's statement timeout (`57014`).

The backfill only mutates `critique_by_agent` **inside** the `metrics` dict — it touches no events, files, blobs, or pieces. So the entire heavy tail of `push_session_dir` is wasted work for this command, and it is the part that times out.

Mitigating detail (explains why badges still mostly landed, **not** the fix): the `runs` row carrying the `metrics` JSONB the badges read is upserted **first**, before the heavy batches. On runs where the `runs` upsert committed before the timeout, metrics actually landed despite the `[push error]`. The fix removes the dependence on that ordering accident.

## 3. Fix

1. **New method `RemoteSession.push_metrics_only(session_dir: Path)`** in [`src/dual_research/persistence/remote.py`](src/dual_research/persistence/remote.py). Reads `session_dir/metrics.json`, derives `run_id = session_dir.name` (matching `push_session_dir`'s `run_id` derivation at [`src/dual_research/persistence/remote.py:74`](src/dual_research/persistence/remote.py)), and issues a **single-row update of only the `runs.metrics` column**:

   ```python
   self._client.table("runs").update({"metrics": metrics}).eq("id", run_id).execute()
   ```

   No `events` / `session_files` / `attachment_blobs` / `turn_prompt_pieces` writes. Raises `FileNotFoundError` if `metrics.json` is absent (a metrics-only push with no metrics is meaningless). Returns a small summary (e.g. a frozen dataclass `MetricsPushSummary(run_id: str, ok: bool)` or a reuse of `PushSummary` with the heavy counts zeroed) so the CLI can keep its `[pushed]` reporting.

2. **Rewire the `--push` block in `_run_backfill_critique`** ([`src/dual_research/cli.py:752`](src/dual_research/cli.py)–`:764`) to call `push_metrics_only` instead of `push_session_dir`. Keep the per-run `try/except` and the `[pushed]` / `[push error]` reporting; adapt the success line to the metrics-only summary (drop the now-meaningless `events=` / `files=` counters, print `run_id` + `ok`).

**Provably sufficient for `backfill-critique` specifically.** The backfill mutates only `critique_by_agent` inside the metrics dict; recompute is deterministic and the cost/token totals do not move, so the derived `runs` columns built in `_build_run_row` ([`src/dual_research/persistence/remote.py:182`](src/dual_research/persistence/remote.py)) — cost, duration, etc. — are unchanged. A metrics-only column update leaves no derived column stale. The hosted list path reads critique from this exact column: the backend FastAPI list endpoint `_supabase_list_runs` → `derive_agent_breakdowns(r.get("metrics") or {})` at `server.py:1151`.

## 5. Regression-prevention test

Honors spec 0238 live-failure discipline — the test exercises the **real entry point** of the captured `57014`-on-`push_session_dir` call path, not a helper in isolation.

- [ ] **Test (real entry point):** drive the `backfill-critique --push` path (or `push_metrics_only` directly at its CLI call site) against a fixture run with a mocked Supabase client. Assert it issues an `update` on `table("runs")` filtered to the run id via `.eq("id", <run_id>)`, AND that `table("events")`, `table("session_files")`, `table("attachment_blobs")`, and `table("turn_prompt_pieces")` are **never** touched. This hits the exact call site that emitted the captured `57014`, per spec 0238 — fails before the fix (full re-push touches all five tables), passes after.
- [ ] **Test (payload fidelity):** assert the metrics payload sent in the `update` equals the run's `metrics.json` contents verbatim, including the populated `critique_by_agent` sub-dict — so the deployed card reads exactly what the backfill wrote.
- [ ] **Harness note:** the existing fake client in [`tests/persistence/test_remote.py:54`](tests/persistence/test_remote.py) (`FakeSupabaseClient`) supports only `upsert`; the new test extends it (or adds a sibling fake) to record the `update().eq().execute()` chain and to assert table-touch absence. Pure stdlib, in-memory — no live Supabase.

## 6. Blast radius

- **Only `_run_backfill_critique`'s `--push` block changes call target.** `push_session_dir` itself is untouched and keeps all other callers: the orchestrator push-watch loop, the `recompute-costs --push` block ([`src/dual_research/cli.py:657`](src/dual_research/cli.py)), and the `--push` session-upload path at [`src/dual_research/cli.py:563`](src/dual_research/cli.py). None of those switch to the metrics-only method.
- **No derived-column staleness for this command** — argued in §3: backfill moves no cost/duration totals, so `_build_run_row`'s derived columns stay correct without a full re-push.
- **Hosted read path is satisfied** — the badges read `runs.metrics` (`server.py:1151`), which is exactly the column the new method writes.

## 7. Out of scope

- **`recompute-costs --push` is NOT folded into this fix.** The block at [`src/dual_research/cli.py:657`](src/dual_research/cli.py) has the **identical** heavy-push-timeout shape, BUT recompute changes cost/duration totals that feed derived `runs` columns the card displays (cost, duration — built in `_build_run_row`). A metrics-only update there would leave those derived columns stale. Correct treatment for recompute is its own follow-up: a metrics-only path **plus** a derived-column refresh. Recorded here as a known adjacent risk; **deferred to a follow-up dev spec to be drafted post-merge** — do not extend `push_metrics_only` to recompute without that refresh.
- **No change to the on-disk `metrics.json` rewrite** — that already works; this spec only changes how the repaired metrics reach Supabase.
- **No UI / design-system changes**, so no DS citations are required.

## 8. Risks

- **`metrics.json` absent for a repaired run.** Mitigated: `_run_backfill_critique` already gates the per-run push on `r.metrics_written` ([`src/dual_research/cli.py:753`](src/dual_research/cli.py)), and `push_metrics_only` raises `FileNotFoundError` defensively; the existing per-run `try/except` turns either into a reported `[push error]` rather than a crash.
- **Run row does not yet exist (`update` matches zero rows).** Low for backfill — these are existing, previously-pushed runs (the whole point is repairing already-deployed cards). An `update` against a missing id is a no-op, not an error; if a never-pushed run is ever backfilled, its card simply stays absent until a normal `push_session_dir` runs, which is acceptable and matches today's "metrics-only is for repair" intent. Noted, not gated.
- **Supabase client `.update().eq()` chain shape drift.** The supabase-py builder API is stable for `table().update().eq().execute()`; the method mirrors the existing `table().upsert().execute()` usage one line away. The fake-client test locks the chain shape so an API change surfaces in CI.

# Spec 0205.1 — ItemCard 8-capture parity grid refresh + retroactive attachment

> **Type:** test  |  **Complexity:** M  |  **Depends on:** 0205
> **Bump:** PATCH — assets + docs only, no runtime code change
> **Evidence:** spec 0205's PR (https://github.com/Lexiz/dual-research/pull/235) included only a single-frame post-fix screenshot, not the 4-kinds × 2-states grid mandated by `design-system/SPEC.md:378` (spec 0179 ItemCard parity verification). The handoff explicitly flagged the deferral at `handoffs/2026-05-24-spec-0205-fix-p4-critique-card-five-visual-regressions.md:47` and noted the reference shots themselves predate spec 0203's head rewrite + spec 0205's body reordering — so a faithful grid needs refreshed references OR an explicit anatomy-departure note.

## 1. Coverage gap

The "ItemCard parity verification" rule at `design-system/SPEC.md:378` requires every PR touching `ItemCard` / its per-kind sub-renderers / `.item-card__*` CSS chrome to embed a side-by-side image grid comparing the live-app rendering to four reference screenshots:

- `design-system/notion-issues/screenshots/07-question-card-duplicate.png`
- `design-system/notion-issues/screenshots/08-disagreement-card.png`
- `design-system/notion-issues/screenshots/09-issue-card.png`
- `design-system/notion-issues/screenshots/10-comments-card.png`

Each PR is expected to ship **eight fresh captures** (4 kinds × 2 states — collapsed + expanded) placed next to the four reference shots. The DS prose at `design-system/SPEC.md:378` calls out the chronic failure mode the rule catches: specs 0138 / 0141 / 0144 / 0151 cited the references in prose but didn't verify the rendered output, and visual regressions slipped through.

**Spec 0205 owed this grid and didn't ship it.** The merged PR's description embedded a single-frame post-fix screenshot of the kind chip row + a Claude-headed Issue card body with lifecycle leading — useful evidence but not the 8-capture grid the rule mandates. The handoff (`handoffs/2026-05-24-spec-0205-fix-p4-critique-card-five-visual-regressions.md:47`) names this as one of three deferred items.

Compounding the gap: the four reference shots predate the recent anatomy changes:

- **Spec 0203** rewrote the ItemCard head (kind chip primitive, raiser chip ordering, sources chip glyph) — the head in the references is the pre-0203 head.
- **Spec 0205 Bug 2** reordered Issue and Comment bodies so lifecycle leads (was: standalone `<Markdown text={item.body}/>` block above lifecycle; is: lifecycle first, inline anchor blockquote below). The expanded-state shape in the references shows the pre-0205 ordering for Issue + Comment kinds. Confirmed at `handoffs/2026-05-24-spec-0205-fix-p4-critique-card-five-visual-regressions.md:14` ("`ItemCardIssueBody` / `ItemCardCommentBody` stripped the standalone `<Markdown text={String(item.body)}/>` block above the lifecycle").
- **Spec 0205 Bug 1** restructured the expanded `SourceRow` (label · value rows + tinted `<blockquote>` excerpt) — references show the pre-0205 inline-spans + `<pre>` excerpt shape.

A faithful side-by-side grid produced today against the four pre-0203 / pre-0205 references would over-flag the intentional anatomy departures as "regressions." That's the second failure mode this spec closes.

Touch surfaces (for parity-grid context — no source code changes in this spec):

- `src/dual_research/ui/static/run-detail.jsx:1849` — head raiser chip resolution post-spec-0205 (the head anatomy the grid captures).
- `src/dual_research/ui/static/run-detail.jsx` — the four per-kind body sub-renderers (`ItemCardDQBody`, `ItemCardIssueBody`, `ItemCardCommentBody`, plus the Question kind that flows through `ItemCardDQBody`).
- `src/dual_research/ui/static/components.css:2305` — legacy `.kind-tab` rules (still live; cleanup is spec 0205.2's scope, not this one).
- `design-system/assets/styles/composed-components.css:740` — same legacy rules in the canonical DS file.

## 2. Test approach

Two parallel deliverables — both no-code, both shipped together so the parity grid lands at the same time as its updated reference baseline.

### 2.1 Refresh the four ItemCard reference screenshots

Replace the four reference shots under `design-system/notion-issues/screenshots/` with fresh captures from the live app (`https://dual-research-alex.fly.dev/` after v1.44.2 deploy — the post-spec-0205 anatomy):

- `07-question-card-duplicate.png` — captured against a Q card collapsed + expanded pair (one image showing both states stacked, matching the layout of the existing reference).
- `08-disagreement-card.png` — D card.
- `09-issue-card.png` — Issue card with the lifecycle-leads-body anatomy (per spec 0205 Bug 2).
- `10-comments-card.png` — Comment card with the same lifecycle-leads anatomy.

Use the same canonical-run / canonical-card selection criteria documented at `design-system/SPEC.md:378` (the existing rule). Use the Claude Preview MCP at `localhost:6173` for the capture (consistent with how `/dev-next` step 14 has been verifying UI for the last several specs).

**Each refreshed shot is committed alongside a tiny `.alt.md` sidecar** (or, equivalently, a one-line entry in a new `design-system/notion-issues/screenshots/REFERENCES.md` index) recording: capture date, app version (`/api/health` reading), canonical run ID, and which spec last shifted the anatomy. The index lets future specs know whether the reference is current relative to their own anatomy changes — closing the "are the references stale?" question the handoff flagged.

### 2.2 Produce the 8-capture parity grid as a follow-up PR comment on spec 0205's PR

The grid lives in two places:

- **Inline image grid in this spec's own PR description**, matching the standard `design-system/SPEC.md:378` shape (4 kinds × 2 states fresh captures, next to the four refreshed reference shots from §2.1).
- **A follow-up comment on https://github.com/Lexiz/dual-research/pull/235** that retroactively attaches the same grid to spec 0205's PR, with a one-line prefix ("Spec 0205.1 retroactive attachment of the parity grid mandated by `design-system/SPEC.md:378` — see spec 0205.1's PR for the full evidence and the refreshed reference baseline.") The retroactive attachment keeps the audit trail honest: a viewer reading PR #235 sees the grid that should have been there at merge time, with a pointer to where the work landed.

### 2.3 DS prose update: anatomy-departure footnote

Add a one-paragraph footnote to `design-system/SPEC.md:378` (or the adjacent §4.8 / §4.7) recording the intentional departures spec 0205 made from the pre-0205 anatomy — specifically:

- Issue + Comment expanded body now lead with `ItemCardLifecycleSection` (spec 0205 Bug 2). Pre-0205 references showed a standalone body block above lifecycle.
- Expanded `SourceRow` renders excerpt as `<blockquote>` not `<pre>`, with label · value grid for URL · FETCHED · SEARCH QUERY (spec 0205 Bug 1).
- Head Sources chip + `.item-card__sources-hd` segment header both carry `mdi:link-variant` glyph (spec 0205 Bug 3).

The footnote anchors future parity grids: they compare against the *current* reference baseline + the documented departures, not against drift from a single point-in-time snapshot.

## 3. What it would catch

The chronic failure mode this spec closes is **visual regression that slips through because the parity grid wasn't attached**. The DS prose at `design-system/SPEC.md:378` names four prior specs (0138 / 0141 / 0144 / 0151) where this exact failure happened — specs cited the references in prose but didn't verify rendered output, and visual regressions landed silently. Spec 0205 *almost* repeated the same failure: five regressions caught visually by the user via screenshots, none caught by tests, and the merged PR shipped without the grid that would have surfaced any new regressions in the fix itself.

Concretely:

- **For spec 0205 retroactively** — the grid surfaces any visual regression the fix introduced beyond the five bugs the spec listed. With only a single-frame screenshot in PR #235, a regression in (say) the Q kind expanded body that wasn't part of the five-bug bundle would have shipped silently.
- **For future ItemCard-touching specs** — the refreshed reference baseline + the documented-departures footnote stops the next dev-next implementer from having to relitigate "are these references stale?" The same handoff text that named this deferral (`handoffs/2026-05-24-spec-0205-fix-p4-critique-card-five-visual-regressions.md:47`) won't recur because the baseline is no longer pre-0203.
- **For the spec author writing the §5 Regression-prevention block** — a current reference baseline means citations like *"matches `09-issue-card.png`"* mean what they say, instead of needing the per-spec mental rebase against intervening anatomy changes.

## 4. Risks

- **The "current anatomy" the references capture is a moving target.** Spec 0205.1's refresh is correct as of v1.44.2 deploy; the next ItemCard-touching spec will shift it again. Mitigation: the `REFERENCES.md` index per §2.1 records app-version + which spec last shifted the anatomy, so future drift is visible at a glance rather than discovered by surprise.
- **Eight captures × four references = nine images per PR.** Bigger PR diffs, more network for git operations on the spec branch. Mitigation: the grid is image-only, no JSX / CSS churn. The author worktree's git push already handles binary assets without issue (the existing references are PNGs of similar size).
- **The retroactive PR comment on https://github.com/Lexiz/dual-research/pull/235 is a manual step that dev-next doesn't currently automate.** Mitigation: spec is explicit about the step at §2.2; the comment text template is documented inline ("Spec 0205.1 retroactive attachment of the parity grid mandated by `design-system/SPEC.md:378`…"). Future dev-next could grow a "retroactive parity grid" step that takes a spec id + the dependent spec id and posts the comment; out of scope here.
- **Reference replacements could destabilize older specs' PR descriptions** if anything linked to the existing `07–10-…png` URLs by hash or LFS pointer (the repo doesn't use LFS, but the merge-commit hashes are stable). Mitigation: the filenames stay the same; only the image contents change. Existing PR descriptions that embed the references show the refreshed content automatically, which is the desired behaviour for future parity grids.
